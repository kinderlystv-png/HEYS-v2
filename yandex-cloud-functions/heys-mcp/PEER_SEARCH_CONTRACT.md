## Что наблюдается

`heys_search_products` в кураторском режиме ищет **не только в списке текущего
клиента**: продукты других клиентов этого куратора попадают в выдачу
автоматически, без отдельного параметра.

### Поля результата

| Источник     | `source`               | `writable`  | `owner_client_id` / `owner_client_name` |
| ------------ | ---------------------- | ----------- | --------------------------------------- |
| Свой список  | `мой список`           | `true`      | отсутствуют                             |
| Чужой список | `список <Имя клиента>` | **`false`** | **заполнены**                           |
| Общая база   | `общая база`           | `true`      | отсутствуют                             |

Пример чужой строки (запрос от Антона, продукт Александры):

```json
{
  "product_id": "p_1786171591803_ca4bd6",
  "name": "Пудинг Hyper High Protein Caramel (Ehrmann)",
  "source": "список Александра",
  "writable": false,
  "kcal100": 69.1,
  "protein100": 10,
  "carbs100": 6.4,
  "fat100": 1.5,
  "portions": [{ "name": "1 стакан", "grams": 200 }],
  "owner_client_id": "4545ee50-4f5f-4fc0-b862-7ca45fa1bafc",
  "owner_client_name": "Александра"
}
```

Симметрия проверена в обе стороны: запрос от Александры находит домашние
конверты Антона с `writable: false` и его `owner_client_*`. То есть индекс
строится по всем клиентам куратора, а не по одному «главному».

### Что переносится у чужого продукта

Нутриенты, `portions`, `piece_grams`, `barcode` — всё, что есть у своего.
Отличие только в `writable`, `source` и паре `owner_client_*`.

### Дубликаты не схлопываются

Один и тот же пудинг вернулся дважды: как чужой (`p_1786557085807_8fe908`,
`writable: false`) и как запись общей базы (`1580767e-…`, `writable: true`) — у
них разные `product_id` и одинаковый штрихкод. Схлопывания по штрихкоду или
имени нет.

### Порядок выдачи

Свой список → чужие списки → общая база.

### Цена

| Запрос                      | `duration_ms` |
| --------------------------- | ------------- |
| Только свои + общая база    | ~500          |
| С попаданием в чужие списки | 750–870       |

Разница ~250–350 мс — построение или чтение индекса чужих списков. Судя по
утраченному имени `ensurePeerIndex`, индекс строился один раз на инстанс с
кэшированием.

## Словесный контракт (уцелел в git)

[`lib/curator.js`](lib/curator.js), правило 8 — единственное, что пережило
потерю:

> Домашний рецепт другого клиента: `heys_search_products(scope=curator)` →
> `writable:false` → `heys_create_product(from_product_id)`, затем приём с НОВЫМ
> id. Не пиши peer-id в дневник.

Отсюда следует то, чего в снимке не видно:

- существовал параметр `scope` (значение `curator`) — но выдача включает чужие
  списки и **без** него, так что это, скорее всего, необязательный расширитель,
  а не выключатель;
- **peer-id нельзя записывать в дневник**: чужой продукт сначала копируется в
  свой список через `create_product(from_product_id)`, и приём пишется уже с
  новым id. Это главный инвариант — без него в дневнике клиента окажется ссылка
  на продукт из чужого overlay.

## Что проверить после восстановления

1. Поиск от Антона находит продукт Александры с `writable: false` и обоими
   `owner_client_*`; обратное направление тоже работает.
2. Свои продукты — `writable: true`, без `owner_*`.
3. `create_product(from_product_id=<peer id>)` создаёт **новый** продукт в своём
   списке; в дневник уходит новый id, не peer.
4. Порядок выдачи: свои → чужие → общая база.
5. Задержка на попадание в чужие списки не превышает наблюдавшиеся ~350 мс.
