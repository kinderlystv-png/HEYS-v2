# Аудит: запись еды через Telegram-бота

Дата: 2026-08-01. Вопрос: можно ли научить `heys-bot-client` записывать приёмы
пищи в дневник клиента, и реально ли это **без подключения LLM**.

Короткий ответ: свободный текст — нет, кнопочный ввод — да, но это не «доработка
бота», а новый контур с двумя нерешёнными архитектурными развязками.

## Что установлено проверкой кода

### Парсера свободного текста в проекте нет

- `parseAIProductString` (`apps/web/heys_models_v1.js:1351`) — парсер карточки
  **одного** продукта в формате «Ключ: значение», которую пользователь получает
  во внешнем AI-чате по промпту из `docs/AI_PRODUCT_PARSE_PROMPT.md` и вставляет
  руками. К разбору фразы «выпил капучино» отношения не имеет.
- `parsePasted`/`extractRow` (`apps/web/heys_core_v12.js:301,362`) — массовый
  импорт каталога продуктов: строка = название + хвост числовых нутриентов. Не
  приём пищи.
- `SmartSearchWithTypos` (`apps/web/heys_smart_search_v2.js`, 3216 строк) —
  поиск **одного** продукта: опечатки, Левенштейн, фонетика, транслит, синонимы,
  персональный буст. Граммовку не извлекает, несколько продуктов из строки не
  выделяет. Прод-тестов нет; `packages/search` из `apps/*` не импортируется.
- Вызовов LLM нет нигде — ни во фронте, ни в cloud functions. Единственный
  внешний AI-сервис — Yandex SpeechKit (STT) в `heys-cron-speechkit-transcribe`.

Вынести на сервер нечего: `heys_models_v1.js` закрыт как `})(window)` и в Node
падает на загрузке; `heys_smart_search_v2.js` при загрузке трогает
`localStorage`/`HEYS.store`/`document`, а ранжирование зависит от накопленной в
браузере статистики.

### Что в боте уже готово

- Привязка `chat_id ↔ client_id`: `handleStartCommand`
  (`yandex-cloud-functions/heys-bot-client/index.js:638`) → SQL
  `claim_pin_token_chat`; связь лежит в `clients.telegram_chat_id`, индекс
  `clients_telegram_chat_idx` есть.
- Транспорт Telegram с DNS-фолбэком и таймаутами (`index.js:214-459`).
- **Рабочий stateless пошаговый диалог кнопками**: квиз start-бота держит
  состояние прямо в `callback_data` (`encodeQuizData`/`decodeQuizData`,
  `index.js:854-865`, `buildInlineKeyboard:867`, обработка
  `handleStartBotCallback:1425`). Это готовый шаблон для пошагового ввода еды.
- Пул подключений к БД и Lockbox-секреты функции уже настроены.
- Гейт подписки на запись дня работает на уровне БД
  (`client_kv_value_can_write`) и сработает для любого пути записи.

### Два блокера, которые не обойти доработкой

**1. Бот не может определить, кто ему пишет.** В `index.js` нет ни одного
запроса `SELECT ... FROM clients WHERE telegram_chat_id = $1`, а runtime-роль
`heys_rpc` прав на таблицу `clients` не имеет: `REVOKE ALL ON ALL TABLES` в
`database/2025-12-25_p1_runtime_user_heys_rpc.sql`, права выдаются точечно на
функции. Нужна новая SECURITY DEFINER функция `get_client_by_chat_id` + грант.

**2. Боту нечем писать от лица клиента.** `issue_client_session` явно отозвана у
runtime-роли (`database/2025-12-25_p1_grants_heys_rpc_only.sql:127`) — сессию
без PIN получить нельзя, это сделано намеренно. Остаётся
`batch_upsert_client_kv_by_curator`: SQL-функция проверяет только владение
(`clients.curator_id = p_curator_id`), JWT не смотрит — то есть бот технически
мог бы писать под curator_id. Но это означает завести «системного куратора» и
обойти HTTP-слой, где сегодня curator_id подставляется из JWT. Архитектурного
решения на это нет.

### Прочее, чего нет

- Обработки `callback_query` у клиентского бота нет вообще; при поллинге стоит
  `allowed_updates: ['message']` (`index.js:1783,1808`) — Telegram кнопки от
  клиента даже не пришлёт.
- Формата дневного блоба бот не знает: вся сборка приёма живёт в вебе.
- Нет rate limiting, нет аудита действий клиента, нет обработчика отказа
  `subscription_required`.
- Тестов на запись данных нет (`pnpm bot:crm-test` покрывает
  лиды/квиз/PIN-claim).

## Что это значит для сценариев

| Сценарий                                                         | Реально без LLM | Чего стоит                                             |
| ---------------------------------------------------------------- | --------------- | ------------------------------------------------------ |
| «Выпил капучино» свободным текстом                               | **Нет**         | Нужен LLM-вызов, которого в проекте нет ни одного      |
| Кнопки: повторить набор, +250 мл воды, повторить вчерашний приём | Да              | 2 блокера выше + 6 пунктов ниже                        |
| Поиск произвольного продукта кнопками с пагинацией               | Да, но дорого   | Отдельный UI-контур поверх `get_shared_products`       |
| Голосом «съел то-то»                                             | Нет             | SpeechKit даёт текст, дальше упирается в тот же парсер |

## Оценка объёма для кнопочного варианта

Переиспользуется: привязка chat_id, транспорт Telegram, шаблон диалога через
`callback_data`, пул БД, SQL-примитивы записи и гейт подписки.

Писать заново: (1) SQL-функция резолва клиента по chat*id + грант; (2) развязка
по праву записи — системный куратор либо новая SECURITY DEFINER функция под
бота; (3) обработка `callback_query` и смена `allowed_updates`; (4) сборка
приёма в формат `heys_dayv2*\*` на стороне функции; (5) сам пошаговый UI (выбор
приёма, выбор набора/продукта, граммовка); (6) обработка отказа подписки; (7)
rate limiting; (8) тесты.

## Рекомендация

**Не начинать бота сейчас.** Причины:

1. Самое ценное — свободный текст — без LLM недостижимо, а именно оно уже
   закрыто MCP-коннектором.
2. Кнопочный бот покрывает только повторяющееся (наборы, вода) — то же самое
   одной фразой делается через коннектор, который работает с телефона.
3. Оба блокера — это ослабление модели доступа: либо новый путь записи в обход
   HTTP-слоя, либо системный куратор. Платить этим за дублирование существующего
   сценария рано.

Что имеет смысл сделать **вместо** бота, если хочется скорости:
`intent_type: 'meal'` в мессенджере (`heys-api-messages`) уже валидируется, но
применение в дневник не реализовано — `apply_intent` помечен TODO и в коде, и в
SQL-миграции (`database/2026-05-27_client_messages.sql:578`). Это готовое
посадочное место: один серверный путь «структурированный intent → приём пищи»,
которым потом смогут пользоваться и мессенджер, и бот, и MCP. Начинать надо с
него, а не с Telegram-UI.

## Когда вернуться к боту

- Появился LLM-контур с решённой трансграничкой по 152-ФЗ, или
- клиенты (не владелец) просят ввод из Telegram, или
- `apply_intent` закрыт, и Telegram остаётся единственным недостающим
  транспортом.
