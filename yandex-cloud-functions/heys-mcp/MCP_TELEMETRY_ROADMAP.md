# MCP-телеметрия: связка «что спросили» ↔ «как отработал сервер»

Живой статус модуля. Тайминги и разбор отдельных замеров — в
[TIMING_LOG.md](TIMING_LOG.md), состав строки лога — в
[lib/telemetry.js](lib/telemetry.js).

## Цель

Сегодня по логам видно, **что** вызывалось и сколько это стоило, но не видно,
**зачем**: текста запроса в логе нет. Нужна машиночитаемая связка «реплика
куратора → цепочка вызовов → суммарное время», чтобы находить лишние круги
(`list_clients` → `get_day` → повтор) не на глаз по таймстампам.

## Что уже работает

- Телеметрия на горячем пути: `duration_ms` в ответе инструмента и строка
  `t=mcp_call` в Cloud Logging на каждый вызов.
- Состав строки — белый список `RECORD_FIELDS`
  ([telemetry.js:29](lib/telemetry.js)): инструмент, тайминги, `session_id`,
  `seq`, `upstream_*`, код ошибки. Ни текста запроса, ни аргументов, ни текста
  исключения. Тест на утечку читает этот же список, поэтому поле нельзя добавить
  мимо него.
- Строка `t=mcp_list` на каждый `tools/list` — сделано 2026-08-18: сколько схем
  и байт ушло клиенту, его `clientInfo.name/version` из `initialize` и версия
  протокола. Свой белый список `LIST_RECORD_FIELDS`, отдельный от
  `RECORD_FIELDS`; сам список инструментов в лог не идёт, только размер. Повод:
  18.08 агент ответил «heys_update_day не поднимается», в телеметрии было 0
  вызовов и 0 ошибок, и отличить «клиент не донёс инструмент до модели» от
  «модель не позвала» было нечем. Имя и версия клиента — свойства программы, не
  человека, ПДн-контур не меняется.
- Лог-группа телеметрии — `e23ndggvq798r3v3eepq` (не тот id, что отдаёт
  `logging group list`). Порядок чтения — в `TIMING_LOG.md`.
- Читать логи через `yc serverless function logs` (stdout функции) или через
  `yc logging read --filter 'message: "mcp_call"'` — строка лежит в `message`, и
  фильтр по подстроке сообщения работает быстро (проверено 2026-08-18). Фильтр
  по `json_payload.t` пуст: YC не парсит stdout в `json_payload`. Без `--filter`
  выборка бесполезна: `--limit` отдаёт начало окна, а не свежие записи, и
  `mcp_call` в него обычно не попадает.

## Ограничение, которое определяет всю Фазу 2

**Текст запроса в Cloud Logging не кладём.** Это новый слой ПДн с другим
retention и правкой перечня обработки — в миграции это прямо оговорено. Реплика
куратора уже хранится в задачнике (`**Кин:** …` в checkpoint и
write-инструментах), поэтому связку строим через псевдонимы, а не через текст.

**`session_id` — не идентификатор чата.** Это `sha256(token|instance)[:12]`
([telemetry.js:68](lib/telemetry.js)), и он ведёт себя в обе стороны плохо:

- cold start меняет инстанс → длинный разговор разрезается на несколько id;
- два параллельных чата под одним токеном на одном инстансе → **один** id и
  перемешанные `seq`.

Отсюда направление связки: **сервер → клиент → стенограмма**. Сопоставлять
задним числом «логи → стенограмма» по одному `session_id` нельзя, результат
неоднозначен.

**`session_id` и `seq` возвращаются клиенту с 2026-08-17** — до этого в ответе
был только `duration_ms`, и правило «пиши `mcp_session_id` в стенограмму» было
невыполнимо: агент этих значений просто не знал. Теперь знает (шаг 1 фазы 2
ниже).

### Инцидент 2026-08-17: деплой в обход `zip` уронил прод

На машине нет `zip`, и `deploy-all.sh` падал на упаковке. Обход через
`tar -a -cf out.zip` дал файл с расширением `.zip`, который zip'ом не является:
в Git Bash на Windows `-a` не переключился на zip-формат по расширению и отдал
обычный tar. Проверяется одной строкой — в central directory ноль записей.

YC такой файл принял: версия `d4e0npals5keua1vbedo` создалась и получила статус
ACTIVE, а распаковаться не смогла. Отсюда
`Cannot find module '/function/code/index.js'` и `502` на каждый вызов с 17:11
до 17:22 UTC. Восстановлено версией `d4evjg5jakq2grrqedr2`: архив собран 7-Zip
(`7z a -tzip`), состав проверен чтением central directory — `index.js` в корне,
`lib/` папкой, разделители прямые; env скопирован с последней рабочей версии.

Первоначальный разбор называл причиной вложенную папку — это было неверно, tar
вскрылся только при чтении самого файла.

**Починено в тот же день** в [deploy-all.sh](../deploy-all.sh): упаковщик
выбирается сам (`zip`, иначе 7-Zip; если нет ни одного — отказ вместо ручного
обхода), а состав архива проверяется до заливки — точка входа обязана лежать в
корне, обратных слешей быть не должно. Проверено на трёх случаях: правильный
архив проходит, tar под видом zip отклоняется (имён нет вовсе), архив с
вложенной папкой тоже.

Постоянное следствие шире этого скрипта: **успешная упаковка ничего не
доказывает**. Сегодня и упаковка, и `version create`, и статус ACTIVE отработали
штатно — функция при этом не стартовала вовсе.

Гейт `autoDeploy: false` для `heys-mcp` снят 2026-08-18 решением владельца:
коннектор деплоится тем же пушем, что и остальной API. Причина отмены — ручной
выкат систематически забывался при ~190 коммитах в месяц, а клиентский PDn/OAuth
канал выключен отдельно и от этого флага не зависел. Вывод этого раздела при
этом остаётся в силе, поэтому post-deploy verify в `cloud-functions-deploy.yml`
теперь смоукает живой `/mcp` (метаданные 200, POST 401), а не довольствуется
статусом ACTIVE.

## Фаза 2 — связка «вопрос ↔ телеметрия» (вариант D+)

Порядок обязателен: без первого шага второй не реализуем.

1. ✅ **Сервер возвращает `session_id` и `seq`** в `structuredContent` рядом с
   `duration_ms` — сделано 2026-08-17. ПДн-контур не изменился: `RECORD_FIELDS`
   те же, оба поля и раньше уходили в Logging, `session_id` — срез хэша, `seq` —
   целое. Номер резервируется `telemetry.begin()` **до** обработчика, поэтому
   ответ и строка лога несут одно и то же значение, а `seq` считает порядок
   начала вызовов, а не завершения (на одном инстансе они идут параллельно).
   Отказы инструментов тоже несут оба поля. Тесты — в
   [`__tests__/telemetry.test.cjs`](__tests__/telemetry.test.cjs).
2. ✅ **Запись в стенограмму** — на проде с 2026-08-17. Метка
   `[mcp session=<id> seq=<n> ts=<ISO>]` дописывается **сервером** последней
   строкой блока, в одном месте — в `tasks_checkpoint` после всех проверок
   формата. Отдельной правки в каждом `heys_add_water` / `heys_log_meal` не
   нужно: дневниковые записи зовут checkpoint из общей обёртки
   ([curator.js:1278](lib/curator.js)). Модель `session_id` не передаёт и знать
   его не может — в момент сборки блока он ей неизвестен.

   Метка берётся из контекста вызова
   ([lib/call-context.js](lib/call-context.js)): вложенный checkpoint видит
   метку **внешнего** инструмента, то есть того обмена, который он и записывает.
   Два write в одном ходе дают два блока и две метки с разным `seq` — это два
   обмена, а не один.

   Список `{tool, seq, duration_ms}` в блок не кладём: он дублировал бы лог и
   устаревал бы при повторной записи. Хватает одной пары.

3. **Read-only обмены — enforcement не первым шагом.** `heys_list_clients`,
   `heys_get_day`, `tasks_context` стенограмму не пишут. Своей метки им не
   нужно: correlate берёт вызовы в окне времени вокруг write, и read
   подтягиваются сами. Требовать `tasks_checkpoint` на каждый `get_day` дорого и
   вредно: под таким правилом модель начнёт писать блоки ради галочки, и отчёт
   станет ложным.
4. ✅ **`scripts/mcp-correlate.mjs`:** стенограмма + лог `mcp_call` → отчёт
   «запрос → N вызовов → Σ ms». Якорь — окно ±5 мин вокруг `ts` метки (или
   `## ЧЧ:ММ` по Москве, если метка старая). Не `session_id`+`seq`: см.
   вопрос 4. **Живой gate 2026-08-17:** лог↔стенограмма на 6 записях
   (22:03–22:04); read с чужим `session_id` цепляется к write по окну; окна ±5
   мин хватает. Один ход куратора может дать **два блока** с одной репликой
   (чек-ин + вода) — `mergeSameTurnExchanges` схлопывает их перед correlate.

## Фаза 3 — метрики эффективности

1. **`tasks_mcp_trace` (кураторский MCP):** по запросу связывает блок
   стенограммы с цепочкой `mcp_call` из **Postgres** (`mcp_call_events`).
   Подтверждённые вызовы — `session_id` совпал с меткой; вероятные — только окно
   ±5 мин. Использует `mergeSameTurnExchanges` (см. gate фазы 2). Живой gate
   2026-08-17: обмен 22:04 → `heys_get_day` → `heys_add_water` → `tasks_read`.
   **Flow-разложение (2026-08-18):** `confirmed_ms` (сумма HEYS), `wall_span_ms`
   (стена цепочки по ts), `gaps_ms` (паузы агента между вызовами), `flow_steps`,
   предупреждения о дублях `get_day`/`search`/`list_clients` и паузах ≥10 с.
   `pre_chain_ms` — от ## ЧЧ:ММ до первого вызова; `post_chain_ms` — от конца
   цепочки до ts метки write. Cursor «musing» / search tools сюда не входят —
   только timestamps из Postgres.

Дашборд поверх `mcp-stats` и correlate: доля лишних пар вызовов, распределение
`duration_ms` по инструментам, цепочки с аномальным числом `seq`.

## Открытые вопросы

1. Нужна ли связка для **client**-коннектора? Там стенограммы нет, механизм
   будет другой.
2. Хватит ли D+ для audit, или нужен `turn_id` на уровне одного сообщения Claude
   — если API его отдаёт.
3. Ставить ли `psql` на машину ради `mcp-stats`, или переписать сам скрипт на
   Node + `pg` — проверка миграции показала, что этого пути достаточно.
4. **Cold start режет `session_id`.** Живая проверка 2026-08-17: три вызова
   одного разговора — три разных `session_id`, у каждого `seq=1`
   (`heys_list_clients` 17:21, `heys_add_water` 21:33, `tasks_read` сразу
   следом). При `concurrency: 1` инстанс гаснет между вызовами. Диапазон seq
   внутри сессии собирает пустоту. Менять формулу `session_id` бесполезно: `seq`
   всё равно в памяти процесса и на каждом cold start снова 1. Correlate поэтому
   идёт по времени. `mcp_seq_daily` считает пары внутри `session_id` и при таком
   трафике занизит «лишние круги» — не читать его как «модель ходит коротко».

### Ловушка `yc logging read --since`

**`--since 8h` и длиннее часто отдаёт `[]` при том же `--filter`, что и
`--since 6h`/`1h`.** Это лимит CLI (~7h), не отсутствие трафика. Пустой JSON
**не записывать** в доки как «нет mcp_call в Logging».

Проверено 2026-08-18: группа `e23ndggvq798r3v3eepq`, фильтр
`message: "mcp_call"` — `1h`/`6h`/`7h` дают строки, `8h`/`24h`/`72h` → `[]`.
Обход — окна по **6h** с `--since`/`--until` RFC-3339:

```bash
node scripts/mcp-baseline-fetch.mjs
node scripts/mcp-baseline-p50.mjs ops/mcp-call-baseline-pre-deploy.json
```

Парсер baseline: `extractRecord(entry)` — целиком entry; `mcp_call` в поле
`message`, не в `json_payload.t`.

Из выгрузки посчитать p50 `duration_ms` **по каждому `tool`** (артефакт
сохранить рядом с deploy receipt).

**Prod smoke после deploy** (пустой ответ и «нет ошибки» не засчитываются):

1. Любой MCP tool → строка в `mcp_call_events` за 5 мин.
2. Свежий обмен: `tasks_checkpoint` →
   `tasks_mcp_trace({ heading: ЧЧ:ММ из checkpoint })` (date по умолчанию =
   **taskDay**, сутки с 03:00 МСК — как у checkpoint) → ≥1 **confirmed**. Старые
   обмены (до deploy) в Postgres не попадут — это принятый исторический разрыв,
   не баг.
3. **p50 vs p50** после deploy: по каждому `tool` на **естественном** трафике за
   ~24h (не искусственная нагрузка) — post-deploy p50 `duration_ms` vs
   pre-deploy baseline из Logging; рост ≤10%. Замер — **2026-08-19 вечер**
   (чеклист в `todo.md`, блок MCP-телеметрия). Одна–две точки smoke **не
   считаются**. `persist_ms` в логах — только если медианы разойдутся.

Gate 22:04 (unit/offline correlate на mock-строках) — **не** prod smoke.

**Если trace пустой на свежем обмене:** 401/403 на `list_mcp_call_events` (JWT)
vs пустая выборка (сырьё не пишется / нет метки в стенограмме).
