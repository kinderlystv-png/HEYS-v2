# MCP-телеметрия: связка «что спросили» ↔ «как отработал сервер»

Живой статус модуля. Тайминги и разбор отдельных замеров — в
[TIMING_LOG.md](TIMING_LOG.md), состав строки лога — в
[lib/telemetry.js](lib/telemetry.js).

## Цель

Сегодня по логам видно, **что** вызывалось и сколько это стоило, но не видно,
**зачем**: текста запроса в логе нет. Нужна машиночитаемая связка «реплика
куратора → цепочка вызовов → суммарное время», чтобы находить лишние круги
(`list_clients` → `get_day` → повтор) не на глаз по таймстампам.

## Что уже работает

- Телеметрия на горячем пути: `duration_ms` в ответе инструмента и строка
  `t=mcp_call` в Cloud Logging на каждый вызов.
- Состав строки — белый список `RECORD_FIELDS`
  ([telemetry.js:29](lib/telemetry.js)): инструмент, тайминги, `session_id`,
  `seq`, `upstream_*`, код ошибки. Ни текста запроса, ни аргументов, ни текста
  исключения. Тест на утечку читает этот же список, поэтому поле нельзя добавить
  мимо него.
- Лог-группа телеметрии — `e23ndggvq798r3v3eepq` (не тот id, что отдаёт
  `logging group list`). Порядок чтения — в `TIMING_LOG.md`.
- Читать логи только через `yc serverless function logs` — это stdout функции, и
  строка `mcp_call` лежит в `message`. `yc logging read` с фильтром по
  `json_payload.t` отдаёт пустой результат и может идти десятки минут: YC не
  парсит stdout в `json_payload`.

## Ограничение, которое определяет всю Фазу 2

**Текст запроса в Cloud Logging не кладём.** Это новый слой ПДн с другим
retention и правкой перечня обработки — в миграции это прямо оговорено. Реплика
куратора уже хранится в задачнике (`**Кин:** …` в checkpoint и
write-инструментах), поэтому связку строим через псевдонимы, а не через текст.

**`session_id` — не идентификатор чата.** Это `sha256(token|instance)[:12]`
([telemetry.js:68](lib/telemetry.js)), и он ведёт себя в обе стороны плохо:

- cold start меняет инстанс → длинный разговор разрезается на несколько id;
- два параллельных чата под одним токеном на одном инстансе → **один** id и
  перемешанные `seq`.

Отсюда направление связки: **сервер → клиент → стенограмма**. Сопоставлять
задним числом «логи → стенограмма» по одному `session_id` нельзя, результат
неоднозначен.

**`session_id` и `seq` сейчас клиенту не возвращаются.** В ответе инструмента
только `duration_ms` ([lib/mcp.js:215](lib/mcp.js)). Поэтому правило «пиши
`mcp_session_id` в стенограмму» невыполнимо до серверной правки — агент этих
значений не знает.

### Инцидент 2026-08-17: деплой в обход `zip` уронил прод

На машине нет `zip`, и `deploy-all.sh` падает на упаковке. Обход через `tar -a`
собрал архив с файлами внутри вложенной папки — версия `d4e0npals5keua1vbedo` не
стартовала вообще (`Cannot find module '/function/code/index.js'`), MCP отдавал
`502` на каждый вызов с 17:11 до 17:22 UTC. Восстановлено версией
`d4evjg5jakq2grrqedr2`: архив собран 7-Zip (`7z a -tzip`, содержимое в корне,
прямые слеши — проверено чтением central directory), env скопирован с последней
рабочей версии.

Из этого два постоянных следствия:

- **Перед деплоем проверять состав архива**, а не только код возврата упаковки.
  `index.js` обязан лежать в корне, `lib/` — папкой, разделители прямые.
- **`deploy-all.sh` знает только `zip`**
  ([deploy-all.sh:903](../deploy-all.sh)). Для машин без него нужен либо `zip` в
  PATH, либо ветка на `7z` в самом скрипте. Пока не сделано — обход остаётся
  ручным и опасным.

Гейт `autoDeploy: false` для `heys-mcp` сохраняется: выкат только через
`ALLOW_DISABLED_FUNCTIONS` с причиной.

## Фаза 2 — связка «вопрос ↔ телеметрия» (вариант D+)

Порядок обязателен: без первого шага второй не реализуем.

1. **Сервер возвращает `session_id` и `seq`** в `structuredContent` рядом с
   `duration_ms`. ПДн-контур это не меняет: оба уже уходят в Logging,
   `session_id` — срез хэша, `seq` — целое.
2. **Запись в стенограмму.** В блок write-инструментов и `tasks_checkpoint`
   добавляются `mcp_session_id` и список `{tool, seq, duration_ms}`. Нужен и
   `ts`: стенограмма ведётся по МСК-дню, телеметрия — в UTC.
3. **Read-only обмены.** `heys_list_clients`, `heys_get_day`, `tasks_context`
   стенограмму не пишут вообще, а типичная цепочка — 2–5 read и один write. Без
   обязательного `tasks_checkpoint` с репликой куратора половина кругов
   останется без текста. Правило З6 уже есть — нужен enforcement и тест.
4. **`scripts/mcp-correlate.mjs`:** стенограмма за день + Logging по
   `session_id` → отчёт «запрос → N вызовов → Σ ms».

## Фаза 3 — метрики эффективности

Дашборд поверх `mcp-stats` и correlate: доля лишних пар вызовов, распределение
`duration_ms` по инструментам, цепочки с аномальным числом `seq`.

## Открытые вопросы

1. Применена ли миграция телеметрии на prod DB? Проверить с устройства — через
   Node + `pg`, либо поставить `psql`.
2. Нужна ли связка для **client**-коннектора? Там стенограммы нет, механизм
   будет другой.
3. Хватит ли D+ для audit, или нужен `turn_id` на уровне одного сообщения Claude
   — если API его отдаёт.
4. Чинить ли `deploy-all.sh` под окружение без `zip`, или закрепить `zip` как
   требование к машине.
