# heys-mcp — remote MCP connector для HEYS

Даёт ассистенту (ChatGPT, claude.ai, Cowork, Claude Desktop, Claude Code)
возможность вести дневник HEYS за пользователя: «выпил кофе в студии» → приём
пищи появляется в PWA.

Работает с любого устройства, включая телефон: запрос идёт из облака OpenAI или
Anthropic в `https://api.heyslab.ru/mcp`, компьютер пользователя не участвует.

**Инструкция для куратора — [CURATOR_GUIDE.md](CURATOR_GUIDE.md):** что можно
сделать с данными клиентов через чат, какими словами, что требует подтверждения
и чего коннектор не делает. Этот README — про устройство и деплой.

## Два решения, которые определяют всё остальное

**1. Функция не ходит в БД.** Запись дня идёт через
`merge_save_client_kv_by_session` в `heys-api-rpc` — тем же путём, что и PWA.
Там живут row-lock, cross-client guard, валидация контракта, `data_loss_audit` и
алерты. Прямой доступ к `client_kv_store` означал бы второй путь записи, который
неизбежно разойдётся с первым.

**2. Состояние OAuth не хранится в БД.** `client_id`, authorization code, access
и refresh — подписанные HS256-структуры. Access-токен несёт внутри зашифрованный
client-session HEYS, поэтому **отзыв доступа = отзыв сессии пользователя**:
выход из аккаунта в приложении мгновенно обрывает доступ ассистента. Отдельного
стора отозванных токенов нет намеренно.

Следствие, которое надо знать: authorization code внутри своих 5 минут
технически переиспользуем (stateless). Атака этим не эксплуатируется — обмен
требует PKCE `code_verifier`, который есть только у легитимного клиента.

## Кураторский режим

Один коннектор — все клиенты куратора. На странице входа секция «Я куратор —
вход по email»: email + пароль (+ код 2FA, если включена). После входа:

- появляются собственные инструменты куратора, а каждый инструмент дневника
  получает параметр `client` (имя или client_id):

  | Инструмент                 | Назначение                                                      |
  | -------------------------- | --------------------------------------------------------------- |
  | `heys_list_clients`        | Кого ведёт куратор: client_id, имя, статус подписки             |
  | `heys_list_inbox`          | Кто написал и сколько сообщений ждёт ответа — по всем клиентам  |
  | `heys_list_messages`       | Переписка с клиентом, включая расшифровки голосовых             |
  | `heys_mark_message_done`   | Отметка «просьба внесена» — защита от повторного внесения       |
  | `heys_reply_message`       | Ответ клиенту в мессенджере приложения                          |
  | `heys_get_photo`           | Фото из переписки — изображением в ответ, а не ссылкой          |
  | `heys_moderate_products`   | Очередь общей базы, а также скрытие ошибочно опубликованного    |
  | `heys_create_client`       | Новый клиент: имя, телефон, PIN                                 |
  | `heys_client_access`       | Ссылка входа и перевыпуск PIN                                   |
  | `heys_manage_subscription` | Продление и сброс подписки                                      |
  | `heys_trial_queue`         | Очередь на триал: список, активация, отказ                      |
  | `heys_leads`               | Заявки с лендинга: список и смена статуса                       |
  | `heys_get_client_health`   | Сессии и входы клиента — на жалобы «не заходит», «не синкается» |

  `heys_list_clients`, `heys_list_inbox`, `heys_moderate_products`,
  `heys_create_client` и `heys_leads` работают без адресата: они и нужны затем,
  чтобы его выбрать или относятся ко всем клиентам сразу;

- для записи и действий наружу параметр обязателен всегда, даже при единственном
  клиенте, и имя матчится только целиком; для чтения остаётся мягкий режим
  (частичное совпадение, авто-подстановка единственного клиента). Подробности и
  повод — «Адресация записи строгая» ниже;
- каждый ответ начинается с имени клиента: `[Александра] Записал…`;
- каждый инструмент, меняющий день, возвращает `day_after` — итог дня по версии
  сервера, чтобы «внёс» не было отчётом о намерении;
- данные ходят кураторскими путями (`merge_save_client_kv_by_curator`,
  `batch_upsert_client_kv_by_curator`, REST с Bearer JWT) — ownership проверяет
  SQL. Write-context на клиента тоже выдаётся, но защитой от промаха адресации
  он не является: см. «Адресация записи строгая» ниже;
- кураторский JWT живёт 24 часа, но коннектор не протухает: на refresh функция
  перевыпускает JWT сама (сырой `JWT_SECRET` уже приходит из Lockbox-overlay,
  формат claims повторяет `createJwt` из heys-api-auth). С SEC-031 перевыпуск
  возможен только после ответа `GET /auth/curator-status`: если аккаунт куратора
  отключён (`curators.is_active = false`) или сервер недоступен, продление не
  происходит;
- логика инструментов общая с клиентским режимом: `createTools` не менялся,
  кураторский слой — адаптер API на клиента (`lib/curator.js`).

Отзыв кураторского доступа (SEC-031, формулировка исправлена 2026-08-02):
отключение коннектора в Claude убирает доступ только на стороне Claude и
**ничего не отзывает на сервере** — прежний текст здесь обещал обратное.
Мгновенного отзыва для кураторов нет: их JWT stateless, как и в веб-приложении.
Что реально работает: `curators.is_active = false` прекращает продление сессии
на ближайшем refresh, но уже выданный JWT доживает свои 24 часа. Полный отзыв
требует `token_version` — задача D5 в [`todo.md`](../../todo.md).

Для клиентского режима отзыв настоящий: внутри токена лежит серверная сессия, её
гасит `revoke_session`.

### Три решения, которые видно в поведении

**Адресация записи строгая, адресация чтения — нет (2026-08-02).** Серверной
страховки от «записал не тому клиенту» в этом пути нет: write-context выдаётся
по тому же `client_id`, который уходит в запись, поэтому серверная сверка
контекста с целью здесь тавтологична — она ловит рассинхрон браузерного стейта,
а не промах адресации коннектора (`HEYS_WRITE_CONTEXT_STRICT` к тому же
выключен, режим warn-only). Значит вся защита живёт в `lib/curator.js`. Для
пишущих инструментов (`WRITE_TOOLS` в `lib/tools.js`, 14 штук) и действий наружу
— ответ в мессенджер, PIN и ссылка входа, подписка, активация триала — `client`
обязателен по схеме и принимается только точно: `client_id` или имя, совпавшее
целиком. Единственный клиент куратора в этих инструментах молча не
подставляется. Для чтения (`heys_get_day`, поиск, период, профиль, переписка)
осталось прежнее поведение: частичное совпадение и авто-подстановка
единственного клиента — цена промаха там несопоставима. Повод: в живой сессии
2026-08-02 все шесть вызовов ушли строкой имени («Полтавский», «Александра»),
сервер принял по подстроке молча, а коллизии с `E2E-TestPopl` не случилось по
удаче. Тесты — `__tests__/curator.test.cjs`, четыре теста про строгую адресацию.

**Инструмент записи отчитывается состоянием дня, а не намерением (2026-08-02).**
Каждый инструмент, меняющий день, возвращает `day_after`: калории, число
приёмов, вода и `outcome` merge — посчитанные по блобу, который вернул сервер в
`v` из `merge_save`, а не по нашей оптимистичной копии. До этого ответ `ok`
означал «запрос принят»: если merge слил нашу запись с параллельной правкой
клиента, отбросил её как stale или в дне уже лежал такой же приём от повторного
вызова, ассистент об этом не узнавал и отчитывался «внёс» — увидеть расхождение
можно было только отдельным `heys_get_day`, которого он обычно не делает.
Лишнего round-trip нет: блоб приходит тем же ответом. Инструкция режима требует
сверять `day_after` с ожиданием и называть расхождение вслух. Это не заменяет
идемпотентность записи — задвоенный ретраем приём по-прежнему ляжет двумя
приёмами, просто теперь он виден в счётчике.

**Показатели дня в подтверждении, а не только калории (2026-08-21).**
`day_after` отдаёт ещё `steps`, `weight_morning`, `household_min`, `sleep`,
`morning`, `sleep_note` и `comment` — из того же серверного блоба. В тексте
ответа показатели печатают только инструменты, которые их правят
(`heys_update_day`, `heys_checkin`), и только те поля, что вошли в `applied`:
строкой `В дне после записи: шаги 8000, вес 90.7 кг.` В ответ на еду или воду
они не попадают — там это шум. Повод: 20.08.2026 вызов `heys_update_day(steps)`
прошёл без ошибки, в дне остался 0, а подтверждение показывало только калории,
приёмы и воду — потеря записи была неотличима от успеха, и ассистент отчитался
«обновил steps». Теперь ноль назван вслух. Тесты — `__tests__/tools.test.cjs`,
четыре теста про показатели в подтверждении.

**Пакетная правка дней и приёмов (2026-08-22).** `heys_update_day(days[])` — до
14 дат одним вызовом («шаги за пять дней»), `heys_update_meal(updates[])` — до
10 приёмов («сахар в каждый кофе»). Обе формы раскладываются на те же одиночные
записи внутри вызова, поэтому поведение и ответ дня не меняются; дубль даты или
`meal_id` в списке отклоняется, чтобы две правки одной сущности не перетирали
друг друга молча. Повод — замер 15:59: после того как поиск ушёл из цепочки,
шесть вызовов из четырнадцати остались только потому, что пакетной формы для них
не существовало.

Тогда же `mcp_list` начал писать `conn_id`. Без него нельзя было ответить,
забрал ли конкретный чат новые схемы: `session_id` у запроса списка свой каждый
раз, и связать список с вызовами было нечем. Тесты — `__tests__/tools.test.cjs`
(«Несколько дат и несколько приёмов одним вызовом») и
`__tests__/telemetry.test.cjs`.

**Пустая выдача поиска — самый дорогой ответ (2026-08-22).** Замер
`tasks_mcp_trace` (обмен 13:28): 8 из 11 вызовов ушли на разведку вокруг двух
ненайденных позиций. «ареон» не находил «Грудку копчёную Орион» — в
`tokenMatches` опечатка допускается только при совпадающих первых трёх буквах, а
разъехались ровно гласные. «Домашний кофе» существовал только внутри наборов:
карточку удалили, снимок в пресете остался, и поиск честно отвечал «ничего».

Теперь пустая выдача отдаёт две подсказки. Первая — похожие по написанию
(`fuzzySearchProducts`): триграммный коэффициент Дайса и скелет согласных под
ошибки распознавания речи, порог 0.5, слова короче четырёх букв не участвуют.
Похожесть считается в памяти рядом с обычным скорингом — каталог уже лежит в
инстансе целиком, отдельный индекс не нужен, — и включается только при нулевой
точной выдаче, чтобы не тащить мусор в нормальные ответы. Вторая — позиции,
которые живут только в наборах: их можно записать через `heys_log_meal(preset)`
прямо сейчас, а карточку вернуть отдельно. Те же подсказки приходят в тексте
ошибки `product_not_found` при записи еды, чтобы следующий круг модели был
записью, а не ещё одним поиском. Тесты — `__tests__/products.test.cjs`
(«Похожесть как fallback пустого поиска») и `__tests__/tools.test.cjs` («Пустая
выдача поиска отдаёт, чем её закрыть»).

Хронология попыток ускорить коннектор и их результат —
[OPTIMIZATION_LOG.md](OPTIMIZATION_LOG.md).

**Одна реплика — один вызов (2026-08-22).** Замер по `tasks_mcp_trace` за 21.08:
запись ужина из трёх приёмов заняла 14 вызовов и 144 секунды стены, из которых
сервер работал 13 — остальное круги «модель → функция → модель». Поэтому дорогие
цепочки схлопнуты в batched-формы:

- `heys_log_meal(meals: [{time, items}, …])` — до 6 приёмов одной датой и одной
  merge-записью дня (меньше окно гонки с открытым приложением);
- `new_product` внутри позиции items — запасной вариант на product_not_found:
  сервер заведёт карточку и запишет позицию тем же вызовом; найденный по query
  продукт всегда сильнее, дубль не создаётся, а заведённые карточки называются
  **первой строкой ответа** — «⚠ Новые карточки (значения от модели, не с
  этикетки) … — проверь состав», до итогов приёма. В хвосте эту строку модель
  теряла и пересказывала куратору обратное (22.08.2026, разбор в
  `OPTIMIZATION_LOG.md`). Тот же лид у `heys_update_meal(add_items)` и
  `heys_save_meal_preset` — они создавать карточки умели, а называть их нет;
- гейт чек-ина за сегодня проверяет сам `heys_log_meal` (`checkin_required`,
  fail-open без профиля, только кураторский режим) — предварительный
  `heys_get_day` ради статуса больше не нужен;
- `heys_update_day(water_add_ml)` — вода вместе с другими показателями дня без
  отдельного `heys_add_water`;
- `heys_get_day` и `heys_get_period` сами говорят, что перед новой записью они
  не нужны: чек-ин и норму сервер проверяет сам, день возвращается в ответе
  записи, а период — про разбор недели;
- норма в **text** ответа несёт поддержание и целевой дефицит (`normDeficitText`
  из `norm.parts`) — «норма с дефицитом и без» больше не стоит отдельного
  `heys_get_profile`;
- **контекст клиента едет попутчиком**: первый `heys_get_day` инстанса и любой
  `heys_get_profile` добавляют в текст 15 частых продуктов за 14 дней с
  `product_id`, наборы и домашние блюда. Отдельного инструмента «дай контекст»
  нет намеренно — он сам был бы кругом. `heys_get_period` этот блок не несёт: у
  него инвариант «один запрос на любой период».

**Инструкции доезжают не целиком (замер 22.08.2026).** Сервер отдаёт 45 316
символов, клиент (Claude Code) обрезает на **2048** — до модели доходит 4,5%
текста, обрыв приходится посреди правила про `day_after`. Всё, что ниже
(«БЫСТРЫЙ ПУТЬ», «СЧЁТЧИК ВЫЗОВОВ», запреты разведочных вызовов), модель не
видит. Описания инструментов при этом доезжают целиком. Разбор в
`OPTIMIZATION_LOG.md`.

**Правило размещения: сначала серверный гейт, потом описание инструмента, потом
текст ответа; инструкция — последнее.** Каналов четыре, и они не равны ни по
надёжности, ни по моменту действия:

| Канал                | Доезжает                          | Когда действует                          |
| -------------------- | --------------------------------- | ---------------------------------------- |
| серверная механика   | всегда                            | до ошибки, предотвращает                 |
| описание инструмента | целиком, **если схема загружена** | до первого вызова                        |
| текст ответа         | целиком                           | после вызова, реактивно                  |
| инструкция           | ~2048 символов                    | до первого вызова, кросс-инструментально |

**Оговорка к описаниям (25.08.2026).** Клиент вправе отложить схемы: в контекст
приходят только имена инструментов, а описания подгружаются по запросу. Пока
схема не подгружена, её описание не существует для модели — значит правило «что
делать, когда инструмента не видно» в описание положить нельзя по построению.
Такие правила остаются в голове инструкции, даже когда по остальным признакам их
место в описании.

Про один инструмент — в его описание. Реактивное («сверь, что получилось») — в
текст ответа. В инструкцию попадает только то, что действует ДО первого вызова и
ни к какому инструменту не привязано: адресация, запрет дневниковой археологии,
transcript, «инструмент не найден — не значит, что его нет», «один вызов на
реплику». Состав головы пересобран 25.08.2026 по телеметрии за 7 дней; разбор и
снимок прежнего набора — в `OPTIMIZATION_LOG.md`. Голова инструкции держится в
`INSTRUCTIONS_HEAD_BUDGET` (1800 — запас к замеренным 2048, потому что это факт
одного клиента, а не контракт); список алиасов при переполнении режется сам и
отсылает к `heys_list_clients`. Держат бюджет три теста в
`__tests__/curator.test.cjs` («Бюджет инструкции»).

Размер обоих каналов пишется в телеметрию `mcp_list`: `tools_bytes` и
`instructions_bytes` рядом. Перенос текста из инструкции в описания растит
первый — а хвост списка схем клиент тоже умеет ронять (18.08.2026 так пропали
`heys_update_day` и `heys_checkin`), поэтому переносить надо сжимая и глядя на
цифру.

Телеметрия пишет `args_hash` (короткий хэш аргументов, значения по-прежнему не
логируются), и дубли в `tasks_mcp_trace` считаются по нему: семь поисков разных
продуктов — не дубль, повтор одного запроса — дубль. Тесты —
`__tests__/tools.test.cjs` («Один вызов на одну реплику»),
`__tests__/mcp-correlate.test.cjs` (дубли по args_hash).

**Активность дня в каждом ответе, быт — одной формой (2026-08-22).** Норма
одинаково выглядит и при пяти часах быта, и при неподвижном дне, поэтому рядом с
ней теперь всегда печатается строка
`Активность: шаги 2000 (+121 ккал), быт 300 мин (+710 ккал) → +831 ккал в расход дня.`;
в пустом дне — «активность за день не отмечена». Разбор приходит и в
`norm.activity`, и когда норму посчитать не на чем.

Быт при этом пишется только полем: `heys_update_day(household_min)` — оно
заменяет прежнее значение — или `household_activities` со временем и названием,
как в приложении. Обе записи кладут список `householdActivities` вместе с
производными `householdMin` / `householdTime`: расчёт читает список и скаляр
рядом с ним игнорирует. `heys_log_training` с бытовым типом или названием
отклоняется (`household_not_training`, обход — `allow_as_training: true`), а
`household_min` поверх быта, уже записанного тренировкой, — с кодом
`household_already_as_training` и списком этих тренировок.

Повод: 21.08.2026 пять часов быта записали двумя household-тренировками, а потом
ещё раз полем — `calculateTDEE` складывает тренировки и `householdMin`
независимо, и норма выросла на 710 ккал. В ответах инструментов этого не было
видно никак, а днём раньше по той же причине день с пятью часами уборки был
назван «почти неподвижным». Тесты — `__tests__/day.test.cjs` и
`__tests__/tools.test.cjs`, блоки «Быт: одна форма записи, один учёт».

**Правка вместо пересоздания.** «Добавь туда ещё» идёт через `heys_update_meal`.
Пересборка приёма через delete + create меняет `meal_id`, теряет оценки
самочувствия и удваивает окно гонки с открытым приложением, поэтому она
оставлена только для случая «приём не нужен вовсе».

**Штуки не пересчитываются в граммы моделью.** `pieces` разрешается в граммы по
порции из карточки продукта. Если веса штуки там нет, инструмент возвращает
`piece_weight_unknown` и просит спросить пользователя — названное значение
дописывается в карточку, и следующий раз проходит без вопроса. Вес пишется
только в свои строки overlay: продукт общей базы правится через модерацию.

**Новый продукт куратора попадает и в общую базу — если он промышленный.**
Заводить одну и ту же пачку творога заново каждому клиенту бессмысленно, поэтому
карточка с брендом или штрихкодом сразу уезжает в общий каталог через
`publish_shared_product_by_curator`. Домашнее блюдо — нет: у него уникальный
состав, дедупликация по отпечатку его не отсечёт, и каталог замусорился бы
чужими рецептами. Решение куратора (`share: true/false`) сильнее этого правила в
обе стороны. Отпечаток (`sha256(имя::нутриенты)`) считается тем же алгоритмом,
что в `apps/web/heys_models_v1.js`, и сверен с живой базой golden-вектором в
тестах: разойтись здесь значит заводить дубли вместо того, чтобы находить
существующий продукт. «Такой продукт уже есть» — нормальный исход, а не ошибка:
личная карточка при этом создана.

**Карточка клиента правится полем, а не блобом.** `heys_update_profile` и
`heys_update_norms` принимают whitelist известных полей с диапазонами из
`apps/web/heys_user_v12.js`; всё остальное игнорируется и возвращается списком
`ignored`. Патч ложится на прочитанное значение и уносит свежий `updatedAt`, а
запись идёт через merge — все три ключа (`heys_profile`, `heys_norms`,
`heys_hr_zones`) входят в `MERGEABLE_KEY_RE` приложения, и сервер сливает их
пофайлово по `updatedAt`. Поэтому правка целевого веса из коннектора не может
снести витамины, флаги онбординга или что угодно ещё, чего модель не видела.
Пульсовые зоны правятся по номеру зоны: названия зон фиксированы, модель меняет
только границы пульса и MET.

**Необратимое требует подтверждения, секрет — предупреждения.** Создание
клиента, смена PIN и сброс подписки проходят только с `confirm: true`: без него
инструмент возвращает вопрос с описанием последствий. PIN и ссылка доступа
возвращаются в ответе — иначе они бесполезны, — но помечены
`contains_secret: true` и сопровождаются напоминанием, что значение осталось в
истории чата. Отказ по заявке, лиду или продукту на модерации невозможен без
причины: её видит человек по ту сторону.

**Поиск знает про два написания.** Запрос сравнивается с названием в исходном
виде и в транслитерации, отдельно по каждому слову: «конфеты тоффифи» находит
«Конфеты Toffifee», а русское слово рядом с латинским не ломает совпадение.
Опечатка прощается внутри слова при совпадающем начале — «сливушки» находят
«Сливочные», но «кагор» не находит «сахар».

**Домашний рецепт другого клиента куратора.** Личные overlay изолированы, общая
база домашнее не берёт. `heys_search_products` без `scope` лениво подгружает
списки остальных клиентов, только если в own+shared нет точного совпадения
(полное покрытие токенов или вхождение фразы). Явный `scope=curator` всегда
смотрит peer; `scope=client` — никогда. Peer-строки помечены `writable: false`:
писать их id в дневник нельзя, сначала `heys_create_product(from_product_id)` —
клон Type B, новый id. Копия — снимок. Общий продукт (Type A) с тем же именем не
клонируется; новое имя (черри ← помидор) работает как раньше. Третий слой
каталога куратора в продукт не вводим.

## Исходники приложения в разговоре

Куратор спрашивает «как в приложении считается белок» и ждёт ответа по тому, как
оно работает сейчас. Отвечать по документации нельзя: она стареет молча, и
проверить её нечем. Поэтому у кураторского режима есть три инструмента только на
чтение — `heys_code_search`, `heys_code_read`, `heys_code_tree`.

| Что                | Как устроено                                                                                                                              |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Источник           | Архив текстовых исходников в приватном бакете `heys-backups`, ключ `source-index/latest.tar.gz` плюс манифест `latest.json`               |
| Кто кладёт         | Сборщик при выкате: `scripts/ci/build-source-index.mjs` в `build-artifact`, заливка — в `deploy-artifact` после проверки прода            |
| Что внутри         | Около 3200 текстовых файлов, 64 МБ, архив ~15 МБ. Собранные бандлы, lock-файлы, карты исходников и бинарники не кладутся                  |
| Как читает функция | `lib/source-index.js`: подпись AWS4 вручную, архив кэшируется в памяти процесса и перечитывается только когда в манифесте сменился коммит |
| Ключи              | `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` из Lockbox `heys-s3`. Нет ключей — инструменты вообще не появляются в списке                  |

**Токена GitHub здесь нет намеренно.** Первый вариант — PAT в промпте облачной
задачи — отклонён: токен возвращается в контекст при каждом запуске и уезжает в
стенограмму, а она в git. Второй — PAT в Lockbox поверх GitHub API — отклонён по
делу: их индекс кода не берёт файлы больше 384 КБ, то есть ровно
`heys_day_bundle_v1.js` (827 КБ), `heys_storage_supabase_v1.js` (824 КБ),
`heys_fingers_bundle_v1.js` (1,2 МБ). Доступ был бы, а поиск в главных файлах —
вслепую.

**Почему в выдаче есть вид файла.** Первая же проверка на живом срезе показала,
чем это кончается без него: поиск по `proteinPct` первыми отдал фикстуры —
`.github/skills/.../examples/day-calculations.js` и `TESTS/*`. В примере белок
делится на 4, а в боевом `apps/web/heys_day_calculations.js` — на
`HEYS.TEF.ATWATER.protein`, то есть на 3 (NET Atwater, TEF уже внутри). Ответ по
фикстуре выглядел бы подтверждённым кодом и был бы неверным. Поэтому каждая
находка помечена как код, тест, пример или документация, боевые пути идут выше,
а правило «отвечать по коду, а не по фикстуре» лежит в инструкциях сервера.

**Границы.** Срез отражает выложенное состояние `main`, а не рабочее дерево
ноутбука; отметка коммита показывается в каждом ответе. Поиск по коду —
единственная тяжёлая операция функции: полный проход по срезу занимает около 0,5
с при пике памяти ~225 МБ, поэтому функции выдано 512 МБ.

## Устойчивость поиска продуктов

Инцидент 2026-08-01: поиск «миндаль» у клиента вернул пусто, хотя продукт был в
её списке и даже в сохранённом наборе. Повторный запрос отработал штатно.

Причина оказалась не в поиске. Личные продукты почти все — Type A: ссылка на
строку общей базы плюс правки клиента. Загрузка `shared_products` сбойнула,
ошибка не проверялась, такие строки молча выпали из каталога — от списка
осталось около 2%. Инструмент честно ответил «не нашлось», а следующий шаг по
инструкции — завести продукт по фото, то есть создать дубликат существующего.

Что сделано, по слоям:

- **Ошибки больше не проглатываются.** Сбой общей базы и «успешный ответ, но
  пусто при наличии связанных продуктов» — оба дают явную ошибку с текстом,
  который прямо запрещает модели заводить дубликат.
- **Кеш справочника на инстанс** (`lib/shared-catalog.js`, TTL 10 минут).
  Справочник глобальный и публичный, персональных данных в нём нет — кеш не
  может протечь между клиентами. Личный overlay не кешируется никогда. Побочный
  эффект: минус ~2 секунды с каждого вызова, где нужен каталог.
- **Работа на прошлом снимке.** Если сеть не ответила, а снимок свежее часа —
  отдаётся он. Пустой ответ рабочий снимок не затирает.
- **Повторы для читающих запросов** (`get_*`, `batch_get_*`, все REST-чтения):
  две попытки с задержкой. Записи не повторяются никогда — повтор merge мог бы
  задвоить приём. `verify_client_pin_v3` тоже исключён: он считает попытки
  входа, и повтор сжигал бы лимит клиента. 429 не повторяется — лимит снимается
  временем, а не настойчивостью.
- **Контроль полноты справочника**: если выборка упёрлась в лимит, это видно в
  логе, а не выглядит как «продукта нет». На 2026-08-01 в базе 425 строк при
  лимите 5000 — запас есть.

## Словоформы в поиске

Русское слово меняет хвост, поэтому сравнение слов идёт от точного к вольному:
префикс в обе стороны («сыра» → «Сыр»), затем одна основа, и лишь потом
опечатка. Одна основа — это дешёвый стемминг без словаря: длинным словам
прощается окончание до трёх букв, коротким — одна. Отсюда «яйца» находит «Яйцо
куриное», «сыра твердого» — «Сыр твёрдый классический», а «вода» не сливается с
«водкой» и «мясо» с «маслом».

Подстрока засчитывается только с границы слова: иначе «сок» вытаскивал
«Сахар-песок». Совпадение внутри перечисления при этом сохраняется — «миндаль»
по-прежнему находит «Орехи микс (миндаль,кешью,фундук)».

  `heys_get_period`, `heys_get_profile` и одну обратимую запись на реальном
  клиенте. Административные инструменты (PIN, подписки, модерация) в проде ещё
  ни разу не вызывались.

## Телеметрия вызовов

На каждый вызов инструмента функция печатает в stdout одну строку чистого JSON и
**await-записывает** ту же строку в Postgres (`mcp_call_events`) через RPC
`insert_mcp_call_event` (таймаут ≤300 мс, вне `upstream_*` счётчиков):

```json
{
  "t": "mcp_call",
  "ts": "…",
  "tool": "heys_log_meal",
  "session_id": "a1b2c3d4e5f6",
  "seq": 3,
  "duration_ms": 812,
  "upstream_calls": 2,
  "upstream_ms": 540,
  "status": "ok",
  "error_code": null,
  "resp_bytes": 1840,
  "arg_count": 4,
  "cold_start": false,
  "fn_version": "…",
  "role": "curator"
}
```

Фильтр в Cloud Logging — для консоли и офлайн `mcp-correlate.mjs`. Trace и
агрегаты читают **Postgres** (`tasks_mcp_trace` → `list_mcp_call_events`,
суточный `mcp_telemetry` → `mcp_call_daily`).

Как проверить за полминуты — в [TIMING_LOG.md](TIMING_LOG.md), раздел «Проверка
за 30 секунд».

Состав строки задан белым списком `RECORD_FIELDS` в
[lib/telemetry.js](lib/telemetry.js). Аргументы, тела ответов, тексты
исключений, имена и идентификаторы людей туда не попадают физически: поле,
которого нет в списке, отбрасывается, даже если его передали. `error_code` —
машинный код, потому что в текст исключения утекают значения аргументов
(«продукт "творог 5%" не найден»).

`session_id` — псевдоним подключения: stateless-транспорт своего
`Mcp-Session-Id` не ведёт, поэтому берётся необратимый срез хэша от токена
вместе с id инстанса. У разных подключений он разный, внутри одного стабилен,
при перезапуске инстанса меняется. На редком трафике (`concurrency: 1`) почти
каждый вызов — новый инстанс, поэтому `seq` почти всегда 1 и диапазон внутри
сессии пустой. Связка «реплика ↔ вызовы» — `node scripts/mcp-correlate.mjs` по
окну времени вокруг метки в стенограмме, не по паре (`session_id`, `seq`).
Подробности — [MCP_TELEMETRY_ROADMAP.md](MCP_TELEMETRY_ROADMAP.md), вопрос 4.

Агрегация — суточной задачей `mcp_telemetry` в `heys-maintenance`
([mcp-telemetry.js](../heys-maintenance/mcp-telemetry.js)), отчёт —
`node scripts/mcp-stats.mjs --days 7`. Подробности и retention — в
[docs/reference/systems/BACKGROUND_JOBS.md](../../docs/reference/systems/BACKGROUND_JOBS.md).

`MCP_LOG_GROUP_ID` у `heys-maintenance` задаётся при деплое: по умолчанию это
folder default `e23ndggvq798r3v3eepq`, куда heys-mcp и так пишет stdout. Без
переменной задача пропускает проход (`skipped: no_log_group`). Retention этой
группы не укорачивать — по ней разбирают 429/503 и dead-man. Отдельная группа на
14 суток — следующий шаг, когда на SA будут `logging.writer`/`logging.reader`.

## Что ещё можно отдать коннектору

Разбор от 2026-08-02: чего не хватает, чтобы куратор вёл клиентов из чата, а не
из веб-приложения. **Authority: рекомендация агента; пользователь поручил
реализацию P0 и ядра P1, остальное решением не является.**

Расширение дешёвое не случайно: кураторский слой уже умеет читать и писать любой
KV-ключ клиента (`getKVByCurator` / `getKVManyByCurator` /
`mergeSaveKVByCurator` + write-context), а в `CURATOR_ONLY_FUNCTIONS`
(`yandex-cloud-functions/heys-api-rpc/index.js`) уже лежат готовые RPC на
клиентов, PIN, подписки, триал-очередь, лиды и модерацию каталога. Не хватает
инструментов, а не серверных возможностей.

| Инструмент                                      | Что закрывает                                      | Бэкенд                                | Статус        |
| ----------------------------------------------- | -------------------------------------------------- | ------------------------------------- | ------------- |
| `heys_list_inbox`                               | «кто мне писал» без перебора клиентов              | `/messages/inbox`                     | ✅ сделано    |

напоминает, что секрет осел в переписке.

Про фото (сделано 2026-08-02): отдельный эндпоинт списка не понадобился — пути
вложений приходят прямо в `heys_list_messages` (`attachments[].path`), а
`POST /photos/read` отдаёт файл куратору, сам проверяя, что путь принадлежит
переписке с его клиентом. Картинка уходит в ответ MCP как image-контент, и
модель видит именно изображение. Размер не мешает: приложение сжимает снимок при
отправке до 800 px по длинной стороне и JPEG q=0.7, то есть 60–150 КБ при
серверном потолке в 5 МБ.

Про чек-лист дня: 2026-08-02 в редизайне мессенджера появился маршрут
`GET /messages/day-checklist` — «чего сейчас нет в дне клиента» (приём, вес,
вода) с проверкой владения клиентом, как в `/thread`. Правило общее с
`heys-cron-reminders` и живёт в `shared/day-checklist-rules.js`. Инструмент
коннектора поверх него не заведён намеренно: на 2026-08-02 маршрут не закоммичен
и не задеплоен, а без записи в `api-gateway-spec.yaml` шлюз отдаёт 404. Заводить
— после того, как маршрут уедет в прод; признак готовности — зелёный post-deploy
smoke «Messenger day-checklist route» в
`.github/workflows/cloud-functions-deploy.yml` (ждёт 401 без авторизации и 204
на preflight): если он проходит, маршрут в шлюзе живой. Частично то же видно уже
сейчас: `heys_get_period` показывает пустые дни и отсутствие веса и воды.

Решения «не делать», принятые в том же разборе:

- **Никакого generic `heys_set_kv`.** Один инструмент «пиши любой ключ любым
  значением» закрыл бы всю таблицу разом — и обошёл бы все серверные проверки,
  дав модели прямой путь к тому классу порчи данных, против которого в
  приложении построена многослойная защита.
- **Не писать в планирование** (`heys_planning_*`): там replace без tombstones,
  и параллельная правка из приложения теряет данные. Чтение безопасно.
- **Не писать в fingers/mobility**: их валидаторы работают fail-closed внутри
  приложения, запись мимо них ломает безопасность протоколов.
- **Не плодить инструмент на ключ.** Чем шире поверхность, тем хуже модель
  выбирает инструмент и тем выше шанс записи не туда — главный риск этого
  режима. Группировать по смыслу: одно `heys_update_profile` с полями вместо
  трёх инструментов, один `heys_trial_queue` с `action` вместо трёх, один
  `heys_moderate_products` вместо «список» + «решение».

## Ревизия стенограммы перед планёркой

### Checkpoint содержательного обмена

`tasks_checkpoint` закрывает обмен одним последним пишущим вызовом: требует
полный `transcript_block` с обеими репликами и при наличии устойчивого вывода
добавляет `journal_block` в месячный журнал. Оба блока валидируются до первой
записи, поэтому ошибка формата журнала не оставляет половину checkpoint; сетевой
сбой между двумя KV-записями всё ещё возможен, и ответ возвращает их ревизии
раздельно. Факты о мире по-прежнему сначала записываются через `tasks_learn`.

### Запись в дневник без провала в стенограмме

Когда к кураторскому коннектору подключён задачник, у каждого пишущего
`heys_*`-инструмента обязателен аргумент `transcript`: дословная реплика
куратора. Без него запись отклоняется **до** изменения дневника. После успешной
записи коннектор сам добавляет в стенограмму эту реплику и подтверждённый
результат инструмента. Если отдельно не сохранилась стенограмма, дневник уже
остаётся внесённым, ответ явно просит вызвать `tasks_checkpoint` вручную и не
предлагает повторять запись — чтобы не задвоить еду или другое действие.

Повестка планёрки собрана только из заведённого. Всё, что за день обсудили и не
завели задачей, напоминанием, идеей или пунктом планёрки, в неё не попадёт и
потеряется молча. Поэтому `tasks_standup` первым блоком отдаёт ревизию — и она
идёт до повестки, а не после.

Читается **не весь день, а несверенный хвост.** Отметка о сверке живёт в самом
файле стенограммы, а не в памяти прохода:

```
## 15:00

**Сверено с доской** · 2026-08-03 15:00 · проверил хвосты — потолок и глазок завёл задачами
```

Заголовок отметки — время, иначе она не прошла бы проверку формата стенограммы.
Хвостом считается всё после **последней** такой строки; отметок нет — читается
файл целиком. Окно — семь дней: работа до двух ночи ложится во вчерашний файл
(сутки задачника кончаются в 3 утра, см. `taskDay`), а планёрку могли и
пропустить. Дни без несверенного хвоста в блок не попадают.

Аргумент `reviewed` дописывает отметку в конец каждого файла, чей хвост сверяли,
и кладёт туда короткий итог. Атомарности по группе файлов нет: если запись
упадёт на втором файле, его хвост просто придёт на следующей планёрке ещё раз —
лишнее чтение, а не потеря.

**Кандидаты на потерю** — подсказка кода, а не результат сверки. Из хвоста
вынимаются суммы, которых нет в `money/`, и вопросы, которым не нашлось строки
`открыто:`. Код не знает, была ли названная сумма тратой или ценой из разведки
рынка, поэтому формулировки оставляют место ошибке. Люди и время считаются, но в
текст не идут: на живых стенограммах 1–3 августа они дали ноль попаданий из
одиннадцати — имена продуктов и таймстампы логов. Подсказка, где всё ложное,
приучает пролистывать блок мимо глаз.

Само сравнение делает модель. Код приносит материал и не даёт молча пропустить
шаг — отличить «уже завели» от «обсудили и забыли» он не умеет.

## Память о мире: факты, а не только предпочтения

**Как было.** `docs/preferences.md` хранил только то, как владелец _решает_
(предпочтение, порог, решение, наблюдение) и возвращался в каждый
`tasks_context` целиком. Фактам о мире — марка машины, площадь склада, кто есть
кто среди людей с одинаковыми именами — места не было вовсе. Они оседали в
`journal/` задним числом или не оседали никак: 04.08 марку машины спросили
четыре раза за день, а записалась она только в 12:50, после четвёртого раза.

**Что изменилось.**

_Вид записи `факт`._ Тот же файл, та же доставка — ничего нового не заводилось.
Отдельная папка (`areas/`, `docs/reference/`) рассматривалась и отвергнута:
подпапки не синхронизируются (`heys_sync.mjs:collectFiles` — плоский обход), а
`keyForPath`/`pathForKey` необратимо схлопывают `/` в `_`. Пятое место хранения
без детектора противоречий сделало бы хуже: даты отпуска на 04.08 лежали в
четырёх файлах, планёрка нашла расхождение 03.08 — за сутки починилось одно
место из четырёх.

_Замена вместо запрета._ Раньше повтор получал «Второй раз не пишу» — продал
машину, и новую марку записать нечем. Теперь есть `replaces`: старая строка не
стирается, на ней появляется отметка «устарело» с датой и новым значением.
Отдельным аргументом, а не побочным эффектом обычной записи, — иначе опечатка
перетёрла бы верный факт. Наблюдением слово владельца не отменяется даже через
`replaces`: расхождение выносится вопросом на планёрку.

_Протухание разведено по видам._ Обычная запись старше 30 дней и ни разу не
пригодившаяся выносится «вычеркнуть». Факт — «проверить», и возраст считается от
последнего касания (запись, подтверждение, попадание в разбор), а не от
создания. Причина: «площадь склада» может не всплывать месяцами и мусором не
является, но устаревший факт опаснее отсутствующего, поэтому совсем выключать
проверку нельзя.

_Подошедшая память печатается в текст ответа._ `tasks_context` отдаёт клиенту
только `result.text` (`lib/mcp.js:toolContent`), а записи уходили исключительно
в `structuredContent`. На «какая у меня машина» задач по словам не находится, и
инструмент честно отвечал «в задачнике ничего не нашлось» — ровно в том случае,
ради которого факты и заводились, при том что ответ лежал этажом ниже в том же
ответе. Теперь подошедшие по словам записи идут блоком «Из памяти». Ревью
2026-08-04 назвало это самым опасным местом реализации.

_Синонимы._ `aliases` («тачка, авто» к записи про машину) участвуют в подборе
наравне с текстом записи и наследуются при замене через `replaces` — иначе
«продал Дастер, купил Ларгус» унесло бы синонимы вместе со старой строкой, и
новый факт перестал бы подниматься на фразе «сколько ехать на тачке». Короткие
формы сверяются по общему префиксу (`shortFormsMatch`, ≥3 символа).

_Подтверждение факта._ Тот же факт, названный тем же значением второй раз, — не
дубль, а подтверждение: дата касания двигается, и на проверку он выйдет не
скоро. Без этого цикл не закрывался — планёрка спрашивала «это ещё так?», ответ
«да» записать было нечем, и тот же факт выносился снова. Подтверждением
считается совпадение значения дословно: «Hyundai Солярис» против «Hyundai
Solaris» — это опечатка или правка, и уходит в обычный отказ с путём `replaces`.

**Чего это не делает.** Принудить модель свериться с памятью кодом нельзя —
вопрос звучит в чате, коннектор его не видит. Поэтому сделано то, что работает:
`tasks_decision` отказывает, если ответ уже записан фактом, и показывает его;
`tasks_resolve` принимает аргументы `fact` и `fact_replaces` и кладёт ответ в
память, а не только дочерней строкой под задачу (оттуда он уезжал в архив вместе
с задачей). Инцидент 2026-08-04 показал, что правило «сверься с памятью» само по
себе не срабатывает — отказ инструмента надёжнее приписки в промпте.

**Куда развивать.** Детектор противоречий между двумя записями одного факта:
`findDivergences` проверяет структуру (слот без задачи, ссылка в никуда), но
«13-19» против «16-19» не увидит никогда. Второе — вид записи необязателен, и
факт, записанный без `kind`, молча получает срок предпочтения (месяц на
вычёркивание вместо полугода на проверку); сейчас это удерживается только
описанием аргумента.

## Потолок чтения: квота на растущие папки

**Как было.** `readAll` брал 60 файлов в порядке `rankPaths` — по смыслу, внутри
датированных папок ближе к сегодня. Проблема в том, что `days/` пополняется
каждый день и стоит выше журнала, денег и архива. Симуляция роста показала:
около **19 августа** `CLAUDE.md` (ранг 7) и `README.md` выпали бы из чтения
молча, вместе с картой районов и временем в пути, которые в них лежат. Ошибки бы
не было — просто ответы стали бы хуже.

**Что изменилось.** `selectPaths` даёт каждой датированной папке квоту
(`DATED_QUOTA = 12`): две недели дней либо год месячных файлов журнала и денег.
Лишнее не выбрасывается, а уходит в хвост — если после отбора место осталось,
тринадцатый день прочитается, но после справочников, а не вместо них. Потолок не
поднимали: каждый файл прохода оплачивается в каждом разборе фразы.

Проверено симуляцией на 60 дней вперёд: инструкция, справочник и память остаются
в чтении.

**Куда развивать.** Квота одинаковая для всех датированных папок; возможно,
`days/` заслуживает больше, чем `archive/`. И `tasks_search` обещает «искали
везде», но из 26 разовых отчётов реально видит часть — остальное срезает тот же
потолок, причём отбор среди них алфавитный.

## Ограничения

- Транспорт stateless: SSE и `Mcp-Session-Id` не поддерживаются (для
  инструментов дневника поток сервер→клиент не нужен).
- `verify_client_pin_v3` ограничивает попытки по IP, а все запросы приходят с
  egress-адреса функции. При частых неудачных входах возможен временный лимит.
- Продукт из общей базы вносится в приём полным нутриентным слепком, но **не**
  клонируется в личный overlay: запись в общий список продуктов оставлена
  приложению, чтобы не конфликтовать с его debounce-синхронизацией.
- В клиентском режиме продукт создаётся только в личном списке: публикация в
  общую базу идёт через очередь модерации (`create_pending_product_by_session` →
  куратор). У куратора прав больше — см. ниже.
- Калорийность нового продукта считается по NET Atwater, а не переносится с
  упаковки — так же, как это делает приложение. Расхождение с этикеткой
  ожидаемо.
- Профиль и нормы правятся только по whitelist полей: имя клиента, витамины,
  флаги онбординга и всё, чего нет в `lib/profile.js`, коннектору недоступны.
  Имя живёт в таблице `clients` и меняется отдельным кураторским путём — правка
  его копии в профиле рассинхронизировала бы две записи об одном человеке.
- `heys_get_period` ограничен 31 днём и не возвращает позиции приёмов: за
  составом конкретного дня идут в `heys_get_day`. Более длинный диапазон
  отклоняется, а не режется молча.
- Наборы (`heys_meal_presets_v1`) пишутся целым блобом через
  `upsert_client_kv_by_session` — этот ключ не входит в merge-контур приложения
  (`MERGEABLE_KEY_RE`), серверного merge для него нет. Значит действует
  last-writer-wins: правка набора из приложения и из коннектора в одну и ту же
  секунду может потерять одну из них. Наборы меняются редко, поэтому окно
  считаем приемлемым; инструменты перечитывают список непосредственно перед
  записью. Внешнее изменение доезжает в открытое приложение за ~12 секунд
  (foreground hot-sync), а открытая модалка наборов обновится только после
  переоткрытия — она не подписана на события синхронизации.
- `sleepHours` в блобе дня — производное поле, а не то, что вводит пользователь:
  контракт приложения — ночной интервал плюс дневной досып `daySleepMinutes`,
  округлённые до 0.1 ч (`apps/web/heys_steps_v1.js`). `heys_update_day`
  пересчитывает его сам, когда пришло `sleep_start` или `sleep_end` и в дне есть
  оба времени. Регресс 2026-08-02: до этого коннектор писал только времена, и
  дневник с обзором за период показывали часы от прежнего интервала (запись
  06:30–12:00 оставляла 5.8 ч от 04:35–10:25). Тест — `__tests__/day.test.cjs`,
  «updateDayFields пересчитывает sleepHours».
- Производные поля дня пересчитываются в `touch()` — единой точке фиксации
  мутации: часы сна, `moodAvg/wellbeingAvg/stressAvg` и `dayScore`. Инструменты
  пишут только источники (`sleepStart/sleepEnd`, `moodMorning` и соседи, оценка
  приёма), потому что входы средних меняются в четырёх местах и точечный
  пересчёт закрывал бы одно из них. Формула повторяет
  `apps/web/heys_day_calculations.js:155`; `dayScore` не трогается при
  `dayScoreManual`.

## Запись куратора × утренний чек-ин — аудит 2026-08-02

Проверено по коду; каждый пункт — факт с опорой, а не намерение. Решений по
исправлению здесь нет, кроме двух уже применённых правок.

**Кто выигрывает при расхождении.** Общего правила нет, оно разное по полям.
Сервер вызывает merge только при конфликте: если пишущая сторона видела
актуальную облачную версию, день перезаписывается её значением целиком
(`heys-api-rpc/index.js:3010`). В merge-ветке
`sleepStart/sleepEnd/sleepQuality/ sleepNote/mood*Morning` разрешаются через
`firstSubjectiveValue` (`lib/heys_sync_merge_v1.cjs:704`) — побеждает первое
непустое значение пишущего, независимо от времени. Вес защищён штампом
`weightUpdatedAt`, который коннектор ставит (`lib/day.js:343`).

**Правка куратора откатывается работой клиента — механизм подтверждён.** У полей
сна и утренних оценок нет ни tombstone, ни per-field timestamp, ни признака
автора. Пока клиент редактирует день, входящий облачный снимок не применяется
(block-window, `apps/web/heys_storage_supabase_v1.js:8772`), в LS остаётся
старое непустое значение, и следующая же выгрузка клиента детерминированно
возвращает его. `hasSubjectiveFieldDrop` тут не помогает: он ловит исчезновение
поля, а не подмену на другое непустое (`lib/heys_sync_merge_v1.cjs:449`).

**Авторства не было — добавлено.** `_writerCid` — это id клиента-владельца
строки, а не актора: в кураторском режиме коннектор штампует блоб id самого
клиента (`lib/curator.js:360`), иначе запись не прошла бы cross-client guard.
Теперь в кураторском режиме `heys_update_day` дополнительно проставляет
`_curatorEdits: { <поле>: { at, value } }` по полям чек-ина, `summarizeDay`
отдаёт список `curator_authored`, а дневник рисует у таких полей пометку «✎
куратор». Контракт метки — ниже.

**Чек-ин закрывался данными, а не действием — исправлено.** Предикаты
`hasCheckinWeight/hasSleepTime/hasSleepQuality/hasMorningMood`
(`apps/web/heys_morning_checkin_v1.js`) смотрели только на наличие значения, и
запись куратора закрывала клиенту три шага из пяти. Теперь поле с действующей
меткой шаг не закрывает, а стрик дисциплины в cascade-карточке и ретро-ачивка
`first_checkin` считают только то, что ввёл клиент. XP `checkin_complete`
по-прежнему привязан к событию UI-флоу и правкой не затронут.

### Контракт метки авторства

- Метка хранит значение, которое вписал куратор, и потому действует ровно до тех
  пор, пока значение то самое. Отдельный tombstone не нужен и невозможен: merge
  объединяет этот словарь union'ом по свежести, поэтому удалённый ключ вернулся
  бы со второй стороны.
- Подтверждение клиента гасит метку явно (`HEYS.models.clearCuratorMarks` ставит
  `{ at, value: null }`) — совпадение значений не спасает, оценки по шкале 1–10
  у клиента и куратора сплошь и рядом одинаковые.
- Поле обязано быть в трёх местах, иначе исчезнет: union в `mergeDayData` (база
  merge — `remote`), перечисление в `ensureDay` (`apps/web/heys_models_v1.js`
  собирает день по whitelist, без спреда) и штамповка в коннекторе. Все три
  копии `heys_sync_merge_v1` — web, api-rpc, api-rest — обязаны совпадать
  побайтово.
- Тесты: `apps/web/__tests__/curator-authorship.test.js` (9), в том числе на
  переживание merge и на то, что погашенная метка не воскресает.

**`mood/wellbeing/stress` из коннектора не доезжали — исправлено.**
`heys_update_day` писал их в `moodAvg/wellbeingAvg/stressAvg`, но в приложении
это производные средние по утренним оценкам, приёмам и тренировкам:
`useRatingAveragesEffect` пересчитывает их из
`moodMorning/wellbeingMorning/stressMorning` и перезаписывает. Этих ключей нет
ни в `SUBJECTIVE_DAY_FIELDS`, ни в mutation-группах серверного merge, так что в
merge-ветке они молча заменялись облачными. Теперь коннектор пишет в источник
(`moodMorning` и соседи), а средние и `dayScore` пересчитывает сам — следствием
куратор закрывает клиенту и шаг `morning_mood` тоже.

**`steps` из коннектора проигрывали облаку — исправлено.** Merge шагов решается
по `stepsUpdatedAt` (`lib/heys_sync_merge_v1.cjs:664`); приложение штамп ставит
(`apps/web/heys_day_steps_ui.js:163`), коннектор — нет, поэтому при конфликте
`localStepsTs = 0` проигрывал непустому облачному. Теперь штамп ставится так же,
как для веса.

**Исправлено этой же задачей.** `steps_set` в кураторском фиде читал
`oldDay.stepsCount`, которого в блобе дня не существует (поле называется
`steps`), — правка шагов не попадала в `client_data_changelog` вовсе
(`heys-api-rpc/curator-action-diff.js:352`, тест обновлён). Плюс `sleep_set` там
же предпочитает `day.sleepHours`, поэтому до фикса протухшего поля он показывал
часы от прежнего интервала.

**Документация.** Файла `docs/heys-mcp-connector.md` в репозитории нет;
last-writer-wins задокументирован выше только для наборов. Для дня
`lib/heys-api.js:246` обещает, что merge разрешает конфликт, — в
`noConflict`-ветке merge не вызывается вообще, так что обещание сильнее кода.
