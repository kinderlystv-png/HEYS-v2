# heys-mcp — remote MCP connector для HEYS

Даёт ассистенту (claude.ai, Cowork, Claude Desktop, Claude Code) возможность
вести дневник HEYS за пользователя: «выпил кофе в студии» → приём пищи
появляется в PWA.

Работает с любого устройства, включая телефон: запрос идёт из облака Anthropic в
`https://api.heyslab.ru/mcp`, компьютер пользователя не участвует.

## Что внутри

| Файл                   | Ответственность                                                  |
| ---------------------- | ---------------------------------------------------------------- |
| `index.js`             | HTTP-роутинг функции, заголовки безопасности, склейка слоёв      |
| `lib/mcp.js`           | JSON-RPC и методы MCP (`initialize`, `tools/list`, `tools/call`) |
| `lib/oauth.js`         | OAuth 2.1 + DCR + PKCE, страница входа по телефону и PIN         |
| `lib/crypto-tokens.js` | Подпись HS256, шифрование AES-GCM, проверка PKCE                 |
| `lib/tools.js`         | Инструменты: день, продукты, наборы, приёмы, вода, тренировки    |
| `lib/admin.js`         | Телефон, PIN и его хеш, предупреждение о секрете в ответе        |
| `lib/day.js`           | Чистые мутации дневного блоба `heys_dayv2_*` и сводки периода    |
| `lib/profile.js`       | Whitelist профиля, норм и пульсовых зон: патч полем, не блобом   |
| `lib/products.js`      | Слияние личного overlay с общей базой + поиск                    |
| `lib/curator.js`       | Кураторский режим: адресация клиента, мессенджер, входящие       |
| `lib/heys-api.js`      | HTTPS-клиент к собственному `/rpc` и `/rest`                     |

## Два решения, которые определяют всё остальное

**1. Функция не ходит в БД.** Запись дня идёт через
`merge_save_client_kv_by_session` в `heys-api-rpc` — тем же путём, что и PWA.
Там живут row-lock, cross-client guard, валидация контракта, `data_loss_audit` и
алерты. Прямой доступ к `client_kv_store` означал бы второй путь записи, который
неизбежно разойдётся с первым.

**2. Состояние OAuth не хранится в БД.** `client_id`, authorization code, access
и refresh — подписанные HS256-структуры. Access-токен несёт внутри зашифрованный
client-session HEYS, поэтому **отзыв доступа = отзыв сессии пользователя**:
выход из аккаунта в приложении мгновенно обрывает доступ ассистента. Отдельного
стора отозванных токенов нет намеренно.

Следствие, которое надо знать: authorization code внутри своих 5 минут
технически переиспользуем (stateless). Атака этим не эксплуатируется — обмен
требует PKCE `code_verifier`, который есть только у легитимного клиента.

## Кураторский режим

Один коннектор — все клиенты куратора. На странице входа секция «Я куратор —
вход по email»: email + пароль (+ код 2FA, если включена). После входа:

- появляются собственные инструменты куратора, а каждый инструмент дневника
  получает параметр `client` (имя или client_id):

  | Инструмент                 | Назначение                                                      |
  | -------------------------- | --------------------------------------------------------------- |
  | `heys_list_clients`        | Кого ведёт куратор: client_id, имя, статус подписки             |
  | `heys_list_inbox`          | Кто написал и сколько сообщений ждёт ответа — по всем клиентам  |
  | `heys_list_messages`       | Переписка с клиентом, включая расшифровки голосовых             |
  | `heys_mark_message_done`   | Отметка «просьба внесена» — защита от повторного внесения       |
  | `heys_reply_message`       | Ответ клиенту в мессенджере приложения                          |
  | `heys_moderate_products`   | Очередь общей базы: список, одобрение, отклонение с причиной    |
  | `heys_create_client`       | Новый клиент: имя, телефон, PIN                                 |
  | `heys_client_access`       | Ссылка входа и перевыпуск PIN                                   |
  | `heys_manage_subscription` | Продление и сброс подписки                                      |
  | `heys_trial_queue`         | Очередь на триал: список, активация, отказ                      |
  | `heys_leads`               | Заявки с лендинга: список и смена статуса                       |
  | `heys_get_client_health`   | Сессии и входы клиента — на жалобы «не заходит», «не синкается» |

  `heys_list_clients`, `heys_list_inbox`, `heys_moderate_products`,
  `heys_create_client` и `heys_leads` работают без адресата: они и нужны затем,
  чтобы его выбрать или относятся ко всем клиентам сразу;

- при нескольких клиентах параметр обязателен: без него инструмент возвращает
  список клиентов и просит уточнить — записи «по догадке» исключены на уровне
  кода, а не только инструкций;
- каждый ответ начинается с имени клиента: `[Александра] Записал…`;
- данные ходят кураторскими путями (`merge_save_client_kv_by_curator`,
  `batch_upsert_client_kv_by_curator`, REST с Bearer JWT) — ownership проверяет
  SQL, цель записи дополнительно фиксируется write-context'ом на клиента;
- кураторский JWT живёт 24 часа, но коннектор не протухает: на refresh функция
  перевыпускает JWT сама (сырой `JWT_SECRET` уже приходит из Lockbox-overlay,
  формат claims повторяет `createJwt` из heys-api-auth);
- логика инструментов общая с клиентским режимом: `createTools` не менялся,
  кураторский слой — адаптер API на клиента (`lib/curator.js`).

Отзыв кураторского доступа: отключить коннектор в Claude (жёсткий отзыв на
сервере невозможен — кураторские JWT stateless, как и в веб-приложении).

### Три решения, которые видно в поведении

**Правка вместо пересоздания.** «Добавь туда ещё» идёт через `heys_update_meal`.
Пересборка приёма через delete + create меняет `meal_id`, теряет оценки
самочувствия и удваивает окно гонки с открытым приложением, поэтому она
оставлена только для случая «приём не нужен вовсе».

**Штуки не пересчитываются в граммы моделью.** `pieces` разрешается в граммы по
порции из карточки продукта. Если веса штуки там нет, инструмент возвращает
`piece_weight_unknown` и просит спросить пользователя — названное значение
дописывается в карточку, и следующий раз проходит без вопроса. Вес пишется
только в свои строки overlay: продукт общей базы правится через модерацию.

**Карточка клиента правится полем, а не блобом.** `heys_update_profile` и
`heys_update_norms` принимают whitelist известных полей с диапазонами из
`apps/web/heys_user_v12.js`; всё остальное игнорируется и возвращается списком
`ignored`. Патч ложится на прочитанное значение и уносит свежий `updatedAt`, а
запись идёт через merge — все три ключа (`heys_profile`, `heys_norms`,
`heys_hr_zones`) входят в `MERGEABLE_KEY_RE` приложения, и сервер сливает их
пофайлово по `updatedAt`. Поэтому правка целевого веса из коннектора не может
снести витамины, флаги онбординга или что угодно ещё, чего модель не видела.
Пульсовые зоны правятся по номеру зоны: названия зон фиксированы, модель меняет
только границы пульса и MET.

**Необратимое требует подтверждения, секрет — предупреждения.** Создание
клиента, смена PIN и сброс подписки проходят только с `confirm: true`: без него
инструмент возвращает вопрос с описанием последствий. PIN и ссылка доступа
возвращаются в ответе — иначе они бесполезны, — но помечены
`contains_secret: true` и сопровождаются напоминанием, что значение осталось в
истории чата. Отказ по заявке, лиду или продукту на модерации невозможен без
причины: её видит человек по ту сторону.

**Поиск знает про два написания.** Запрос сравнивается с названием в исходном
виде и в транслитерации, отдельно по каждому слову: «конфеты тоффифи» находит
«Конфеты Toffifee», а русское слово рядом с латинским не ломает совпадение.
Опечатка прощается внутри слова при совпадающем начале — «сливушки» находят
«Сливочные», но «кагор» не находит «сахар».

## Устойчивость поиска продуктов

Инцидент 2026-08-01: поиск «миндаль» у клиента вернул пусто, хотя продукт был в
её списке и даже в сохранённом наборе. Повторный запрос отработал штатно.

Причина оказалась не в поиске. Личные продукты почти все — Type A: ссылка на
строку общей базы плюс правки клиента. Загрузка `shared_products` сбойнула,
ошибка не проверялась, такие строки молча выпали из каталога — от списка
осталось около 2%. Инструмент честно ответил «не нашлось», а следующий шаг по
инструкции — завести продукт по фото, то есть создать дубликат существующего.

Что сделано, по слоям:

- **Ошибки больше не проглатываются.** Сбой общей базы и «успешный ответ, но
  пусто при наличии связанных продуктов» — оба дают явную ошибку с текстом,
  который прямо запрещает модели заводить дубликат.
- **Кеш справочника на инстанс** (`lib/shared-catalog.js`, TTL 10 минут).
  Справочник глобальный и публичный, персональных данных в нём нет — кеш не
  может протечь между клиентами. Личный overlay не кешируется никогда. Побочный
  эффект: минус ~2 секунды с каждого вызова, где нужен каталог.
- **Работа на прошлом снимке.** Если сеть не ответила, а снимок свежее часа —
  отдаётся он. Пустой ответ рабочий снимок не затирает.
- **Повторы для читающих запросов** (`get_*`, `batch_get_*`, все REST-чтения):
  две попытки с задержкой. Записи не повторяются никогда — повтор merge мог бы
  задвоить приём. `verify_client_pin_v3` тоже исключён: он считает попытки
  входа, и повтор сжигал бы лимит клиента. 429 не повторяется — лимит снимается
  временем, а не настойчивостью.
- **Контроль полноты справочника**: если выборка упёрлась в лимит, это видно в
  логе, а не выглядит как «продукта нет». На 2026-08-01 в базе 425 строк при
  лимите 5000 — запас есть.

## Словоформы в поиске

Русское слово меняет хвост, поэтому сравнение слов идёт от точного к вольному:
префикс в обе стороны («сыра» → «Сыр»), затем одна основа, и лишь потом
опечатка. Одна основа — это дешёвый стемминг без словаря: длинным словам
прощается окончание до трёх букв, коротким — одна. Отсюда «яйца» находит «Яйцо
куриное», «сыра твердого» — «Сыр твёрдый классический», а «вода» не сливается с
«водкой» и «мясо» с «маслом».

Подстрока засчитывается только с границы слова: иначе «сок» вытаскивал
«Сахар-песок». Совпадение внутри перечисления при этом сохраняется — «миндаль»
по-прежнему находит «Орехи микс (миндаль,кешью,фундук)».

## Деплой

Функция не получает PG-креды (`deploy-all.sh` исключает `mcp` из ветки с
`PG_*`/`LOCKBOX_DB_SECRET_ID`): прямой путь записи в `client_kv_store` для неё
физически недоступен. `LOCKBOX_APP_SECRET_ID` она получает, поэтому
`initSecrets()` подтянет `MCP_TOKEN_SECRET` из секрета `heys-app-secrets` при
холодном старте.

```bash
# 1. Секрет подписи. Если не задан — используется JWT_SECRET (ключи разведены
#    через HKDF, пересечения с curator-JWT нет). Отдельный секрет предпочтительнее.
#    ВАЖНО: add-version заменяет payload целиком — сначала выгрузи текущий,
#    добавь к нему ключ и залей полный набор обратно, иначе снесёшь JWT_SECRET,
#    SESSION_SECRET и токены ботов.
yc lockbox payload get --id e6qrvefs3vn66jiamfk4 --format json > /tmp/app-secrets.json
#    → добавить в набор {"key":"MCP_TOKEN_SECRET","text_value":"<openssl rand -hex 32>"}
#    → залить полный payload обратно через `yc lockbox secret add-version`

# 2. Деплой функции
cd yandex-cloud-functions && ./deploy-all.sh heys-mcp

# 3. Узнать id функции и подставить в спеку gateway
yc serverless function get --name heys-mcp --format json | jq -r .id
#    → заменить __HEYS_MCP_FUNCTION_ID__ в блоке из api-gateway-mcp-paths.yaml
#    и вставить этот блок в paths: файла api-gateway-spec.yaml

# 4. Обновить gateway
yc serverless api-gateway update --name <gateway-name> --spec=api-gateway-spec.yaml
```

(чужие поля переживают правку, значение вне диапазона отклоняется, повтор того
же значения записью не считается), правка зон по номеру, агрегаты периода одним
пакетным чтением и подписи имён в кураторском inbox.

Тайминг вызовов и стоимость сценариев записи: [`TIMING_LOG.md`](TIMING_LOG.md).

Отдельно: [`TELEGRAM_MEAL_LOGGING_AUDIT.md`](TELEGRAM_MEAL_LOGGING_AUDIT.md) —
аудит того, можно ли завести запись еды через Telegram-бота и почему без LLM это
покрывает только повторяющиеся сценарии.

## Что ещё можно отдать коннектору

Разбор от 2026-08-02: чего не хватает, чтобы куратор вёл клиентов из чата, а не
из веб-приложения. **Authority: рекомендация агента; пользователь поручил
реализацию P0 и ядра P1, остальное решением не является.**

Расширение дешёвое не случайно: кураторский слой уже умеет читать и писать любой
KV-ключ клиента (`getKVByCurator` / `getKVManyByCurator` /
`mergeSaveKVByCurator` + write-context), а в `CURATOR_ONLY_FUNCTIONS`
(`yandex-cloud-functions/heys-api-rpc/index.js`) уже лежат готовые RPC на
клиентов, PIN, подписки, триал-очередь, лиды и модерацию каталога. Не хватает
инструментов, а не серверных возможностей.

| Инструмент                                      | Что закрывает                                      | Бэкенд                                | Статус        |
| ----------------------------------------------- | -------------------------------------------------- | ------------------------------------- | ------------- |
| `heys_list_inbox`                               | «кто мне писал» без перебора клиентов              | `/messages/inbox`                     | ✅ сделано    |
| `heys_get_period`                               | неделя/месяц одним вызовом                         | пакетное чтение KV                    | ✅ сделано    |
| `heys_get_profile` / `heys_update_profile`      | профиль, который куратор вбивал руками             | `heys_profile` (merge)                | ✅ сделано    |
| `heys_update_norms` / `heys_update_hr_zones`    | нормы рациона и пульсовые зоны                     | `heys_norms`, `heys_hr_zones`         | ✅ сделано    |
| `heys_update_product` / `heys_delete_product`   | правка личного продукта вместо дубликата           | overlay + explicit tombstone          | ✅ сделано    |
| `heys_moderate_products`                        | модерация общей базы из чата                       | RPC модерации + REST очереди          | ✅ сделано    |
| `heys_create_client` / `heys_client_access`     | завести клиента и выдать доступ                    | `create_client_with_pin` и др.        | ✅ сделано ⚠️ |

| `heys_get_client_health`                        | диагностика синка клиента                          | `get_client_observability_by_curator` | ✅ сделано    |

⚠️ PIN и ссылка доступа возвращаются в ответе инструмента и остаются в истории
чата. Это осознанный компромисс: без значения инструмент бесполезен, поэтому
вызов требует подтверждения, ответ помечен `contains_secret: true`, а текст
напоминает, что секрет осел в переписке.

Про фото: `heys-api-photos` умеет только upload/read/delete по конкретному пути,
списка фото клиента нет, а MCP-ответы этого коннектора — текстовые. Поэтому
инструмент «покажи фото» потребовал бы серверного эндпоинта списка и поддержки
image-контента; пока `heys_list_messages` лишь сообщает, что к сообщению
приложено фото или голосовое, и отдаёт расшифровку, если она есть.

Про чек-лист дня: 2026-08-02 в редизайне мессенджера появился маршрут
`GET /messages/day-checklist` — «чего сейчас нет в дне клиента» (приём, вес,
вода) с проверкой владения клиентом, как в `/thread`. Правило общее с
`heys-cron-reminders` и живёт в `shared/day-checklist-rules.js`. Инструмент
коннектора поверх него не заведён намеренно: на 2026-08-02 маршрут не закоммичен
и не задеплоен, а без записи в `api-gateway-spec.yaml` шлюз отдаёт 404. Заводить
— после того, как маршрут уедет в прод; признак готовности — зелёный post-deploy
smoke «Messenger day-checklist route» в
`.github/workflows/cloud-functions-deploy.yml` (ждёт 401 без авторизации и 204
на preflight): если он проходит, маршрут в шлюзе живой. Частично то же видно уже
сейчас: `heys_get_period` показывает пустые дни и отсутствие веса и воды.

Решения «не делать», принятые в том же разборе:

- **Никакого generic `heys_set_kv`.** Один инструмент «пиши любой ключ любым
  значением» закрыл бы всю таблицу разом — и обошёл бы все серверные проверки,
  дав модели прямой путь к тому классу порчи данных, против которого в
  приложении построена многослойная защита.
- **Не писать в планирование** (`heys_planning_*`): там replace без tombstones,
  и параллельная правка из приложения теряет данные. Чтение безопасно.
- **Не писать в fingers/mobility**: их валидаторы работают fail-closed внутри
  приложения, запись мимо них ломает безопасность протоколов.
- **Не плодить инструмент на ключ.** Чем шире поверхность, тем хуже модель
  выбирает инструмент и тем выше шанс записи не туда — главный риск этого
  режима. Группировать по смыслу: одно `heys_update_profile` с полями вместо
  трёх инструментов, один `heys_trial_queue` с `action` вместо трёх, один
  `heys_moderate_products` вместо «список» + «решение».

## Ограничения

- Транспорт stateless: SSE и `Mcp-Session-Id` не поддерживаются (для
  инструментов дневника поток сервер→клиент не нужен).
- `verify_client_pin_v3` ограничивает попытки по IP, а все запросы приходят с
  egress-адреса функции. При частых неудачных входах возможен временный лимит.
- Продукт из общей базы вносится в приём полным нутриентным слепком, но **не**
  клонируется в личный overlay: запись в общий список продуктов оставлена
  приложению, чтобы не конфликтовать с его debounce-синхронизацией.
- Продукт создаётся только в личном списке. Публикация в общую базу идёт через
  очередь модерации (`create_pending_product_by_session` → куратор) и коннектору
  намеренно недоступна.
- Калорийность нового продукта считается по NET Atwater, а не переносится с
  упаковки — так же, как это делает приложение. Расхождение с этикеткой
  ожидаемо.
- Профиль и нормы правятся только по whitelist полей: имя клиента, витамины,
  флаги онбординга и всё, чего нет в `lib/profile.js`, коннектору недоступны.
  Имя живёт в таблице `clients` и меняется отдельным кураторским путём — правка
  его копии в профиле рассинхронизировала бы две записи об одном человеке.
- `heys_get_period` ограничен 31 днём и не возвращает позиции приёмов: за
  составом конкретного дня идут в `heys_get_day`. Более длинный диапазон
  отклоняется, а не режется молча.
- Наборы (`heys_meal_presets_v1`) пишутся целым блобом через
  `upsert_client_kv_by_session` — этот ключ не входит в merge-контур приложения
  (`MERGEABLE_KEY_RE`), серверного merge для него нет. Значит действует
  last-writer-wins: правка набора из приложения и из коннектора в одну и ту же
  секунду может потерять одну из них. Наборы меняются редко, поэтому окно
  считаем приемлемым; инструменты перечитывают список непосредственно перед
  записью. Внешнее изменение доезжает в открытое приложение за ~12 секунд
  (foreground hot-sync), а открытая модалка наборов обновится только после
  переоткрытия — она не подписана на события синхронизации.
