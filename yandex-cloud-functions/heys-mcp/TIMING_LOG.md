# Тайминг записи в HEYS через коннектор

Зачем: видеть, какой сценарий записи чего стоит, и оптимизировать самый дорогой.
Без этого «стало медленнее» остаётся ощущением, а не числом.

## Что именно измеряется

Только машинная работа: от вызова инструмента до ответа. Время на уточнения у
пользователя и на раздумья модели сюда не входит — это другая величина, и мешать
их в одну нельзя.

Две точки замера:

- **Инструмент.** `duration_ms` приходит в `structuredContent` каждого ответа —
  видно прямо в диалоге, без похода в логи.
- **Функция.** Строка `[heys-mcp] tool_timing` в Cloud Logging на каждый вызов:
  `ms` — весь инструмент, `upstream.calls` и `upstream.ms` — обращения к
  `heys-api-rpc`. Разница между ними — собственная логика инструмента. `cold` —
  первый вызов на этом инстансе, `uptime_ms` — возраст процесса,
  `response_bytes` — размер ответа.

Обычно дорожает не логика, а число round-trip'ов: почти каждый инструмент читает
день, каталог продуктов и пишет обратно.

`cold` и `uptime_ms` появились потому, что без них строка неинтерпретируема: та
же запись стоит около секунды на живом инстансе и втрое дороже на поднятом с
нуля. Замер 17.08 (см. журнал) держался только на том, что вызовы шли подряд и
инстанс заведомо был тёплым, — на одиночной строке из лога так не скажешь.

Прочитать за последний час:

```bash
yc logging read --group-name default --since 1h \
  --filter 'json_payload.message contains "tool_timing"' --format json
```

Лог-группа `default` хранит записи **3 суток** (259200 s). Выгрузка «за неделю»
не вернёт ничего: если нужен ряд длиннее, его надо копить самому.

## Ожидаемая стоимость сценариев

Считается по числу обращений к API, а не по секундомеру: округляется медленнее и
не врёт при холодном старте функции.

Счёт ведётся по кураторскому пути — том самом, которым идёт коннектор. Раньше
таблица считала только чтение дня и запись; на деле к каждой записи прицеплены
ещё три вещи, и вместе они стоят больше, чем сама запись.

Постоянный хвост любой записи в дневник:

| Что                                   | Обращений | Примечание                                        |
| ------------------------------------- | --------- | ------------------------------------------------- |
| Входы нормы дня                       | 1         | профиль, БЖУ, зоны и 4 прошлых дня — одним батчем |
| Контекст записи                       | 1         | `issueWriteContext`, кэшируется на инстанс        |
| Стенограмма (`transcript_checkpoint`) | 3         | ревизия до записи, дельта-append, проверка после  |

Стенограмма пишется **после** дневника и до 17.08 стоила 4 обращения: файл
читался ещё и целиком перед записью, хотя дельта-путь перечитывает ревизию сам.
Дубль убран, а оставшееся чтение ревизии стартует параллельно с записью дня.
Проверка после записи оставлена намеренно: уверенность, что стенограмма легла,
дороже сэкономленной четверти секунды.

| Сценарий                 | Инструмент                 | Обращений к API                                      |
| ------------------------ | -------------------------- | ---------------------------------------------------- |
| Вода                     | `heys_add_water`           | 2 + хвост — чтение дня, запись                       |
| Тренировка               | `heys_log_training`        | 2 + хвост — чтение дня, запись                       |
| Дневные показатели       | `heys_update_day`          | 2 + хвост — чтение дня, запись                       |
| Новый приём              | `heys_log_meal`            | 4 + хвост — overlay, общая база, чтение дня, запись  |
| Приём из набора          | `heys_log_meal` с `preset` | 5 + хвост — плюс чтение наборов                      |
| Добавить в готовый приём | `heys_update_meal`         | 4 + хвост — overlay, общая база, чтение дня, запись  |
| Продукт по этикетке      | `heys_create_product`      | 5 — overlay, общая база, tombstones, overlay, запись |
| Штуки с новым весом      | любой из записи еды        | +2 — чтение и запись overlay                         |

Каталог кэшируется на один вызов, поэтому несколько позиций в одном приёме стоят
столько же, сколько одна. Разбивать приём на несколько вызовов — самый дорогой
способ сделать то же самое.

## Журнал

Одна строка на просьбу пользователя. `Вызовов` — сколько раз агент дёрнул
инструменты, включая поиск и чтение дня.

| Дата       | Просьба                         | Сценарий                                      | Вызовов | Σ duration_ms | Заметка                                                                                           |
| ---------- | ------------------------------- | --------------------------------------------- | ------- | ------------- | ------------------------------------------------------------------------------------------------- |
| 2026-08-01 | «выпил бутылку» + фото этикетки | Продукт по этикетке + новый приём             | 5       | —             | До инструментовки. Из них 3 вызова — разведка: поиск дубля, список наборов, `get_day`             |
| 2026-08-01 | «добавь туда 4 позиции»         | Пересборка приёма (`update_meal` ещё не было) | 9       | —             | 5 поисков + `get_day` + 3 холостых `get_day` за прошлые дни в поисках граммовки + delete + create |
| 2026-08-14 | запись дня (из Cloud Logging)   | `get_day`, `log_meal`, `add_water`            | 3       | ≈4600         | `log_meal` 1.6 с при 13 обращениях; `add_water` 2.7 с — холодный старт, а не норма                |
| 2026-08-17 | замер стоимости записи          | `get_day` ×2, `add_water` ±1 мл               | 4       | 3016          | Тёплый инстанс: чтение 283/304 мс, запись 1131/1298 мс. Разница — хвост записи                    |

Второй ряд — та самая причина, по которой появился `heys_update_meal`: девять
вызовов там, где хватает двух (`get_day` + `update_meal`).

Замер 17.08 отвечает на вопрос, ради которого журнал заводился: дорога не логика
и не чтение, а хвост записи. Чтение дня вместе с расчётом нормы стоит ~0.3 с, а
запись одного числа — 1.1–1.3 с на тёплом инстансе. Из этой разницы примерно
половина приходилась на стенограмму. Отсюда порядок работ: сначала дешевле
сделать саму запись, и только потом экономить круги агента.

Чего замер не показал и что остаётся открытым:

- **Холодный старт не пойман** — оба прогона попали на живой инстанс. Цена
  подъёма известна только по строке 14.08 (2.7 с против 1.2 с тёплых). Ответит
  `cold` / `uptime_ms`, когда накопятся строки.
- **Доля «повтор vs новая еда» не выводится** ни из логов, ни из журнала: за 3
  суток хранения реальных просьб про еду единицы. Решать, нужны ли `copy_meal`
  по имени и авто-подстановка наборов, придётся по живым случаям, а не по
  статистике.

## Как пополнять

После каждой просьбы, изменившей дневник, дописывать строку. `Σ duration_ms` —
сумма `duration_ms` из ответов инструментов, без времени на уточнения. Если
уточнение было, отметить это в заметке: оно объясняет, почему вызовов больше.
