# Тайминг записи в HEYS через коннектор

Здесь живут замеры и методика. Хронология попыток («что пробовали, что из этого
сработало») — в [OPTIMIZATION_LOG.md](OPTIMIZATION_LOG.md).

Зачем: видеть, какой сценарий записи чего стоит, и оптимизировать самый дорогой.
Без этого «стало медленнее» остаётся ощущением, а не числом.

## Что именно измеряется

Только машинная работа: от вызова инструмента до ответа. Время на уточнения у
пользователя и на раздумья модели сюда не входит — это другая величина, и мешать
их в одну нельзя.

Две точки замера:

- **Инструмент.** `duration_ms` приходит в `structuredContent` каждого ответа —
  видно прямо в диалоге, без похода в логи.
- **Функция.** Строка `t="mcp_call"` в Cloud Logging на каждый вызов:
  `duration_ms` — весь инструмент, `upstream_calls` и `upstream_ms` — обращения
  к `heys-api-rpc`. Разница между ними — собственная логика инструмента.
  `cold_start` — первый вызов на этом инстансе, `uptime_ms` — возраст процесса,
  `resp_bytes` — размер ответа, `arg_count` — число аргументов, `arg_keys` —
  имена полей верхнего уровня JSON-аргументов (без значений; с 18.08.2026),
  `session_id` и `seq` — подключение и номер вызова в нём.

  До 17.08 это была строка `[heys-mcp] tool_timing` с текстовым префиксом и
  именами `ms` / `upstream.calls` / `cold`. С 17.08 печатается чистый JSON без
  префикса (`{"t":"mcp_call",...}`). В Cloud Logging строка лежит в **message**
  (stdout функции), а не в `json_payload` — фильтровать надёжнее по
  `message: "mcp_call"`, не по `json_payload.t`. Состав строки задан белым
  списком `RECORD_FIELDS` в [lib/telemetry.js](lib/telemetry.js).

Обычно дорожает не логика, а число round-trip'ов: почти каждый инструмент читает
день, каталог продуктов и пишет обратно.

`cold` и `uptime_ms` появились потому, что без них строка неинтерпретируема: та
же запись стоит около секунды на живом инстансе и втрое дороже на поднятом с
нуля. Замер 17.08 (см. журнал) держался только на том, что вызовы шли подряд и
инстанс заведомо был тёплым, — на одиночной строке из лога так не скажешь.

### 3. Не делать

- `--group-name default` или id из `logging group list` — пусто по mcp_call.
- Только `json_payload.t = "mcp_call"` — stdout не попадает в json_payload.
- **`yc logging read --filter 'message: "mcp_call"'` для живой приёмки** —
  индекс message может отставать на минуты; пустой вывод ≠ поле не пишется. Для
  проверки свежего прогона (в т.ч. `arg_keys` / `copy_meal`) — только
  `yc serverless function logs d4epjmd9lnk059u29bg8 --since 15m --limit 40` и
  `grep mcp_call` (§1).
- Длинные bash-цепочки grep/sed/timeout на Windows — медленно; одной команды из
  §1 хватает.
- `yc serverless function logs` **без `--limit`** — поток, команда может висеть
  бесконечно; для выгрузки в файл всегда `--limit N`.
- Путать **вызовы модели** (сколько раз дернули инструмент в чате) и
  **`upstream_calls`** в строке (round-trip'ы к API внутри одного вызова).

### 4. Связка со стенограммой

Метка в блоке: `[mcp session=<id> seq=<n> ts=<ISO>]`. На cold start `session_id`
каждый раз новый, `seq` почти всегда 1 — соседние read цепляются **окном
времени**, не диапазоном seq:

```bash
node scripts/mcp-correlate.mjs --transcript transcript/2026-08-17.md --logs calls.txt
```

`calls.txt` — вывод `yc serverless function logs` или JSON-массив `mcp_call`.

В кураторском коннекторе то же самое по запросу:
`tasks_mcp_trace({ date, heading? })` читает **`mcp_call_events`** в Postgres
(не Cloud Logging). Сырьё хранится **180 суток**; дата старше — ошибка
`telemetry_retention_exceeded`. Полный процесс и пять ловушек (`taskDay`,
разъезд обмена на соседние heading, кэш инструкций в старой сессии) —
[`docs/operations/MCP_TRACE_RUNBOOK.md`](../../docs/operations/MCP_TRACE_RUNBOOK.md).

Stdout по-прежнему уходит в Logging (консоль, 3 суток). Агрегаты —
`mcp_call_daily` / `mcp_seq_daily` через `mcp_telemetry`:

```bash
node scripts/mcp-stats.mjs --days 7
```

Логи нужны для разбора одиночного вызова, агрегаты — для «что дорожает за
неделю». **Prod smoke после deploy:** свежий `tasks_checkpoint` → trace по его
heading (≥1 confirmed); старые обмены в Postgres не появятся. Подробнее —
[MCP_TELEMETRY_ROADMAP.md](MCP_TELEMETRY_ROADMAP.md), [README.md](README.md).

## Ожидаемая стоимость сценариев

Считается по числу обращений к API, а не по секундомеру: округляется медленнее и
не врёт при холодном старте функции.

Счёт ведётся по кураторскому пути — том самом, которым идёт коннектор. Раньше
таблица считала только чтение дня и запись; на деле к каждой записи прицеплены
ещё три вещи, и вместе они стоят больше, чем сама запись.

Постоянный хвост записи. Стенограмма и контекст висят на **каждом** инструменте
из `WRITE_TOOLS` — включая те, что дневной блоб не трогают (продукты, профиль,
наборы). Входы нормы читает только запись в день, через `writeDay`:

| Что                                   | Обращений | На чём                                                                |
| ------------------------------------- | --------- | --------------------------------------------------------------------- |
| Контекст записи                       | 1         | все пишущие; `issueWriteContext` кэшируется на инстанс                |
| Стенограмма (`transcript_checkpoint`) | 3         | все пишущие; ревизия до записи, append, проверка после                |
| Входы нормы дня                       | 1         | только запись в день; профиль, БЖУ, зоны и 4 прошлых дня одним батчем |

Стенограмма пишется **после** дневника и до 17.08 стоила 4 обращения: файл
читался ещё и целиком перед записью, хотя дельта-путь перечитывает ревизию сам.
Дубль убран, а оставшееся чтение ревизии стартует параллельно с записью дня.
Проверка после записи оставлена намеренно: уверенность, что стенограмма легла,
дороже сэкономленной четверти секунды.

| Сценарий                 | Инструмент                 | Обращений к API                                                        |
| ------------------------ | -------------------------- | ---------------------------------------------------------------------- |
| Вода                     | `heys_add_water`           | 2 + хвост — чтение дня, запись                                         |
| Тренировка               | `heys_log_training`        | 2 + хвост — чтение дня, запись                                         |
| Дневные показатели       | `heys_update_day`          | 2 + хвост — чтение дня, запись                                         |
| Новый приём              | `heys_log_meal`            | 4 + хвост — overlay, общая база, чтение дня, запись                    |
| Приём из набора          | `heys_log_meal` с `preset` | 5 + хвост — плюс чтение наборов                                        |
| Добавить в готовый приём | `heys_update_meal`         | 4 + хвост — overlay, общая база, чтение дня, запись                    |
| Продукт по этикетке      | `heys_create_product`      | 5 + хвост без нормы — overlay, общая база, tombstones, overlay, запись |
| Штуки с новым весом      | любой из записи еды        | +2 — чтение и запись overlay                                           |

Каталог читается двумя обращениями (личный overlay и общая база), но они уже
идут одним `Promise.all` — по времени это одно ожидание, а не два.

### Обращения и ожидания — разные величины

Числа выше — сколько раз инструмент ходит к API. Ждёт он меньше: независимые
обращения запускаются вместе. 17.08 таких мест стало на три больше:

- **день ‖ каталог** в `heys_log_meal`: день нужен только под конец, для
  классификации и записи, и от разбора позиций не зависит;
- **tombstones ‖ каталог** в `heys_create_product`: обе проверки идут до записи
  и друг о друге ничего не знают;
- **контекст записи ‖ чтения** для всех пишущих: `issueWriteContext`
  прогревается сразу после резолва клиента, а не в момент сохранения.

Тесты проверяют именно перекрытие, а не число вызовов: правка число не меняет.
`traceCalls` в `curator.test.cjs` пишет начало и конец каждого обращения и
падает, если одно снова начинает ждать другое.

Каталог кэшируется на один вызов, поэтому несколько позиций в одном приёме стоят
столько же, сколько одна. Разбивать приём на несколько вызовов — самый дорогой
способ сделать то же самое.

запись одного числа — 1.1–1.3 с на тёплом инстансе. Из этой разницы примерно
половина приходилась на стенограмму. Отсюда порядок работ: сначала дешевле
сделать саму запись, и только потом экономить круги агента.

сокращение записи упирается уже не в лишнюю работу, а в число обязательных
обращений: чтение дня, запись дня, append стенограммы и проверка после него.
Убрать что-то из них — значит отказаться от гарантии, а не от лишнего.

### Круги агента

Машинное время — половина ожидания. Вторая половина в том, сколько раз модель
сходила к серверу: каждый лишний вызов это ещё один круг «модель → функция →
модель», дороже любой экономии внутри инструмента.

17.08 из инструкции убрано требование звать `heys_list_meal_presets` перед
каждым новым составным приёмом. Набор и так резолвится по имени внутри
`heys_log_meal`, а если имени нет — ошибка возвращает список. Обязательный
список стоил целого круга на каждом составном приёме и ничего не добавлял.
Наверх инструкции поднят «БЫСТРЫЙ ПУТЬ» — частые просьбы куратора с минимальным
набором вызовов под каждую.

Эффект в секундах здесь замерить нельзя: он в поведении модели, а не в
`duration_ms`. Проверяется живым прогоном в Claude — сколько вызовов ушло на
одну просьбу. Тест сторожит только контракт: быстрый путь стоит до подробных
правил, и обязательного списка наборов в тексте нет.

18.08 ~02:13 — трейс составной реплики «конверт как в обед и блинчик»: wall 110
с, HEYS 3.9 с, 8 вызовов вместо 3 (3× `heys_get_day`, 3× `heys_search_products`,
2× `heys_log_meal`). Причина — быстрый путь покрывал только чистое «как вчера»,
а схема `copy_meal` писала «items/preset не нужны», хотя код складывает
`copy_meal` и `items` в один приём. Исправлено в инструкции и описании
инструмента 18.08.

Чего замер не показал и что остаётся открытым:

- **Холодный старт подешевел, но остаётся самым дорогим.** Первый вызов после
  деплоя — 1482 мс против ≈2700 мс на старом коде; тёплый — 937 мс. Разрыв между
  ними всё ещё полсекунды, и закрыть его можно только прогревом. Стоит ли он
  денег, покажет `uptime_ms`: если YC гасит инстанс за минуты, прогрев
  окупается, если за часы — нет.
- **Доля «повтор vs новая еда» не выводится** ни из логов, ни из журнала: за 3
  суток хранения реальных просьб про еду единицы. Решать, нужны ли `copy_meal`
  по имени и авто-подстановка наборов, придётся по живым случаям, а не по
  статистике.

### Замер 18–21.08 и что из него сделано

Первый разбор не по одному обмену, а по всем размеченным блокам четырёх суток
(`tasks_mcp_trace` за 18, 19, 20, 21.08). Цифры, ради которых журнал и
заводился:

| День  | Вызовов | `search_products` / из них дублей | `get_day` / дублей | `tasks_update` |
| ----- | ------- | --------------------------------- | ------------------ | -------------- |
| 18.08 | 336     | 60 / 55                           | 52 / 43            | 33             |
| 19.08 | 209     | 13 / 13                           | 6 / 2              | 1              |
| 20.08 | 193     | 18 / 17                           | 7 / 2              | 51             |

Главное число — **паузы между вызовами составляют 94–96% времени обмена**.
Медиана цепочки 30–58 с, а сама работа HEYS внутри неё — 2–4 с. Оптимизировать
инструменты дальше почти нечего; всё ожидание куратора сидит в числе кругов
«модель → функция → модель».

Второе — правило в инструкции работает, но не до конца. «СЧЁТЧИК ВЫЗОВОВ»
(добавлен 18.08) уронил дубли поиска втрое, и всё же 13–17 дублей за сутки
остаются: правило, которое некому проверить, соблюдается на усмотрение модели.

Третье — дубли бывают двух разных видов, и лечатся они по-разному. Точный повтор
(`get_day` за ту же дату) — это просто лишнее чтение. Перебор формулировок
(21.08, 13:44: «капучино с сиропом» → шесть поисков подряд разными словами,
затем приём составом) — следствие того, что ответ поиска не говорил, где конец:
выдача без точного совпадения выглядела так же, как выдача с ним.

Сделано 21.08 (`lib/repeat-guard.js`, `lib/mcp.js`, `lib/tools.js`,
`lib/tasks-tools.js`):

- **Повтор отдаётся из памяти инстанса** с первой строкой `[повтор] …`. Круг всё
  равно потрачен, но без обращения к API, и модель видит, что он был лишний. Кэш
  держит только читающие инструменты; любая запись стирает память подключения
  целиком — после `create_product` поиск идёт заново.
- **Второй поиск подряд получает подсказку**, что каталог просматривается
  целиком и по всем написаниям, а другая формулировка даст тот же список. Отказа
  нет: «8 креветок, помидор и яйцо» — это три законных поиска подряд, и отличить
  их от перебора сервер не может.
- **Ответ поиска закрывает сам себя.** Пустая выдача называет следующий шаг
  (`create_product` → приём), выдача без точного совпадения честно говорит, что
  это ближайшее по словам; в `structured` появилось `exact_match`.
- **`tasks_update` принимает `updates[]`.** 51 вызов за сутки и серии до
  тринадцати подряд — это тринадцать перезаписей одного файла проекта вместо
  одной. Правки одного проекта теперь применяются к тексту по очереди и
  сохраняются одной записью; непринятая правка отменяет весь вызов.

Проверено симуляцией, не живым прогоном: `node --test __tests__/*.test.cjs` —
1207 тестов, включая новый `repeat-guard.test.cjs` (повтор, окно, инвалидация
записью, серия поисков, чужое подключение, отказ не кэшируется) и батч-тесты
`tasks_update` (одна запись файла на несколько правок, два проекта, откат при
непринятой правке).

Эффект в секундах здесь замерить нельзя ровно по той же причине, что и у правки
17.08: он в поведении модели. Мерится следующим `tasks_mcp_trace` после deploy —
по числу вызовов на реплику и доле дублей, а не по `duration_ms`.

**Что показал живой прогон в тот же день** (то, чего тесты в одном процессе
поймать не могли):

- **Дедуп повторов работает только на тёплых цепочках.** Повторный
  `heys_search_products` с теми же аргументами вернулся полным вызовом:
  `cold_start=t` у большинства строк 21.08, YC разводит по разным инстансам даже
  последовательные вызовы, а память guard живёт в инстансе. Подсказки в ответе
  поиска и батч `tasks_update` от инстанса не зависят и работают всегда — они и
  были главными. Общая память между инстансами (`SELECT` перед каждым читающим
  вызовом) — отдельное решение, не принято.
- **Подсказку перенесли с памяти инстанса на телеметрию.** Раз память почти
  всегда пуста, серию считает сервер: `count_mcp_recent_calls` по уже пишущимся
  событиям. Запрос идёт параллельно работе инструмента, поэтому ожидание
  куратора не растёт, а сбой означает просто отсутствие подсказки. Аргументы в
  счёте не участвуют — серия считается по инструменту, значений запросов в БД
  по-прежнему нет. Эффект меряется полем `hint` и блоком «Лишние круги и
  подсказки» в `scripts/mcp-stats.mjs`; базовая линия до включения — 40.4%
  (18.08) и 45.6% (20.08) вызовов «в серии».
- **`conn_id` от токена склеивал параллельные чаты.** В трейс обмена 14:37
  попали `heys_create_product` и `heys_update_meal` из соседнего чата — токен у
  них общий. Исправлено в тот же день: сервер выдаёт `Mcp-Session-Id` на
  `initialize` и считает `conn_id` от метки чата, с откатом на токен для
  клиентов без поддержки сессии. Метка выдаётся при подключении, поэтому
  проверяется на новом чате, а не на уже открытом.

## Как пополнять

После каждой просьбы, изменившей дневник, дописывать строку. `Σ duration_ms` —
сумма `duration_ms` из ответов инструментов, без времени на уточнения. Если
уточнение было, отметить это в заметке: оно объясняет, почему вызовов больше.
