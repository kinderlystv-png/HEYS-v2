# prompt-push-consent-gate

**Цель.** Отказ и отзыв согласия на push должны гасить **доставку** на сервере,
а не только не подписывать устройство на фронте. Сейчас гейта нет вовсе.

**Основание.** 152-ФЗ ст. 21 ч. 5: после отзыва согласия обработка по этому
основанию прекращается. В форме заявки основание для push заявлено как согласие.
Значит отозвавший не должен получать доставку.

**Чего эта задача НЕ касается.** Подписи `ocenka-pravovogo-rezhima.md`. Оценка в
§5 п. 5 утверждает ровно две вещи — одноразовый код кандидата и серверный
перечень допустимых служб доставки при **приёме подписки**. Обе на проде с
13.08, обе правдивы. Про гашение доставки при отзыве оценка не утверждает
ничего. Не трогайте текст оценки и не ждите её.

Отправляется с **обязательной преамбулой** из `handoff-prompts.md` и
`release-plan.md`.

## Источник истины по согласию

Таблица `public.consents`, тип `push_notifications`, версия `1.0` активна в
`legal_consent_registry` (`database/2026-07-27_consent_proof_v2.sql`).

Предикат «согласие живо» — ровно такой, без вариантов:

```sql
EXISTS (
  SELECT 1 FROM public.consents
   WHERE client_id = $1
     AND consent_type = 'push_notifications'
     AND granted = true
     AND revoked_at IS NULL
)
```

Уникальность в таблице — `(client_id, consent_type, document_version)`, то есть
у одного клиента может быть несколько строк одного типа разных версий. `EXISTS`
по любой живой строке — правильное поведение: согласие на любую действующую
версию считается данным. Но **отзыв обязан гасить все версии сразу** —
проверьте, что существующий путь отзыва так и делает, и если нет, почините.

## Что сделать

Три точки. Все три обязательны — гейт на отправке без чистки подписок при отзыве
оставляет данные, которые нельзя обрабатывать.

### 1. Приём подписки — не принимать без согласия

В `handleSubscribe`, **после** проверки хоста и **до** `INSERT`: клиент без
живого согласия → `403`, код причины `push_consent_missing`, `console.warn` с
`client_id` и причиной, как сделано у белого списка.

### 2. Отправка — не отправлять без согласия

В `handleTest` и в любом будущем отправителе. Не «фильтровать подписки», а
проверять согласие **до** запроса к `push_subscriptions`: если согласия нет, до
чтения эндпоинтов дело доходить не должно. Ответ — `403`,
`push_consent_missing`, отдельный код, не путать с `no_subscriptions`.

Вынесите предикат в один общий модуль рядом с `push-endpoint-host.js` (например
`push-consent.js`) и зовите его из обеих точек. Два скопированных SQL
разъедутся.

### 3. Отзыв — удалять подписки

Найдите **все** пути отзыва и перечислите их в отчёте. Как минимум:

- `revoke_consent` — `database/2025-12-20_consents.sql` (~205–230)
- флоу отзыва в `database/2026-07-27_trial_intake_flow.sql` (~582–625) — там
  сейчас чистятся только health-ключи по `is_health_key`
- `database/2026-05-20_compliance_overhaul.sql` (~1117) — комментарий про detach
  `push_subscriptions`, проверьте, что там на самом деле происходит

Отзыв `push_notifications` →
`DELETE FROM push_subscriptions WHERE client_id = …`. Отзыв `personal_data` →
тоже, push не может пережить отзыв основного согласия.

Делайте это в БД, в самой функции отзыва, а не в вызывающем коде. Механизм
должен стоять на пути, а не быть договорённостью, что его позовут.

## Границы

- **Кураторы вне задачи.** `curator_push_subscriptions` не трогать. Куратор —
  сотрудник, основание обработки у него другое, и модель согласий своя
  (`curator_consents`). Смешивать два основания в одном гейте — ошибка. В отчёте
  напишите явно, что кураторская ветка не менялась.
- Фронт не переделывать. `notificationsOptIn` работает правильно, он просто
  недостаточен.
- Текст согласия, версии документов, `legal_consent_registry` — не трогать.
- Белый список хостов не трогать, он выкачен и работает.

## Fail closed, и что это ломает

Нет строки согласия — доставки нет. Это правильное поведение, но оно выключит
push тем, кто подписался до появления типа `push_notifications`.

**До правки** снимите с прода и приведите в отчёте: сколько строк в
`push_subscriptions`, по каким `client_id`, и есть ли у каждого живое согласие
`push_notifications`. По состоянию на 13.08 там была одна подписка, хост
`web.push.apple.com`. Если у неё согласия нет — **не удаляйте молча**, покажите
владельцу и дождитесь ответа. Скорее всего это его собственное устройство.

## Тесты

Обязательный минимум, все на уровне функции:

1. Согласие живо → `subscribe` принимает, `test` отправляет.
2. Согласия не было никогда → оба `403 push_consent_missing`.
3. Согласие отозвано (`revoked_at` проставлен) → оба `403`, и строк в
   `push_subscriptions` у этого клиента не осталось.
4. Две строки согласия разных версий, одна отозвана, одна живая → доставка идёт.
5. Отзыв `personal_data` → подписки удалены.
6. Кураторская ветка не задета: у куратора без клиентского согласия `test`
   работает как раньше.

DB-тесты на функции отзыва — отдельно, по образцу тестов миграции одноразового
PIN.

## Порядок и выкат

1. Снять состояние прода (см. выше), доложить **до** правок.
2. Код + миграция + тесты, один коммит, source-only, без бандлов.
3. Прогнать pre-push. Чужой dirty не трогать: в прошлый раз pre-commit сдвинул
   строки в `bootstrap-bypass-allowlist.txt` под чужой WIP и push отбился.
4. Миграцию на прод — отдельным шагом, с отдельным докладом.
5. Деплой `heys-api-push` — **только с коммита, который уже в `origin/main`**. В
   прошлый раз функцию выкатили с `33a4b0a25`, которого в ветке нет; пришлось
   деплоить второй раз. Version id из первого деплоя не годится ни для отчёта,
   ни для плана.
6. Post-deploy health + живая проверка: запрос без согласия получает `403`
   `push_consent_missing`.
