# D. Механика подписания согласия

**Для юриста · HEYS · сверка 11.08.2026**

## Каким действием клиент подтверждает согласие

Сейчас — **галочка (checkbox) и явное продолжение** в аутентифицированной
сессии.

- На экране согласий клиент отмечает обязательные типы (пользовательское
  соглашение, обработка ПДн, данные о здоровье; маркетинг и прочие — отдельно) и
  нажимает кнопку продолжения.
- SMS-код / простая электронная подпись **построены в коде, но выключены**
  флагом `SMS_VERIFICATION_ENABLED = false`. Пока флаг выключен, все живые
  записи идут со способом `signature_method: "checkbox"`.
- Отдельная поверхность: шаг 1 предтриальной анкеты — чекбокс согласия на данные
  о здоровье у кандидата (ещё не клиента). Пишется в таблицу
  `trial_candidate_consents`, не в клиентскую `consents`.

ПЭП по SMS и соглашение об использовании ПЭП — подготовлены как следующий
контур; **на дату сверки клиент ими не подписывается**.

## Что записывается на сервере в этот момент

В таблицу согласий (клиентскую или кандидатскую) уходит примерно такой набор:

| Поле                  | Смысл                                                                                                                        |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Тип согласия          | `user_agreement`, `personal_data`, `health_data`, `marketing`, `speech_transcription`, push и т.д.                           |
| Версия документа      | Например `health_data` 1.5, `personal_data` 1.7, `user_agreement` 1.10                                                       |
| `granted`             | принято / нет                                                                                                                |
| `signature_method`    | сейчас `checkbox`                                                                                                            |
| `document_sha256`     | контрольная сумма текста версии из серверного реестра `legal_consent_registry` (для записей после внедрения proof-контракта) |
| `accepted_at` / время | серверное время принятия                                                                                                     |
| IP-адрес              | из запроса (источник IP сейчас спорный: приоритет `x-forwarded-for` позволяет подделку; правка в плане)                      |
| User-Agent            | строка браузера / клиента                                                                                                    |

Полный текст документа **в строку согласия не копируется** — копируется хэш и
номер версии.

## Сколько хранится запись

По политике конфиденциальности: доказательства согласий — **не менее 3 лет после
отзыва** (или дольше при споре / обязанности доказать согласие). Сюда же
относится журнал подписания ПЭП и тексты версий документов: они не удаляются
вместе с иными данными субъекта в общие сроки. В операторском черновике
retention фигурирует и ориентир «5 лет» — это открытый вопрос к юристу на
согласование цифры в публичных текстах.

**Решение владельца 11.08.2026 (соглашение ПЭП):** вход допускается с
зарегистрированного устройства без кода; **подписание документа всегда требует
ввода кода доступа**. Согласие на трансграничную передачу из перечня
подписываемых документов убрано — трансграничной передачи клиентских ПДн нет.

## Можно ли восстановить текст той версии, которую человек видел

**Да, если выполнены оба условия:**

1. В записи согласия есть корректные **версия** и **`document_sha256`**.
2. Текст этой версии сохранён как неизменяемый снимок
   (`apps/web/public/docs/v…/` и запись в `legal_consent_registry` с путём к
   документу).

Тогда проверка: взять архивный текст версии → посчитать SHA-256 → сравнить с
хэшем в записи. Совпадение = это тот текст.

**Ограничения (факт на 11.08):**

- У части старых записей `document_sha256` пустой — текст этих согласий
  **доказать хэшем нельзя**.
- Есть исторические версии в записях, которых нет в реестре (тексты не
  сохранены) — восстановление невозможно.
- Пока клиент присылает версию с фронта, а реестр живёт отдельно, теоретически
  возможна рассинхронизация; правило «клиент шлёт версию+хэш показанного, сервер
  сверяет с реестром» в плане, гейт ещё не включён.

Итого для юриста: **механизм восстановления текста версии есть и задуман
правильно; полнота доказательной базы по всем историческим строкам — нет.**
Новые записи после proof-контракта опираются на серверный хэш из реестра.
