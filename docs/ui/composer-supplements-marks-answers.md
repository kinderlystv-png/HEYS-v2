# Ответ кодера · отметки приёма добавок

**Зачем:** снять строку `отметки «выпил» здесь нет` в контракте вкладки
«Питание» (`nutrition-tab.v4.dc.html:329`, `ACCEPTANCE-nutrition-tab.md:54`) и
нарисовать блок «Добавки» с отметками. Ниже — как механика устроена **сейчас**,
по коду, а не по памяти.

**Главный вывод:** механику не надо придумывать — она вся есть в легаси-карточке
`HEYS.Supplements.renderCard` (`apps/web/heys_supplements_v1.js:2396`), которая
живёт в дневнике дня (`apps/web/heys_day_diary_section.js:779`). Вкладка
«Питание» v4 показывает **только состав** (`heys_day_nutrition_v1.js:669`),
потому что так был написан контракт. Переносить есть что. Но в самой механике
есть **четыре расхождения**, которые надо чинить кодом до отрисовки — они в
конце.

Источники: `apps/web/heys_supplements_v1.js`, `heys_day_nutrition_v1.js`,
`heys_day_diary_section.js`, `heys_health_features_v1.js`,
`heys_consents_v1.js`, `heys_cascade_card_v1.js`, `heys_gamification_v1.js`,
`yandex-cloud-functions/heys-mcp/lib/day.js`.

## 1. Данные

**1. Где курс.** В профиле (`heys_profile`, per-client, синкается в облако). Не
одна запись, а три поля:

| Поле                              | Что в нём                                                                                                 |
| --------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `plannedSupplements: string[]`    | **весь курс — просто массив id** каталога, порядок = порядок добавления                                   |
| `supplementSettings: {id: {...}}` | `{ form, dose, unit, updatedAt }` — пишутся только эти три поля (`heys_supplements_v1.js:3075,3110,3129`) |
| `supplementHistory: {id: {...}}`  | `{ startDate, days, totalTaken, lastTaken, takenDates[], sideEffects[] }`                                 |

Названия/иконки/время приёма **не хранятся** — они в неизменяемом каталоге
`SUPPLEMENTS_CATALOG` (`heys_supplements_v1.js:21`, 33 позиции). Свободный ввод
отключён намеренно (`addCustomSupplement` — no-op, `:354`), это требование
согласия «только позиции из справочника».

Чего в курсе **нет вообще**: дней недели, периода курса (даты начала/конца),
флага активности. Позиция либо в массиве, либо её нет. `startDate` в истории —
не курс, а «когда впервые отметили», и ставится он не всегда (см. дыру №2).

**2. Где факт приёма.** Внутри дня, `heys_dayv2_<YYYY-MM-DD>`:

```js
supplementsTaken: ['vitD', 'magnesium'],              // отметки
supplementsTakenAt: { vitD: '08:14' },                // время нажатия, HH:MM local
supplementsTakenMeta: { vitD: { form, dose, unit } }, // снимок дозы на момент отметки
supplementsTakenUpdatedAt: 1755950000123,             // для sync stale-guard
supplementsPlanned: ['vitD'],                         // снимок курса на этот день
```

`supplementsPlanned` в дне — важная вещь: день помнит **свой** состав курса,
поэтому правка курса задним числом не переписывает историю.

**3. Дата или время.** И то и другое: отметка привязана к `dateKey` **открытого
на экране дня**, а время нажатия пишется в `supplementsTakenAt[id]` как `HH:MM`
по локальным часам. Ночного правила (как у приёмов пищи, где 00:00–02:59 уезжают
на вчера) для добавок **нет** — берётся календарная дата экрана.

**4. Правка курса.**

| Что сделали                | Что с прошлыми отметками                                                                        |
| -------------------------- | ----------------------------------------------------------------------------------------------- |
| Переименовали добавку      | невозможно — каталог фиксированный, id стабильны                                                |
| Изменили дозу              | прошлые отметки хранят **старую** дозу в `supplementsTakenMeta`                                 |
| Убрали позицию из курса    | отметка в дне остаётся, но становится невидимой: карточка считает пересечение `planned ∩ taken` |
| Добавили позицию среди дня | дописывается в `supplementsPlanned` сегодняшнего дня, отметки не трогаются                      |
| Прошлые дни                | не трогаются никогда — у них свой `supplementsPlanned`                                          |

Потерь нет, но есть «осиротевшие» отметки — id, который отмечен, а из курса уже
убран. Они лежат в данных и нигде не показываются.

**5. Прошлые дни.** Редактируются свободно, ограничения нет. Карточка
монтируется с `dateKey` того дня, который открыт
(`heys_day_diary_section.js:779`), проверки `isToday` в этом месте нет вообще.
«Момента закрытия дня» для добавок не существует.

## 2. Категории времени

**6. Точный список.** Их два слоя.

У каждой позиции каталога — своё `timing`, 9 значений
(`heys_supplements_v1.js:8`): `morning` Утром · `withFood` С едой · `withFat` С
жирной едой · `evening` Вечером · `beforeBed` Перед сном · `empty` Натощак ·
`beforeMeal` До еды · `afterTrain` После трени · `anytime` Любое время.

В карточке они сворачиваются в 4 группы (`:1479`), а `anytime` затем **вливается
в «Утро»** (`groupByTimeOfDay`, `:1491`) — чтобы не показывать бейдж «Любое
время». Итог на экране — ровно **три блока, в этом порядке**:

1. 🌅 **Утро** — `morning`, `empty`, плюс `anytime` и `afterTrain`
2. 🍽️ **С едой** — `withFood`, `withFat`, `beforeMeal`
3. 🌙 **Вечер** — `evening`, `beforeBed`

**7. Свойство или вычисление.** Свойство каталога. Из времени ничего не
выводится. Персональный override времени можно записать в
`supplementSettings[id].timing`, но **его никто не читает** — группировка идёт
только по каталогу (`:1500`). Поля в UI для него тоже нет.

**8. Две категории.** Нельзя. Одна позиция = один id = одна группа = одна
отметка в сутки. «Дважды в день» текущей моделью не выражается никак.

**9. Пустая категория.** Скрывается: `renderGroup` возвращает `null` на пустом
списке (`:2603`), в разметке остаётся только воздух. Пустого состояния у группы
нет.

## 3. Три способа отметить

**10. Что было, а что придумываем.**

| Способ                     | Было?                                                                                                                                                                         |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Тап по строке (чипу)       | **да**, `handleClick` `:2718` → `markSupplementTaken`                                                                                                                         |
| Тап по заголовку категории | **да**, шапка группы — кнопка `:2633` → `markSupplementsTaken` пачкой                                                                                                         |
| «Отметить всё»             | **кнопки нет.** Функция `markAllSupplementsTaken` (`:1316`) и публичный `markAllTaken` есть, замыкание `markAll` (`:2537`) написано — но в разметку не выведено. Мёртвый код. |
| Долгое нажатие / 🔬        | **да**, открывает научную карточку, а не отмечает                                                                                                                             |

То есть «отметить всё» — это то, что мы **добавляем заново**, но API под него
уже лежит готовым.

**11. Одно действие или N записей.** N записей. Тап по категории делает
`markSupplementsTaken(dateKey, notTakenInGroup, true)` — дописывает N id в тот
же плоский массив `supplementsTaken`. Отдельной сущности «категория отмечена»
нет. **Поэтому да — снять одну позицию внутри отмеченной категории можно**, и
это единственный способ: шапка группы, когда всё отмечено, кликом уже не
снимается (`cursor:default`, `if (!allGroupTaken)` `:2637`).

**12. Повторный тап.** По чипу — снимает отметку, без подтверждения и без тоста
отмены. Побочно гасит празднование «всё принято». По шапке группы — не снимает
(см. выше).

**13. Счётчик.** Два: в шапке карточки — полоска прогресса + `принято/всего`
(`:2863`); в шапке каждой группы — `n/m`, и он **исчезает**, когда группа
закрыта, уступая место ✓ (`:2678`). Процентов нет.

**14. Частичная категория.** Третьего состояния в данных нет и не нужно: и
«частично», и «всё» вычисляются на лету из `taken ∩ группа`. В данных живёт
только плоский список отмеченных id.

## 4. Связи

**15. На что влияет.** На оценку дня и риск — **ни на что**, и это осознанно:
каскадный score обнуляет фактор явно (`heys_cascade_card_v1.js:1452,1731,3151` —
«Трекинг плана не является доказательством пользы»), бонус к инсулиновой волне
тоже прибит к нулю (`heys_supplements_v1.js:1394`). Влияет только на:

- **геймификацию** — 5 XP в день (`heys_gamification_v1.js:113`) и ачивка
  «Первый план добавок» 20 XP (`:146`), по событию `heysSupplementsTaken`
  (`:5694`);
- **советы** — утреннее напоминание про неотмеченное (`advice/_other.js:42`),
  раз за сессию.

**16. Куратор.** Видит: это поля дня клиента, куратор открывает тот же экран.
Через MCP `heys_get_day` отдаёт `supplements_planned` / `supplements_taken`
(`yandex-cloud-functions/heys-mcp/lib/day.js:2441`), `heys_update_day` умеет
`supplements_mark` / `supplements_unmark` (`lib/tools.js:3672`). **Отдельного
отчёта или выгрузки по курсу нет.** Есть только `getComplianceStats(daysBack)`
(`heys_supplements_v1.js:1345`) — процент соблюдения за N дней, и он сейчас
используется только внутри советов.

**17. Напоминания.** Пушей и локальных уведомлений **нет**. Есть две подсказки
внутри приложения, обе от часов, а не от планировщика:

- баннер в самой карточке (`getTimeReminder`, `:1044`): 7–10 «Утренние добавки
  ждут», 21–23 «Не забудь вечерние», 12–18 при ≥3 неотмеченных;
- совет на главной, один раз за сессию.

Обе привязаны к группам времени, но берут **текущий час**, а не час открытого
дня (см. дыру №4).

**18. «Сколько дней подряд».** Такого нет. В `supplementHistory[id]` копится
`takenDates[]` и `days` = **число уникальных дат всего**, не подряд. Серию
считать не из чего без прохода по дням.

## 5. Согласие и доступность

**19. Согласие.** Подтверждаю, это про эти же данные. Тип `supplements_tracking`
версии `1.0`. Чип «Добавки» на вкладке помечен `needsConsent: true`
(`heys_day_nutrition_v1.js:369`) и включает флаг через
`requestHealthFeatureToggle` (`:409`).

Короткий текст (`heys_consents_v1.js:189`):

> **Вести отметки о добавках из справочника сервиса** Сохраняем выбранные
> позиции и даты приёма. Лекарства вносить нельзя. Видят вы и куратор. Можно
> отказаться без потери доступа к HEYS.

Полный текст, «Что сохраняем по добавкам?» (`:265`):

> 📋 Только позиции из справочника сервиса и даты приёма 🚫 Лекарства и
> свободный ввод недоступны 👤 Видят вы и назначенный куратор 🚪 Можно
> отказаться сейчас или выключить позже — доступ к HEYS сохранится 🗑️ Выключение
> удаляет сохранённые отметки

Последняя строка не декоративная: выключение реально вычищает и поля дня, и поля
профиля (`heys_health_features_v1.js:160,175`).

**20. Без курса.** Сейчас поведение разное на двух экранах, и это надо решить:

- вкладка «Питание» v4 — блок **исчезает целиком** (`renderSupplementsBlock`
  возвращает `null` на пустом курсе, `heys_day_nutrition_v1.js:673`);
- легаси-карточка дневника — показывает приглашение: 💊, «Добавки не настроены»,
  «Ведите свой план и проверяйте дозы и ограничения», кнопки «⚙️ Настроить курс»
  и «Скрыть карточку» (`heys_supplements_v1.js:2406`).

Чип на вкладке при этом включён — то есть человек включил «Добавки» и не видит
ничего. Приглашение из легаси-карточки просится сюда.

## Что чинить кодом до отрисовки

Четыре расхождения. Первые два — прямые дефекты, чиню без обсуждения; третье и
четвёртое зависят от того, что вы нарисуете.

**1. Одиночный тап затирает время всех отметок.** Пачка пишет
`supplementsTakenAt` как карту `{id: 'HH:MM'}` (`:999`), а одиночный тап
(`:1296`) и `markAllTaken` (`:1321`) **перезаписывают всё поле** одной
ISO-строкой `new Date().toISOString()`. То есть тап по одному чипу стирает время
приёма всех остальных за день. Каноничная форма — карта: так пишет и сервер
(`heys-mcp/lib/day.js:1687`).

**2. Одиночный тап не попадает ни в историю, ни в XP.**
`updateSupplementHistory` зовётся только из пачки (`:1010`), событие
`heysSupplementsTaken` — только из пачки и `markAllTaken`. Значит самый частый
способ отметить (тап по чипу) не двигает ни `takenDates`, ни `startDate`, ни XP.
Поэтому «сколько дней принимал» сейчас считает не то.

**3. Снять отметку с целой категории нечем.** Отметить группу — один тап, снять
— только по одной. Если рисуете обратимость на уровне категории, нужен второй
режим у шапки; если нет — надо назвать это в контракте явно.

**4. Напоминание в карточке смотрит на текущий час на любом дне.** Откройте
прошлый вторник в 22:00 — увидите «Не забудь вечерние» про тот вторник. На
закрытом дне баннер надо гасить.

Отдельно, не дефект, а решение для вас: **«дважды в день» модель не умеет** — id
один, отметка одна. Если в кадрах появится позиция с двумя временами, это уже
другая схема данных (id + слот), и её надо закладывать до реализации, а не
после.

## Что мне нужно от кадров

- Три блока времени (🌅 Утро · 🍽️ С едой · 🌙 Вечер) или другое деление — если
  другое, назовите, куда девать «натощак», «после трени» и «любое время».
- Обратимость: снимается ли категория целиком.
- Пустой курс на вкладке: приглашение или ничего.
- Нужен ли «отметить всё» отдельной кнопкой при уже существующих тапах по трём
  шапкам.
