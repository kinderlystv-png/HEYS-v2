# Расхождения с контрактом v4 — открытые вопросы

Здесь лежит только то, что **ждёт решения**. Закрытая запись уезжает в
[`UI_V4_FINDINGS_HISTORY.md`](UI_V4_FINDINGS_HISTORY.md) вместе с решением —
иначе дизайнер получает файл, в котором нужное тонет среди уже разобранного.

Сюда идёт то, что нашлось при сведении экрана с пакетом
[`docs/ui/handoff-v4/canvas/Переработка дизайна приложения/`](handoff-v4/README.md)
и **меняет контракт, кадр или приёмочный лист**. Не баг-трекер: дефект кода, где
контракт прав и однозначен, чинится молча и живёт в протоколе своего экрана.

**Формат записи:** что нашли · чем это грозит · что предлагаю · чей ход.

**Статусы:** `?` ждёт дизайнера · `!` решено без дизайнера (тогда рядом — почему
нельзя было ждать).

---

**Разложено по адресату:** дизайнер отвечает за кадры, контракт и приёмочный
лист; владелец — за продуктовые и палитровые решения; зона — за свой код.
Запись, у которой ход дизайнера закрыт, уезжает в архив целиком, а её открытый
хвост остаётся здесь короткой записью со ссылкой на разбор.

## Ждут дизайнера

<a id="frames-still-carry-55-percent-ink"></a>

### `?` Кадры остались на 55 % чернил после решения о 56 и 61

**Что нашли.** 7 сентября доля `--v4-ink-2` изменена вашим решением: песочный 55
→ 56 %, синий 55 → 61 %. Повод — метод, который вы же назвали: доля считается по
САМОЙ ТЁМНОЙ поверхности набора, а не по фону; при 55 % выходило 4,48 в песочном
и 3,77 в синем, то есть ниже 4,5. Код решение несёт. Кадры пакета по-прежнему
рисуют 55 %.

**Чем это грозит.** Около сорока пяти проверок сведения красные на разнице в
одну сотую: `кадр: rgba(0,0,0,0.55) · код: rgba(0,0,0,0.56)`. Это не дефект кода
и не повод править число под кадр — но пока кадры не перерисованы, гейты зон
показывают красноту, в которой тонут настоящие расхождения. Своей выкатке это не
мешает: гейты сведения с 3 сентября живут в отдельном контуре.

**Что предлагаю.** Перевыпустить кадры с 56 % в песочном и 61 % в синем — либо
сказать, что кадры остаются справочными по цвету, и тогда мы внесём долю чернил
в список исключений гейтов поимённо.

**Чей ход.** Дизайнера.

**Смежное.** В продукте 480 записей `var(--v4-ink-2, rgba(0, 0, 0, 0.55))` —
запасное значение отстало от роли на ту же сотую. На экран это не влияет: роль
объявлена во всех четырёх наборах и рисуется она. Правим отдельной задачей,
чтобы не мешать её с этим разбором.

<a id="home-widgets-absolute-fab-touch"></a>

### `?` Главная · плавающие кнопки с `position: absolute` и слайдер масштаба

**Что нашли.** В зоне home-widgets часть целей уже добирает 44 pt прозрачным
`::after` (минус undo, карандаш, resize/delete в режиме редактирования, крестик
шторки). Гейт polosa 1 всё равно видит нарушение у элементов с
`position: absolute` в первом rule-блоке: `.widgets-quick-minus`,
`.widgets-quick-pencil`, `.widget__resize-handle`, крестики sparkline/metric
popup, `.sparkline-brush-stats`, `.sparkline-zoom-indicator`. У
`.widgets-settings__scale-slider` видимая дорожка 4 px — цель по смыслу ползунок
18 px. У `.widget` декоративный `::after` (линия сверху) занят визуалом и не
может стать hit-area без смены разметки.

**Чем это грозит.** Контракт «рисунок меньше 44, нажимается 44» в коде соблюдён
через `::after`, но машинный гейт visible-targets и требование
`position: relative` на хосте расходятся с канвасом, где кнопки привязаны к
углам сетки.

**Что предлагаю.** A — разрешить для угловых FAB `::after` на
`position: absolute` (обновить гейт). B — обернуть иконку во внутренний
`relative`-хост (разметка). C — для слайдера назвать исключение «дорожка 4 px,
thumb 44» в контракте. D — режим «удалить виджет»: цель = вся плитка без
отдельного hit-layer.

**Чей ход.** Дизайнер.

### `?` date-remainders · видимые 44 px vs гейт visible-targets

**Что нашли.** Капсула даты, «Сегодня» inline и «Вчера» закрыты по polosa6:
`min-height: 44px` и/или `::after` без увеличения рисунка. Гейт
`ui-v4-check-touch-target-visible` всё ещё помечает их как 0×0 (jsdom не мерит

**Чем это грозит.** Красный инвентарь polosa 1 не отражает контрактный тест

**Что предлагаю.** Не править baseline до учёта `::after` в гейте (решение
владельца 7 сентября). Для шапки — отдельный smoke с computed-style на 375 px.

**Чей ход.** Владелец / инфра (гейт), не дизайн.

### `?` norm-correction · NC5 · строка 07 · stable_girths недостижим из owner-flow

**Что нашли.** Кадр «Сверка · норма снизилась · 07» требует прозу «Три недели
вес и обхваты держатся на месте». Код умеет рендерить её только при

**Что предлагаю.** A — расширить server RPC обхватами biceps/thigh и тогда
закрыть ·07 в «=». B — ограничить кадр условием подтверждённых замеров (как
ветка «без обхватов»). C — назвать отдельный маршрут applied Pro-decision для
`waist_only`.

**Чей ход.** Владелец/server + дизайнер (ветка кадра). До решения вердикт
остаётся «?».

### `?` Четыре узла messenger без строки контракта

**Что нашли.** При переводе зоны на роли набора нашлись четыре места, которым
контракт не называет ни цвета, ни роли: полоса прокрутки ленты, фон своей
звуковой записи (белая `rgba`), подложка ожидающего оверлея и заглушка вложения.
Плюс семь литералов затемнения лайтбокса в поле ввода — тоже без строки.

**Чем это грозит.** Без строки контракта роль выбирается на глаз, а выбор на
глаз здесь неоднозначен по построению: в песочном наборе несколько ролей несут
одно значение и расходятся только в синем и тёмном. То есть угадавший сегодня
получит расхождение завтра.

**Что предлагаю.** Дописать строки контракта на эти узлы — по одной фразе с
ролью. Это дешевле, чем разбирать потом расхождение в тёмном наборе.

**Чей ход.** Дизайнер. До ответа литералы остаются на месте и названы здесь, а
не переведены наугад.

**Ответ для handoff (7 сентября, пакет 47).** Четыре узла без строки — назовите
по одной строке контракта с ролью набора:

| Узел                        | Селектор в продукте                                                  | Сейчас в коде                                                      |
| --------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Полоса прокрутки ленты      | `.messenger-thread` (`::-webkit-scrollbar-thumb`, `scrollbar-color`) | `rgba(100, 116, 139, 0.22)` — без роли                             |
| Фон своей звуковой записи   | `.msg-audio` (свой пузырь)                                           | фон `rgba(255,255,255,0.16)`, border/play `rgba(255,255,255,0.18)` |
| Подложка ожидающего оверлея | `.msg-attachment-pending`                                            | `rgba(0,0,0,0.4)`, текст `var(--v4-bg)`                            |
| Заглушка вложения           | `.msg-attachment-item`                                               | `var(--v4-accent-bg, #f0dcc6)`                                     |

Семь литералов затемнения лайтбокса в поле ввода — отдельный долг, не входят в
эти четыре.

### `!` Крестик шапки приёма ушёл с акцента в чернила при миграции литералов · food-meal

**Что нашли.** Проверка `meal-time-v4-structure` требует `background: #c67139` у
глифа `.mc-modal--meal-create .mc-header-btn--close`, а в коде теперь
`var(--v4-ink-3, rgba(0, 0, 0, 0.45))`. Тест красный, и он в деплойном контуре.

**Почему это не просто устаревший тест.** `#c67139` — это **значение роли
`--v4-act`** в песочном наборе. Правильная миграция такого литерала —
`var(--v4-act, #c67139)`; перевод в `--v4-ink-3` меняет вид: терракотовый
крестик становится серым. То есть здесь совпали два дефекта разного рода — тест
сторожит литерал вместо роли, и миграция подменила роль.

**Что сделали без дизайнера.** Ничего в коде: зона `food-meal` занята сессией
сведения, и цвет крестика — вопрос её кадра, а не попутной уборки. Находка
передана владельцу зоны с точным диагнозом, чинится вместе с вердиктом кадра:
роль по кадру плюс проверка, сторожащая роль, а не литерал.

**Чей ход.** Сессии зоны `food-meal`; дизайнеру — только если кадр действительно
рисует крестик нейтральным, а не акцентным.
