# Вердикты контракта v4 — по файлу на зону

Здесь лежит вердикт по каждой строке `[data-contract]` каждого канваса: что код
делает с этой строкой и чем это подтверждено. Один файл — одна зона, имя файла
совпадает с id зоны: `home-widgets.json`, `tab-activity.json` и так далее.

Найти зону по канвасу: имя файла зоны совпадает с именем канваса без
`.v4.dc.html`. Поле `canvas` внутри файла называет его точно.

## Почему по файлу на зону

До 31 августа это был один файл `docs/ui/ui-v4-contract-verdicts.json` на все
зоны. За один день он дважды уехал в чужой коммит целиком, вместе с чужой
незакоммиченной работой: `38ce39110` забрал вердикты библиографии, дневного
долга и «Актива», `94d6301a4` — зоны `food-meal` и `product-card`.

Дисциплиной коммита это не лечится, и явные пути не спасают:
`git commit -- <путь>` берёт **текущее содержимое файла целиком**, а снимок
правится в середине разбора зоны — коммитить середину нельзя, а к концу разбора
в файле уже чужое. При одном файле на 23 зоны избежать этого нельзя вообще
никак.

Теперь каждый коммитит свой файл, и чужая работа физически не может попасть в
чужой коммит.

## Как работать

```bash
# сводка по зонам и что осталось без вердикта
node scripts/ui-v4-check-contract-drift.mjs --list

# проверить, не менял ли дизайнер строки под уже поставленными вердиктами
node scripts/ui-v4-check-contract-drift.mjs --zone tab-activity

# поставить вердикт одной строке
node scripts/ui-v4-set-verdict.mjs tab-activity "вид · шаги" "=" "факт: где это в коде"

# пересчитать отпечатки после разбора изменившихся строк
node scripts/ui-v4-check-contract-drift.mjs --rehash tab-activity
```

`--rehash` пишет только файл названной зоны. Читать все зоны разом умеет
`scripts/lib/ui-v4-verdicts.mjs` — путь знает только он, чтобы следующая
перекладка снова не разошлась по двум десяткам мест.

## Что внутри файла

| поле           | что значит                                                 |
| -------------- | ---------------------------------------------------------- |
| `canvas`       | имя файла канваса                                          |
| `contractOnly` | брать только блок `[data-contract]` или все строки `.spec` |
| `recorded`     | дата, когда отпечатки снимались                            |
| `rows`         | ключ строки → `{ v, f, h }`                                |

`v` — вердикт: `=` совпало · `≠` код делает иначе, причина в `f` · `?` никто не
смотрел · `—` строка не про код. `f` — факт: где это в коде или почему иначе.
`h` — отпечаток значения строки на момент разбора; по нему гейт понимает, что
дизайнер переписал строку под уже поставленным вердиктом.

## Что снимок не проверяет: ссылка стареет молча

Обоснование обычно называет место в коде —
`heys-components.css:6274-6286 .heys-update-modal__icon`. Дрейф-гейт сторожит
**строку контракта**, а за ссылкой не следит: файл продукта растёт, строки
уезжают, а число в обосновании остаётся прежним.

Проверка «номер строки в пределах файла» это не ловит — файлы длинные, любое
число попадает внутрь. Ловит только «названное имя действительно лежит по этой
строке». Замер 31 августа по двум зонам:

| зона         | пар «строка + имя» | устарело |
| ------------ | ------------------ | -------- |
| `pwa-update` | 21                 | 14       |
| `undo-bar`   | 1                  | 1        |

Все четырнадцать — в `heys-components.css`, сдвиг ровно +159: снимок сделан 24
августа, после этого в файл писали трижды. Существо вердиктов при этом уцелело
целиком — круг 56 радиусом 999 заливкой `--v4-hero`, глиф без своей заливки, —
гнилые только указатели. Это не ложный вердикт, а вердикт, который через месяц
нельзя перепроверить по его же ссылке.

Чинить правкой чисел бессмысленно: они устареют снова к следующему коммиту в тот
же файл. Нужно, чтобы проверка роняла ссылку, которая больше не показывает на
своё имя, — тогда старение видно сразу и правится вместе с кодом, который его
вызвал. Гейта пока нет; при разборе чужой зоны ссылки стоит перепроверять
отдельно от вердиктов.
