# Контракт акцепта на лендинге — протокол реализации 2026-07-31

> **Что это:** разбор и закрытие decision-gate `22` п. 3.14 (`PurchaseModal` /
> legal v1.9). Живой статус задачи ведёт
> [`маркетинг/22`](../../маркетинг/22_План_реализации_маркетинга.md) — этот файл
> хранит основания решения и evidence, а не статус.

## Решение владельца (2026-07-31)

1. **Контракт акцепта:** покупка с лендинга — это **заявка, а не акцепт
   оферты**. `PurchaseModal` собирает только согласие на обработку ПДн; акцепт
   `user_agreement` / `payment_oferta` остаётся в приложении, после входа.
   Отклонены: фиксация акцепта на лендинге (потребовала бы правки оферты, Leads
   API и схемы БД) и полный отказ от прямой покупки (продуктовое изменение
   воронки).
2. **Два текста оферты:** страница лендинга и canonical markdown остаются
   раздельными, но получают автоматическую проверку структурного совпадения.
   Пословное выравнивание вынесено в отдельный legal-проход.

## Что изменено

- `apps/landing/src/components/modals/PurchaseModal.tsx` — убран
  `user_agreement_version` из payload; текст чекбокса приведён к контракту
  `TrialForm` («согласие относится только к заявке и обратной связи по ней»), а
  ссылка на оферту подписана как «Условия использования принимаются при входе в
  приложение». Legal-тексты, Leads API и схема БД не менялись.
- `scripts/verify-legal-release.mjs` — добавлена
  `verifyLandingUserAgreementStructure()`: сверяет состав разделов и набор
  номеров пунктов страницы `/legal/user-agreement` с canonical markdown.

## Про два текста оферты

Страница лендинга — самостоятельный JSX (488 строк), canonical и immutable
snapshot — markdown (325 строк). До 2026-07-31 их не сравнивал никто: verifier
проверял только canonical ↔ snapshot ↔ manifest ↔ registry.

Замер 2026-07-31: **структура совпадает полностью** — 13 разделов и 37 номеров
пунктов в обоих текстах. Расхождения найдены в 11 пунктах и по результатам
ручной проверки (7.3, 10.2, 11.2) являются **редакционными, не смысловыми**: JSX
— перефразировка canonical. Отдельно замечено, что в п. 11.2 JSX теряет
уточнение canonical «до применения соответствующего изменения».

Поэтому включена проверка структурного уровня: она защищает от появления,
исчезновения или переименования разделов и пунктов и работает сразу, без правки
legal-текста. Пословная сверка сознательно не включена — она упала бы на этих 11
пунктах, а их выравнивание требует отдельного legal-решения по каждому.

## Проверки

- `node scripts/verify-legal-release.mjs` → exit 0,
  `landing user agreement structure: 13 sections, 37 clauses`.
- Негативный тест: переименование раздела 12 в JSX → verifier падает с
  `sections drifted from canonical markdown`; после отката снова exit 0.
- TSX парсится без синтаксических ошибок (TypeScript compiler API).

   canonical markdown.
2. **Статус `22` п. 3.14** обновляет владелец плана: этот проход снимает
   техническое основание gate, но статусы живут только в `22`.
