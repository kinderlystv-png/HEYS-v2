## 2. Туры

### Тур 1 — SQL-инъекция в REST-фильтрах (SEC-029) + чистка ID (SEC-028)

**Проблема.** Имя колонки в фильтре берётся из ключа query-параметра и
подставляется в SQL без валидации:
`conditions.push(\`"${fieldName}" = $${i++}\`)`. Кавычка в имени не экранируется. В ветке `is.`
плейсхолдер вообще не добавляется, поэтому инъекция не ломает нумерацию
параметров.

**Что меняется.** Валидация имени колонки по образцу уже существующего
`sanitizeSelectColumns`: regex + whitelist `ALLOWED_COLUMNS[table]`, невалидное
имя → 400, до обращения к БД.

**Почему решение достаточно простое.** Механизм в файле уже есть и проверен на
SELECT-пути; тут он применяется ко второму месту, где его не хватало.
Отклонённая альтернатива — построитель запросов/ORM: несоразмерно объёму и
переписывает работающий роутинг.

**Критерий готовности.** Контрактный тест: инъекционное имя колонки → 400,
легальный фильтр → работает; в собранном SQL нет посторонних кавычек.

**Статус: ✅ закрыт.**

- `sanitizeFilterColumn()` —
  [heys-api-rest/index.js:467](../../yandex-cloud-functions/heys-api-rest/index.js#L467);
  сначала regex `^[a-zA-Z_][a-zA-Z0-9_]*$`, затем whitelist
  `ALLOWED_COLUMNS[table]`.
- Проверка стоит **в начале цикла** разбора параметров, а не в каждой из 19
  ветвей: имя колонки в любой ветви берётся либо из `key`, либо из `key` без
  операторного префикса, и оба варианта проверяются одним местом. Новая ветвь не
  сможет появиться в обход. Точки применения: GET (:918), PATCH (:1778), DELETE
  (:1846). Невалидная колонка → 400 `invalid_filter_column`.
- Дополнительно закрыт **POST**, которого не было в исходной находке: имена
  колонок там приходят из ключей JSON-тела, а `on_conflict` — из query, и оба
  подставлялись как идентификаторы (:1638). Сюда доходят только
  `shared_products` и `shared_products_pending` (у `client_kv_store` и
  `client_log_trace` свои ветки, у второй список колонок зашит), то есть за
  гейтом SEC-028 — но куратор не должен получать произвольный SQL под владельцем
  таблиц. → 400 `invalid_insert_column` / `invalid_on_conflict_column`.
- Служебные ключи — `NON_FILTER_PARAMS`
  ([:481](../../yandex-cloud-functions/heys-api-rest/index.js#L481)): `order`,
  `limit`, `offset`, `select`, `table`, `on_conflict`, `columns`, `upsert`.
- **Риск регрессии проверен разведкой по всем вызывающим** (apps/web,
  apps/mobile, scripts, другие cloud functions, тесты): служебных ключей ровно
  три группы, все перечислены выше; все фильтры реального трафика — колонки из
  whitelist. Колонка вне whitelist и раньше не работала (Postgres 42703 → 500),
  так что 400 не отнимает рабочих сценариев. `upsert` добавлен в список по
  итогам разведки — единственный ключ обёртки, который иначе выпадал.
- ID-коллизия: комментарий гейта переименован `SEC-025` → `SEC-028`
  ([:648](../../yandex-cloud-functions/heys-api-rest/index.js#L648)) и в шапке
  теста `rest-shared-products-write-auth.contract.test.cjs:1`.
- Evidence:
  `node --test yandex-cloud-functions/__tests__/rest-filter-column-injection.contract.test.cjs`
  → 11/11 pass; `rest-shared-products-write-auth.contract.test.cjs` → 7/7 pass.

### Тур 2 — OAuth: allowlist redirect и честная страница согласия (SEC-030)

**Проблема.** `POST /mcp/register` открыт и принимает любой https-redirect;
страница `/mcp/authorize` собирает первичные учётные данные (телефон+PIN,
email+пароль+2FA), но не показывает, куда уйдёт код, а имя приложения на ней —
строка из запроса регистрации. Плюс в согласии заявлен только «доступ к
дневнику», тогда как кураторский вход открывает управление клиентами, подписками
и лидами.

**Что меняется.**

1. Allowlist хостов redirect_uri, fail-closed, с env-переопределением.
2. На странице явно показан origin получателя и пометка, что имя приложения не
   подтверждено.
3. Текст согласия для кураторской ветки честно перечисляет объём доступа.

**Критерий готовности.** Тест: регистрация с посторонним хостом → отказ;
регистрация с разрешённым хостом → успех; в HTML страницы присутствует origin из
`redirect_uri`.

**Статус: ✅ закрыт.**

- Allowlist —
  [lib/oauth.js:56](../../yandex-cloud-functions/heys-mcp/lib/oauth.js#L56)
  (`DEFAULT_ALLOWED_REDIRECT_HOSTS`: `claude.ai`, `claude.com`, `anthropic.com`
  с поддоменами; loopback `localhost`/`127.0.0.1`/`[::1]` с любым портом — для
  Claude Code). Переопределение — `MCP_ALLOWED_REDIRECT_HOSTS` (список через
  запятую, `*.example.com` разрешает поддомены; переопределение заменяет список
  целиком). Заодно запрещён фрагмент в `redirect_uri` (OAuth 2.1).
- Проверка стоит **и** в `registerClient`, **и** повторно в
  `validateAuthorizeRequest`
  ([:141](../../yandex-cloud-functions/heys-mcp/lib/oauth.js#L141)): `client_id`
  живёт год, поэтому без второй проверки регистрации, выданные до фикса,
  работали бы до истечения TTL.
- Почему список в коде, а не в env: heys-mcp при деплое получает ровно одну
  переменную (`LOCKBOX_APP_SECRET_ID`), остальное приходит Lockbox-overlay'ем —
  проверено по `deploy-all.sh`. Env оставлен как аварийный рычаг, деплой менять
  не потребовалось.
- Origin получателя на странице —
  [lib/oauth.js:387](../../yandex-cloud-functions/heys-mcp/lib/oauth.js#L387),
  имя приложения показано отдельной строкой с пометкой, что HEYS его не
  проверяет.
- Объём кураторского доступа перечислен явно —
  [lib/oauth.js:416](../../yandex-cloud-functions/heys-mcp/lib/oauth.js#L416):
  дневники, переписка, заведение клиентов и смена PIN, подписки, заявки и лиды.
- Evidence: 7 новых проверок в `__tests__/oauth.test.cjs` (включая то, что имя
  приложения не может внести разметку), файл 22/22 pass.

**Уточнение 2026-08-04.** По решению пользователя default allowlist расширен
только точным host `chatgpt.com`, без wildcard: OpenAI использует callback
`https://chatgpt.com/connector/oauth/{callback_id}`. Тесты пропускают текущий и
legacy callback ChatGPT и отклоняют `chatgpt.com.evil.tld`; OAuth-набор 22/22.
Изменение пока только в рабочем дереве, live DCR начнёт принимать ChatGPT после
отдельно разрешённого deploy `heys-mcp`.

### Тур 3 — кураторская сессия: проверка состояния при refresh (SEC-031)

**Проблема.** На refresh-гранте функция сама подписывает новый кураторский JWT
боевым `JWT_SECRET` без единого обращения к серверу. Состояние аккаунта не
проверяется, отзыва для кураторских JWT в платформе нет, а страница согласия
обещает, что доступ отзывается отключением коннектора в Claude — это неправда.

**Что меняется.** Перед перевыпуском — серверная проверка, что куратор
существует и активен; при отказе refresh не проходит. Текст про отзыв приведён в
соответствие фактам.

**Критерий готовности.** Тест: неактивный/отсутствующий куратор → refresh падает
с `invalid_grant`; активный → перевыпуск как раньше.

**Статус: ✅ закрыт (с явно названным остатком).**

Разведка показала, что подходящего эндпоинта в платформе не было: `/auth/verify`
проверяет только подпись и `exp` и в БД не ходит вовсе, поэтому JWT удалённого
куратора там остаётся «валидным». Единственный признак деактивации в схеме —
`curators.is_active` (`database/2025-12-22_curators.sql:14`). Пришлось завести
эндпоинт.

- Новый `GET /auth/curator-status` — `handleCuratorStatus`
  ([heys-api-auth/index.js:1096](../../yandex-cloud-functions/heys-api-auth/index.js#L1096)),
  роутинг там же в `case 'curator-status'`. Требует кураторский JWT, читает
  `curators.is_active` → 200 `{active:true}` / 403 `curator_inactive` / 404
  `curator_not_found`.
- Путь добавлен в шлюз — `api-gateway-spec.yaml`, блок `/auth/curator-status`.
- Клиент — `api.curatorStatus(bearer)`
  ([lib/heys-api.js:318](../../yandex-cloud-functions/heys-mcp/lib/heys-api.js#L318)):
  всё, кроме явного 200 `{active:true}`, трактуется как отказ; сетевая ошибка
  тоже отказ.
- `exchangeRefreshToken` стал асинхронным и получает `verifyCurator`
  ([lib/oauth.js:270](../../yandex-cloud-functions/heys-mcp/lib/oauth.js#L270)):
  перевыпуск только после положительного ответа сервера, иначе `invalid_grant`.
  Проверка идёт **под свежевыпущенным** JWT — прежний к моменту продления обычно
  уже мёртв (24 часа против 30 суток у refresh-токена).
- `client_id` в refresh-гранте стал обязательным: раньше проверка стояла под
  `if (form.client_id)` и обходилась простым отсутствием параметра.
- Изменение поведения: refresh без `rawJwtSecret` теперь отказ, а не «протащить
  прежний JWT». Прежнее поведение выдавало валидную с виду пару токенов с
  заведомо мёртвой сессией внутри.
- Клиентская ветка не тронута: там в токене серверная сессия, её гасит
  `revoke_session`.
- Текст страницы про отзыв переписан
  ([lib/oauth.js:421](../../yandex-cloud-functions/heys-mcp/lib/oauth.js#L421)):
  клиенту — про выход из аккаунта, куратору — прямо сказано, что мгновенного
  отзыва нет и доступ действует до суток.
- Комментарии-шапки `crypto-tokens.js:10` и `oauth.js:10` больше не утверждают,
  что kill switch работает для обеих ролей.
- Evidence: 5 новых проверок в `__tests__/curator.test.cjs` + 1 в
  `oauth.test.cjs`; наборы 229/229 (MCP) и 83/83 (корневой) зелёные.
- **Порядок деплоя важен:** сначала `heys-api-auth` и шлюз, только потом
  `heys-mcp`. Обратный порядок = проверка бьётся в 404, fail-closed отказывает
  во всех кураторских refresh, и кураторам придётся войти заново.
- **Остаток (назван, не закрыт):** мгновенного отзыва уже выданного кураторского
  JWT по-прежнему нет — окно до 24 часов. Для него нужен `token_version` в
  токене и сверка во всех функциях платформы; заведено в `todo.md` отдельной
  задачей.

### Тур 4 — ownership при записи в `shared_products_pending` (SEC-032)

**Проблема.** Гейт SEC-028 проверяет роль `curator`, но не владение строкой.
Куратор A может изменить или удалить заявку куратора B.

**Что меняется.** Для `shared_products_pending` на PATCH/DELETE сервер сам
добавляет условие `curator_id = <sub из JWT>`.

**Критерий готовности.** Тест: PATCH с чужим `curator_id` в фильтре → отказ;
свой — проходит; в SQL всегда присутствует условие по `curator_id`.

**Статус: ✅ закрыт.**

- Гейт —
  [heys-api-rest/index.js:698](../../yandex-cloud-functions/heys-api-rest/index.js#L698):
  чужой `curator_id`, явно переданный в фильтре, → 403
  `cross_curator_forbidden`.
- Одной этой проверки мало, и это главное в правке: запрос **без** фильтра по
  `curator_id` (только по `id` заявки) иначе дотянулся бы до чужой строки.
  Поэтому сервер сам дописывает условие `"curator_id" = $n` в WHERE — PATCH
  (:1836) и DELETE (:1888).
- `shared_products` под правило не попадает намеренно: это общий каталог,
  колонки `curator_id` у него нет вовсе.
- Разведка подтвердила семантику и отсутствие регрессии: `curator_id` в
  `shared_products_pending` — куратор клиента-автора, то есть «чья очередь»
  (`database/2025-12-16_shared_products_pending.sql:18`), фактический модератор
  пишется отдельно в `moderated_by`. Общей очереди и супер-модератора нет.
  REST-write в эту таблицу вообще не делает ни один штатный вызывающий — вся
  модерация идёт через RPC, где ownership уже проверяется. Правка закрывает
  ровно прямой curl под валидным кураторским JWT.
- Evidence: 6 проверок в `__tests__/rest-pending-ownership.contract.test.cjs`,
  6/6 pass.

## 2а. Порядок деплоя — жёсткое ограничение

SEC-031 связал две функции: `heys-mcp` на refresh-гранте ходит в новый
`GET /auth/curator-status`, который живёт в `heys-api-auth` и в спеке шлюза.
Проверка fail-closed, 404 = отказ.

**Обязательный порядок:**

1. `heys-api-auth` + `api-gateway-spec.yaml`
2. только после этого `heys-mcp`

Обратный порядок = все кураторские refresh отказывают, коннектор перестаёт
продлевать сессию, кураторы проходят OAuth заново.

**Состояние прода на 2026-08-02** (подтверждено параллельной сессией, которая
эту функцию деплоила): `heys-mcp` — версия `d4ee37sd8d6o44ohveei` из коммита
`64a0bf483` (2026-08-01T23:04Z), то есть **без** зависимости от
`/auth/curator-status` и без правок SEC-030/031. Прод в рабочем состоянии,
refresh там идёт по-старому. Сломать его может ровно один сценарий: деплой
`heys-mcp` из текущего рабочего дерева раньше `heys-api-auth`.

**Договорённость между сессиями (2026-08-02):** параллельная сессия («MCP
куратора: функции для управления клиентами») заморозила деплой `heys-mcp` со
своей стороны до выката auth и спеки. Обе сессии деплой не выполняют — решение и
команда за владельцем.
