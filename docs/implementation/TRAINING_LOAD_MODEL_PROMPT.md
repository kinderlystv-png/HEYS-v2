# Модель нагрузки: оценка тренировки, тренированность, восстановление

Статус на 2026-08-08: этапы 1–3 сделаны, этап 4 частично (часть сознательно
отменена, см. ниже), этап 5 не понадобился.

## Цель

Система сама оценивает каждую тренировку и держит производные величины —
накопленную тренированность и текущую усталость/готовность, — чтобы рекомендации
опирались на них. Числа считаются НАШИМ алгоритмом из наших данных; ничего от
сторонних трекеров не импортируется.

## Ключевой инвариант

**Производные величины не хранить — считать на чтении.** Тренированность зависит
от всей истории (добавление тренировки меняет её и для последующих дней),
готовность — от текущего времени. Замороженное значение устаревает молча: это
ровно баг `savedDisplayOptimum` из
[BUGS_HISTORY.md](../../apps/web/BUGS_HISTORY.md). Хранится только сырьё.

## Что уже было в проекте (проверено по коду)

- Объект тренировки богатый: `z`, `time`, `type`, `activityLabel`, `source`,
  `mood`, `wellbeing`, `stress`, `comment`, `strengthEntryMode`, `workoutLog`.
- Силовой конструктор с тоннажем работает
  ([heys_day_trainings_v1.js](../../apps/web/heys_day_trainings_v1.js)).
- Readiness в двух доменах; в ядре `TK.stats`, `TK.periodization`, `TK.assess`.
- NDTE моделирует «вчерашняя тренировка → сегодняшний расход».
- Модели накопленной нагрузки (TRIMP / CTL-ATL) не было вовсе.

## Этап 1 — MCP перестаёт терять данные тренировки ✅

`addTraining` и `heys_log_training` принимают `time`, `type`, `activity_label`,
`mood`, `wellbeing`, `stress`, `comment`; `source: 'curator_mcp'` проставляется
сервером. `summarizeDay` отдаёт эти поля и больше не теряет силовые с
`workoutLog` при `z=[0,0,0,0]` — раньше такая тренировка не показывалась вовсе.

## Этап 2 — тоннаж в чистом ядре ✅

[\_kernel/heys_kernel_strength_v1.js](../../apps/web/_kernel/heys_kernel_strength_v1.js):
`trainingTonnage`, `dayTonnage`, `countStrengthWorkouts` — чистые функции от
блоба. Раньше формула читала localStorage напрямую и была недоступна ни ядру, ни
серверу. `heys_day_trainings_v1.js` делегирует сюда.

Не вынесено сознательно: `findPrevDayTonnage` и поиск исторического рекорда по
имени упражнения — оба сканируют неограниченную историю.

## Этап 3 — модель нагрузки в ядре ✅

[\_kernel/heys_kernel_load_v1.js](../../apps/web/_kernel/heys_kernel_load_v1.js):

- `sessionLoad(training, zoneMets)` — MET-минуты, вес зоны из `hr_zones`
  клиента, не из новой константы.
- `fitnessFatigue(dailyLoads, opts)` — импульс-реакция Банистера, CTL/ATL/TSB, τ
  42/7 дней, деградация `confidence` на короткой истории.

Кардио и силовая считаются **раздельными рядами**: единого физиологического
коэффициента «кг тоннажа = MET-минуты» не существует, и выдумывать его нельзя.
Общим знаменателем мог бы стать session-RPE, но он нигде не собирается.

## Этап 4 — потребители ⚠️ частично, часть отменена

**Сделано:** `heys_get_training_status` отдаёт тренированность/усталость/
готовность по 42-дневному окну (`LOAD_WINDOW_DAYS`). Окно шире `MAX_PERIOD_DAYS`
(31) сознательно: `readMany` уходит одним RPC `batch_get_client_kv_by_session`,
поэтому окно стоит объёма ответа, а не round-trip'ов; прецедент — тот же
обработчик уже читал 30 дней. `heys_log_training` отдаёт нагрузку сессии сразу,
без чтения истории.

**ОТМЕНЕНО: перевод доменных readiness на `TK.load`.** Исходная формулировка
(«оба доменных readiness смотрят на вчерашнюю нагрузку кустарно») оказалась
фактически неверной:

- `mobility/heys_mobility_readiness_v1.js` **не смотрит на нагрузку вообще**:
  только скованность, болезненность, качество сна, стресс, HRV z-score.
- `fingers/heys_fingers_readiness_v1.js` использует не нагрузку, а
  **категориальную интенсивность фингерборда** (`lastIntensity`) с правилом 48
  часов на восстановление сухожилий.

Подменять это MET-минутами кардио опасно: максимальный вис — единицы MET-минут
при предельной нагрузке на сухожилия. `TK.load` сказал бы «лёгкий день», гейт
разрешил бы max-протокол. Это регрессия с риском травмы.

Правильная интеграция аддитивная и уже сделана в другом месте: модель питает
общие рекомендации по дневнику, доменные гейты остаются на доменных сигналах.

## Этап 5 — чекпойнт-кэш ❌ не понадобился

Опасение «42 чтения на запрос» не подтвердилось: `readMany` — один RPC с
массивом ключей
([heys-api.js:231](../../yandex-cloud-functions/heys-mcp/lib/heys-api.js)). Окно
читается только в `heys_get_training_status` (инструмент по требованию), не в
`heys_get_day`. Кэш производного значения не заводился принципиально.

## Дополнительно: правка записанной тренировки ✅

`heys_update_training` — дописать оценки/время/тип/комментарий или заменить зоны
у уже записанной тренировки. Раньше коннектор умел только добавлять, и история
без оценок оставалась без них навсегда. `index` — позиция в блобе, отдаётся в
`summarizeDay` (считается до фильтра заготовок).

## Аудит 2026-08-08 и правки по нему ✅

Независимый аудит нашёл четыре сценария потери данных и три дефекта, из-за
которых куратор видел неверные числа. Все исправлены, подробности и причины — в
[BUGS_HISTORY.md](../../apps/web/BUGS_HISTORY.md). Коротко:

| Что                                      | Как чинили                                         |
| ---------------------------------------- | -------------------------------------------------- |
| Удаление гасило соседнюю тренировку      | уникальный `id` + passthrough в модели приложения  |
| Четвёртая тренировка терялась            | список не обрезается, запись сверх трёх отбивается |
| Позиционный merge терял сдвинутые строки | удаление поднимает штамп всем оставшимся           |
| Блоб на 25 МБ                            | потолки на упражнения, подходы, длины, минуты      |
| Готовность всегда в минусе               | ряд стартует со среднего по окну                   |
| Уверенность всегда одна и та же          | считаются дни с реальными данными                  |
| MET-фолбэк завышал в 3.2 раза            | дефолт своей зоны, а не последней                  |

Каждая находка закрыта регресс-тестом: 979 в коннекторе, 24 в ядре.

## Что осталось открытым

- **Шкала не откалибрована.** На реальной истории (7 тренировок за 42 дня)
  модель даёт CTL 71, ATL 250, TSB −178 MET-мин/д. Направление верное (три
  тренировки подряд → накопленная усталость), но абсолютные числа не сопоставимы
  ни с чем: пороги вроде «TSB ниже −30 = переутомление» взяты из TSS-шкалы и
  здесь неприменимы. До калибровки показывать сырые числа клиенту нельзя —
  только динамику. Макет силового конструктора («Сборка экранов», экран 08)
  рисует нормализованную шкалу — тренированность 58, усталость 71, готовность
  −13 — и уверенность по 14 дням, а не по 42. Ориентир для калибровки есть,
  решение по нему не принято.
- **UI-гейт не проходился.** По `Product UI invariants` всё, что меняет
  рекомендацию, обязано быть видно; сейчас числа доступны только куратору через
  MCP. Клиентский UI не проектировался.
- **RPE есть у силовых, нет у кардио.** Поле `rpe` на упражнении конструктора
  принимает и коннектор. Общим знаменателем `RPE × длительность` он станет,
  когда появится и у кардио-тренировок.
- **План от куратора.** В макете есть («Начать по плану · День В, назначил
  Артём»), в коде нет ни схемы, ни читателя. Запись через MCP имеет смысл
  проектировать вместе с реализацией макета — иначе получится структура, которую
  никто не покажет.
