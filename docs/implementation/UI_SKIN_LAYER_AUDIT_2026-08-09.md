# Аудит слоя оформления: возможен ли сменный скин («Мягкий») — 2026-08-09

**Статус:** аудит + рекомендация агента. **Решения владельца нет.** Запрос: дать
клиенту переключатель стиля («как сейчас» / «Мягкий»), который перерисовывает
визуал **без изменения структуры и логики**.

## 2. Главный вывод

**Слоя, через который можно «просто перерисовать», сейчас нет.**

- Токен-слой существует (`001-design-tokens.css`, v1.0.0 от 2025-12-10), но
  фактически мёртв: ~640 использований против ~18 500 хардкодов — покрытие
  порядка 3–5 %.
- Тёмная тема уже реализована **самым дорогим способом** — дублированием 3 796
  правил `[data-theme="dark"] .x`, а не подменой значений токенов. Если «Мягкий»
  сделать так же, получится 4 комбинации (тема × скин) и четырёхкратная
  стоимость любой будущей правки UI.
- 1 782 цвета зашиты в inline `style` в JS — **CSS-скин до них не достаёт**
  вообще, никаким селектором.

Смягчающий фактор: React прокидывает значение `style` как есть, поэтому
`style: { color: 'var(--heys-success)' }` работает. Миграция инлайнов — замена
литералов, а не переписывание компонентов в классы.

## 3. Рекомендуемая архитектура (рекомендация агента)

1. **Один канал: `html[data-skin]` × `html[data-theme]`.** Атрибут ставится в
   уже существующем boot-слое
   [`heys_boot_theme_v1.js`](../../apps/web/heys_boot_theme_v1.js) до первого
   пейнта (там же уже есть прецедент — класс `board-dark-nav`). Новых механизмов
   не заводить.
2. **Токены — единственный источник цвета/шрифта/радиуса/тени/плотности.** Скин
   = один файл, который переопределяет **значения** токенов под
   `[data-skin="soft"]`. Если файл скина трогает селекторы компонентов — это
   нарушение контракта.
3. **Тёмная тема мигрирует в те же токены**, иначе комбинаторный взрыв.
4. **Инлайн-цвета JS → `var(--heys-*)`.** Механическая замена по словарю 290 →
   ~30. Исключение: цвета, вычисляемые из значения (градиенты, интерполяция) —
   их прячем в хелпер, а не размазываем.
5. **Гейт от расползания:** линтер «новых hex/rgba в JS `style` и в CSS вне
   tokens-файлов быть не должно» — по образцу уже существующих
   `scripts/lint-*.mjs`.
6. **Граница скина.** Токенами решаются: палитра, типографика, радиусы, тени,
   плотность. Модификаторами `[data-skin="soft"] .card {…}` — «плашки вместо
   рамок», «цифра-герой». Скину **запрещено** менять DOM, порядок узлов и
   логику.
7. **«Часть значений не показывать» — это не скин.** Отдельная независимая ось
   `detail: full | compact`, декларативным списком. «Мягкий» тогда — пресет
   (`skin=soft` + `detail=compact`), а не ветка в компонентах.
8. **Хранение выбора — поле профиля** (как `profile.defaultTab`), per-client,
   синкается в облако; boot читает из `heys_<cid>_profile`. Отдельный LS-ключ
   вне профиля не заводить — рассинхрон между устройствами.

## 4. Риск прототипа

Прототип «Мягкий» развивается как самостоятельный HTML-файл. Если его разметка
разойдётся с реальным DOM приложения, перенос перестанет быть скином и станет
переписыванием экранов. Прототип нужно трактовать как **спецификацию токенов и
модификаторов**, а не как исходник разметки.

## 5. Предлагаемый первый шаг

Не мигрировать 125 k строк вслепую. Пилот на **одном экране** (Главная/День)
через весь путь: словарь токенов → замена инлайнов на этом экране → файл скина →
замер. Пилот даёт реальную цену за экран и проверяет главную гипотезу — что скин
действительно не требует лезть в логику.

Отклонённый вариант: отдельный набор компонентов под «Мягкий» — двойная
поддержка живого продукта, при текущих ресурсах неприемлемо.

## 6. Решения (2026-08-09)

Решения владельца:

- **Переключатель виден всем** — платных клиентов ещё нет, скрытый флаг не
  нужен.
- **Scope v1 — только клиентские экраны:** Главная (`widgets`), Питание
  (`diary`), Актив (`activity`), Отчёты (`stats`), Инсайты (`insights`) +
  профиль. Источник: `heys_app_shell_v1.js:4143`.
- **Fingers не трогаем.** Курaторские экраны и planning-игры — тоже вне v1.
- **«Мягкий» — третья тема, а не ось поверх light/dark.** Одна ось:
  `data-theme = light | soft | dark`. Мягкий заменяет светлую, тёмная остаётся
  как есть; soft-dark не рисуется и не поддерживается. Раздел 3 п. 1–2
  скорректирован: отдельный атрибут `data-skin` не вводится. Отменяет прежнюю
  рекомендацию агента «требовать два набора значений».
- **Два потока работы разделены** (предложение дизайнера, принято):
  - **A — перекраска.** Ноль изменений DOM: цвет, радиусы, тени, плотность,
    типографика, «плашки вместо рамок». Проходит через токены и модификаторы.
  - **B — структура.** Навигация 7→5 вкладок, шапка из двух полос в одну, 4
    плавающие кнопки в одну, порядок блоков. Отдельные задачи, к теме отношения
    не имеют. Прототип «Мягкий» содержит и A, и B — при переносе их обязательно
    разделять.
- **Пилот — вкладка Актив, не Главная.** Аргумент дизайнера (все типовые
  сущности разом: карточки, прогресс, календарь-сетка, таблица расчёта)
  подтверждён замером: Актив ≈ 5 570 строк / 102 инлайн-цвета
  (`heys_steps_v1.js` + `heys_day_activity*.js` + `heys_day_steps_ui.js`) против
  Главной ≈ 10 730 / 157 и Питания 12 013 / 210.

Технические следствия одной оси: атрибут уже существует, boot-слой
[`heys_boot_theme_v1.js`](../../apps/web/heys_boot_theme_v1.js) достаточно
расширить третьим значением; правила `[data-theme="dark"]` к `soft` не
применяются автоматически. Но базовые (светлые) правила к `soft` применяются как
основа — значит миграция хардкодов в токены остаётся обязательной, одна ось её
не отменяет.

### Открытый вопрос: семантика цвета (светофор)

Предложение дизайнера — отменить шестизонный светофор (срыв / маловато / хорошо
/ идеально / переел / срыв) в пользу двух состояний: «в норме» (шалфей) и
«требует внимания» (терракота), остальное нейтраль. Статус: **предложение,
решения владельца нет.**

Проверка кода уточняет цену вопроса:

- Светофор **уже централизован** — `DEFAULT_RATIO_ZONES` в
  [`heys_ratio_zones_v1.js`](../../apps/web/heys_ratio_zones_v1.js) (6 зон,
  цвета в одном массиве, настраиваются через LS-ключ `heys_ratio_zones`).
- Но ходят через него **только два файла** (`heys_day_stats_vm_v1.js`,
  `heys_user_tab_impl_v1.js`); остальные ~310 `#22c55e` и ~250 `#ef4444` —
  самостоятельные литералы.

Отсюда поправка к аргументу дизайнера: решение можно **не принимать авансом**.
Точка подмены существует, и правильный ход миграции — сводить цветовые решения к
ней, а не к новым литералам. Тогда «6 зон или 2» — правка одного файла,
обратимая. Экономия от раннего решения реальна, но она в **числе решений** («это
good или perfect?» отпадает), а не в числе правок: точек замены в Активе те же
~100. Оценка «пилот вдвое дешевле» завышена.

## 6a. Уточнения после тёмного макета (2026-08-09, вечер)

**Факт кода: клиентское меню уже состоит из 5 вкладок.** `primaryTabs` в
[`heys_app_shell_v1.js:4352`](../../apps/web/heys_app_shell_v1.js) даёт всегда:
Отчёты, Питание, Актив, Виджеты, Инсайты. «Задачи» добавляются только
PIN-клиенту (`!cloudUser && clientId`), «Доска» — только board-клиенту
(владелец). Следствие: заявленное дизайнером «7 вкладок → 5» **для обычного
клиента не является изменением структуры** — это перекраска (поток A). В потоке
B остаётся только мелочь: переименование `Виджеты → Главная` и её перенос на
первую позицию (порядок элементов массива + label).

**Переоценка стоимости тёмного «Мягкого».** Прежний аргумент («soft-dark = +3
796 правил») исходил из нынешнего способа темизации дублированием правил.
Дизайнер собрал тёмный вариант на уровне значений, а не правил — в целевой
токен-архитектуре это ещё одна колонка значений. Прежняя рекомендация «тёмный
Мягкий не нужен» **снимается как основанная на завышенной оценке.** Новая
рекомендация агента: тёмный Мягкий принять, но **после** того как светлый доедет
до кода, иначе пилот раздувается.

**Модель тем при четырёх вариантах — по-прежнему одна ось:**
`data-theme = light | dark | soft | soft-dark`, где каждое значение — свой набор
значений токенов. Двух перемножающихся осей не вводить; в UI можно показывать
две настройки, но маппить их в одно значение атрибута.

**Главная как хаб** (вход в разделы, которых нет в меню — Задачи, Доска,
Продукты) — поток B, отдельная задача. Обоснование: сейчас у владельца 7 вкладок
и вариант вёрстки `sext`; хаб снимает давление на меню, не дублируя навигацию.
Требует решения владельца, не входит в v1 перекраски.

## 6c. Дыры словаря, найденные сверкой с кодом Актива

1. **Шкала не одна, их минимум шесть.** Маппинг «6 зон → 2 смысла» покрывает
   только ratio калорий. В Активе независимо живут: цель шагов
   (`heys_steps_v1.js:1962`, три уровня), дефицит/профицит (`:2115`),
   `getColdPositiveColor` (`:3375`, четыре уровня), `getColdNegativeColor`
   (`:3383`, четыре, инвертированные), статусы зарядки (`:748`). У шкал
   самочувствия сведение к двум смыслам стирает градацию: 3/10 и 8/10 станут
   неразличимы. **Предложение агента:** не вводить новые цвета, а разложить
   четырёхуровневые шкалы по уже данным ступеням — `--heys-norm` (сильно) /
   `--heys-norm-chip` (слабо) / `--heys-track` (нейтраль) / `--heys-accent`
   (внимание). Требуется подтверждение дизайнера.
2. **Нет токенов графиков.** В Активе есть линия веса, спарклайны и заливки
   областей; в словаре линии/области не описаны, хотя на макетах они цветные.
   Нужны как минимум «линия основная», «линия вторая», «заливка области»,
   «сетка».
3. **Совпадающие значения у разных ролей.** `--heys-accent-tint` совпадает с
   `--heys-surface-primary` (`#efe3cf`), `--heys-norm-tint` — с
   `--heys-surface-norm` (`#eaefe0`). Держим раздельно; нужно подтверждение, что
   при будущей правке тинта плашка меняться **не** должна.

## 6d. Поправка к оценке пилота и смена единицы работы (2026-08-09)

**Ошибка в разделе 6.** Оценка «Актив ≈ 5 570 строк / 102 цвета» посчитана по
`heys_steps_v1.js`, а это не экран вкладки, а набор шаговых модалок чек-ина
(вес, сон, цель шагов, замеры, настроение, закаливание, добавки). Цифра
недействительна; вывод «Актив вдвое меньше Питания» ею не подтверждается.

**Факт: Отчёты, Питание и Актив — один компонент, не три.**
`heys_day_tab_impl_v1.js:541-544` разделяет их флагами `showStatsContent` /
`showActivityContent` / `showWaterContent`; блок Актива — `:2314-2353`.
Семейство DayTab (`heys_day_tab_impl_v1` + `heys_day_bundle_v1` +
`heys_day_core_bundle_v1` + `heys_day_meals_bundle_v1` + `heys_day_stats_vm_v1`)
≈ 38 300 строк и ~657 инлайн-цветов на три вкладки.

Следствие: **единица работы — не «вкладка», а «День» (три подвкладки), плюс
отдельно Главная и Инсайты.** Правка общей карточки в Активе неизбежно видна в
Питании и Отчётах. Актив остаётся первым — он наименьший по контенту из трёх и
не задевает каталог продуктов — но соседние подвкладки проверяются в том же
заходе.

## 6e. Расширение задачи: перекраска + упрощение структуры

Владелец (2026-08-09): раз оболочка всё равно меняется, вместе с ней навести
порядок в структуре — переставить карточки, убрать перегруженность,
согласовывать повкладочно вместе с дизайнером. Идея принята; двойной перенос
экрана (сначала в тему, потом при перестановке) — реальная потеря.

Два ограничения, без которых расширение опасно (рекомендация агента, требует
подтверждения владельца):

1. **Перестановка блоков не может жить внутри темы.** Разный порядок блоков в
   Мягком и Классическом = две разметки, и каждая следующая фича делается
   дважды. Значит структурные решения применяются **к обеим темам сразу**:
   Классический получает новый порядок со старой краской. Это уже редизайн
   продукта, идущий рядом с темой, а не «эксперимент внутри Мягкого».
2. **У всего убранного должен быть назван новый адрес.** «Убрали кнопки советов
   и настроек — стало спокойнее» верно визуально, но функции остались. По
   каждому убранному элементу: переехал (куда) / во второй слой (в какой) /
   удалён осознанно (почему). Иначе это не упрощение, а потеря функции.
   Согласуется с правилом progressive disclosure в `CLAUDE.md`.

### Адреса убранного — проверка по коду

- **Фиолетовая кнопка «минус» — это оценка голода и энергии**
  (`heys_day_page_shell.js:70-87`, класс `hunger-energy-fab`, в бандле `.n`,
  градиент `#74639a → #5a4e80`). Иконка — круг с горизонтальной чертой, из-за
  чего читается как «убавить». То, что функцию не опознали по виду, —
  самостоятельный аргумент за смену иконки, а не только за перенос.
- **«Настройки → тап по имени клиента» уже реализовано.** Дропдаун аккаунта
  (`heys_app_shell_v1.js:3375-3418`) содержит «⚙️ Настройки — Профиль и цели» и
  «🚪 Выйти». Адрес существует, новый узел не нужен.
- **Правило проверки B-решений** (предложение дизайнера, принято): каждое
  структурное решение обязано быть понятнее и на текущей краске. Если
  перестановка убедительна только в Мягком — это обаяние палитры, а не
  структура, и решение отклоняется.

### Повкладочный цикл

1. **Инвентарь из кода** — список того, что реально на экране, включая редко
   показываемое. Готовит разработка.
2. **Раскладка текстом:** остаётся / переезжает (куда) / во второй слой /
   удаляется (почему). Согласуется **до** макета — иначе решение принимается по
   картинке, и «уже красиво нарисовано» становится аргументом.
3. **Макет** по согласованной раскладке.
4. **Перенос:** структура — в обе темы, краска — в Мягкий.
5. **Проверка в живом приложении**, включая соседние подвкладки Дня. Затем
   следующая единица.

## 6g-2. Формула цели дня — против макета a2 (2026-08-09)

Источники: `heys_day_caloric_display_state.js:18-29`,
`heys_day_energy_context_v1.js:15-34`, `heys_day_core_bundle_v1.js:1885`.

```
Затраты (tdee)   = BMR + шаги + быт + тренировки + буст вчерашней тренировки + TEF
Базовая цель     = tdee × (1 + дефицит% / 100)
Показанная цель  = одна из четырёх ВЗАИМОИСКЛЮЧАЮЩИХ веток:
                     refeed-день      → Refeed.getRefeedOptimum(...)  — заменяет всё
                     иначе долг > 0   → базовая + dailyBoost
                     иначе снижение>0 → базовая − dailyReduction
                     иначе            → базовая
```

**Макет a2 неверен по существу.** В нём цель 2260 объясняется тремя причинами
сразу — загрузка +35 %, долг 1435 ккал, буст вчерашней тренировки +90 ккал. В
коде это невозможно:

1. Refeed (загрузка) **исключает** долг — ветки взаимоисключающие, вместе они не
   встречаются никогда.
2. Буст вчерашней тренировки **не является слагаемым цели** — он входит в
   `tdee`, то есть уже сидит внутри строки «Затраты 2145».
3. Значит причин уровня цели одновременно бывает **максимум одна**, плюс
   дефицит/профицит. Правило «максимум три причины, дальше ещё N» описывает
   состояние, которого не существует.
4. Пропущена четвёртая ветка — **снижение цели** (`dailyReduction`, день, когда
   компенсация уменьшает цель). Её в макете нет вовсе.

Следствие для раскладки: ярус «Сегодня» должен уметь показать одну причину
уровня цели и отдельно — разбивку затрат, внутри которой живёт буст. Это проще,
чем нарисовано, но требует другой группировки: причина цели и слагаемые затрат —
разные уровни, а не общий список.

### Эталонный пример четырёх веток

Refeed считается как `Math.round(базовая цель × 1.35)`
(`REFEED_BOOST_PCT = 0.35`, `heys_refeed_v1.js:11,157`) — умножается **цель**, а
не затраты, и базовая цель **уже включает дефицит**.

При затратах 2145 и дефиците 10 % (`Math.round(2145 × 0.9) = 1931`):

| Ветка          | Цель | Строка-причина                |
| -------------- | ---- | ----------------------------- |
| обычный день   | 1931 | нет, только свёрнутые затраты |
| долг +478      | 2409 | компенсация долга             |
| снижение −185  | 1746 | снижение по плану             |
| загрузка ×1.35 | 2607 | день загрузки                 |

Формулировка «в refeed-ветке дефицита нет» неточна: дефицит применён внутри
базовой цели, просто результат умножен на 1.35. Прятать строку дефицита в этот
день можно, но по причине «перекрыт загрузкой», а не «отсутствует».

## 7. Бриф дизайнеру (v2, 2026-08-09)

Технический контекст: «Мягкий» — третья тема приложения. В коде это одно
значение атрибута темы, меняющее набор переменных оформления. Отсюда формат:

1. **Структура зафиксирована.** Экраны и порядок блоков внутри вкладки не
   меняются. Меняется, _как блок выглядит_, не _что где стоит_.
2. **Изменения структуры идут отдельным потоком.** Всё, что меняет DOM — 7
   вкладок в 5, шапка в одну строку, четыре плавающие кнопки в одну — ставится
   отдельными задачами и не смешивается с перекраской.
3. **Тёмный вариант «Мягкого» не нужен.** Мягкий заменяет светлую тему; тёмная
   остаётся текущая.
4. **Результат — не картинки, а списки:** словарь токенов (палитра трёх тонов,
   радиусы, плотность, шкала кегля); модификаторы для `.card`, `.pill`, `.nav`;
   поблочный разбор «что первично / что вторично» для оси `compact` по каждой
   вкладке. Имена переменных даёт разработка из кода.
5. **Отдельно — предложение по семантике цвета:** маппинг шести зон в два
   состояния списком, с указанием, что становится нейтралью. Это отдельное
   решение, а не часть палитры.
6. **HTML-прототип = спецификация, не исходник.** Точность значений важнее
   вылизанности файла.
7. **Первый экран — Актив** (не Главная): в нём разом карточки, прогресс,
   календарь-сетка и таблица расчёта, и он вдвое меньше Питания. Главная почти
   целиком плитки и дала бы заниженную оценку.
