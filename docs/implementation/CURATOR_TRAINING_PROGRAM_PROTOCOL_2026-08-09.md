Тариф **Pro Спорт (19 990 ₽/мес)** уже объявлен клиенту с обещанием «Программа

## Часть 2. Аудит: чего нет и что из-за этого сломается

### 2.1. Блокер: план немедленно съедает калории клиента

`setStrengthWorkout` всегда пишет ненулевые минуты зоны:
`z = [0, minutes, 0, 0]`, а без длительности — `[0, 1, 0, 0]`
([`day.js:720-724`](../../yandex-cloud-functions/heys-mcp/lib/day.js)). Дневной
расход считается по зонам первых трёх тренировок
([`heys_tdee_v1.js:160-164`](../../apps/web/heys_tdee_v1.js)).

Значит назначенная на сегодня тренировка **сразу** поднимает расход и оптимум
калорий, хотя человек ещё ничего не делал. Клиент съест лишнее за тренировку,
которой не было. Это не косметика: калорийный оптимум — центральное число
продукта.

То же и с нагрузкой: `TK.load.sessionLoad` посчитает MET-минуты плана как
состоявшуюся нагрузку.

### 2.2. Нет признака «план, а не факт»

Никакого поля. Следствия каскадом: калории (выше), тоннаж дня, накопленная
тренированность, счётчики «сколько тренировок за период», статистика куратора —
всё посчитает назначенное как выполненное.

### 2.3. Нет сущности «программа»

План выразим максимум как набор независимых дней. Нет идентичности программы, её
периода, версии, автора и статуса. Из-за этого нельзя ни показать клиенту «цикл
на 4 недели», ни ответить куратору «12 из 16 сессий выполнено», ни заменить
программу целиком.

### 2.4. Исходный план теряется при выполнении

Клиент правит ту же запись, что назначил куратор. После тренировки сравнить
«назначено против сделано» будет нечем — а это и есть услуга про-тарифа.

### 2.5. Правка куратора во время сессии затрёт зал

Слияние выбирает победителя целиком по тренировке, по «богатству» записи
([`heys_sync_merge_v1.js:937-950`](../../apps/web/heys_sync_merge_v1.js)),
проигравшая версия выбрасывается (:999-1017). Коннектор при этом намеренно
устроен так, чтобы выигрывать. Правка плана в момент, когда клиент тренируется,
может стереть уже отмеченные подходы.

### 2.6. Прочее

- **Лимит три тренировки в день** (`MAX_TRAININGS_PER_DAY`,
  [`day.js:30`](../../yandex-cloud-functions/heys-mcp/lib/day.js)). Для плана
  обычно хватает, но если хранить план и факт как две отдельные записи — лимит
  съедается вдвое. Это довод в пользу выбранной модели (см. часть 3).
- **Нет чтения статуса программы куратором.** `heys_get_day` покажет день,
  сводки по циклу нет.
- **Нет уведомления клиенту** о назначенном плане.
- **Нет гейта по тарифу**: назначение программы — функция Pro Спорт, серверной
  проверки подписки для такого действия сейчас нет.
- **Авторство на уровне подхода** отсутствует (общий пункт с редизайном
  конструктора, решение 3 того протокола).

## Часть 3. Ключевое архитектурное решение

**План — это та же запись тренировки в дне, помеченная как назначенная, плюс
неизменяемый снимок исходного задания. Не параллельная сущность-двойник.**

Почему так:

- модель дня уже умеет тренировки, синхронизацию, tombstone-удаление и слияние —
  двойник потребует всего этого заново;
- `trainingTonnage` уже считает план и факт раздельно;
- лимит трёх тренировок в день не удваивается;
- клиент выполняет ровно ту запись, которую видел, — не появляется момент
  «копирования плана в факт», где данные обычно и теряются.

Отвергнуто: отдельное хранилище планов со своей синхронизацией — дублирует merge
и создаёт второй источник правды о том, что произошло в день.

Снимок исходного плана нужен всё равно — иначе правки по факту стирают задание.
Он живёт **внутри той же записи** как иммутабельная копия, а не как вторая
тренировка.

## Часть 4. Схема данных

### 4.1. На записи тренировки

```js
plan: {
  id: 'pl_…',            // идентичность назначения
  programId: 'pr_…',     // null, если разовое назначение
  weekIndex: 2,          // номер недели цикла, с 1
  dayLabel: 'День B',    // как куратор называет этот день
  assignedBy: '<curatorId>',
  assignedAt: 1754…,
  status: 'assigned',    // assigned → started → done | skipped
}
planSnapshot: { exercises: [...] }   // копия задания на момент назначения, не меняется никогда
```

`planSnapshot` фиксируется **при назначении**, а не при старте: иначе правка
куратора между назначением и стартом пройдёт мимо снимка.

### 4.2. Программа — client-scoped KV `heys_training_program`

```js
{
  id: 'pr_…', title: 'Верх/низ, 4 недели',
  weeks: 4, startDate: '2026-08-11',
  assignedBy, assignedAt, version: 1,
  status: 'active',      // active | replaced | finished
  days: [{ date, dayLabel, weekIndex, trainingId }]
}
```

Программа — **индекс, а не содержание**. Содержание всегда читается из дней;
индекс нужен, чтобы показать месяц одним чтением, не собирая тридцать блобов.
При расхождении правда за днями, индекс перестраивается сканом.

### 4.3. Совместимость

Запись без `plan` — обычная тренировка, как сегодня. Ни миграции, ни обратной
несовместимости: все проверки идут через «есть `plan` и статус `assigned`».

### Слой 1. Назначенное не считается сделанным — делать первым

Пока этого нет, любая другая часть фичи портит калории и нагрузку клиента.

**Масштаб уточнён инвентаризацией 2026-08-09: около пятидесяти мест читают
`day.trainings` как факт.** Имя `training.plan` при этом свободно — совпадения
`plan.status` в коде относятся к опросам голода, не к тренировкам.

### Найдено попутно: NDTE на клиенте мёртв

`heys_tdee_v1.js:244` вызывает `HEYS.InsulinWave.calculateNDTE` и
`getPreviousDayTrainings` через публичный неймспейс, но обе функции живут только
в `InsulinWave.__internals` — публично их не присваивает никто (проверено `rg`
по исходникам и закоммиченным бандлам плюс живой загрузкой модулей в рабочем
порядке). Условие молча ложно, `ndteBoost` на клиенте всегда 0.

Сервер при этом зовёт их через `webMirror.insulinWaveInternals()` и надбавку
считает. То есть **норма клиента в приложении и норма, которую видит куратор
через коннектор, расходятся** после каждого тренировочного дня на
`bmr × tdeeBoost` — десятки килокалорий.

Дефект существующий, к редизайну отношения не имеет. Чинить — отдельное решение:
починка поднимет нормы всем клиентам с тренировками, поэтому это не безобидная
правка одной строки.

### Слой 2. Схема и назначение одной тренировки

- Поля `plan` и `planSnapshot` в модели дня приложения и коннектора.
- MCP `heys_assign_training`: тот же валидатор упражнений, но `done: false` по
  умолчанию, `z: [0,0,0,0]`, `plan.status: 'assigned'`, `planSnapshot`
  заполняется.
- `heys_log_strength_workout` перестаёт молча перетирать назначенное: если в дне
  есть запись со статусом `assigned`, нужен явный `index`.
- Правка назначенного разрешена, пока статус `assigned`; после `started` —
  запрещена (см. слой 5).

### Слой 4. Программа на недели и обзор для клиента

- MCP `heys_assign_program`: валидировать **все** дни целиком до первой записи;
  писать по одному дню; при сбое посреди — вернуть куратору список записанных и
  незаписанных дат, а программу пометить частичной. Транзакции на несколько дней
  нет и не будет: дни — разные ключи.
- Клиентский обзор: ближайшая тренировка и «на неделе ещё три» первым слоем,
  весь цикл — вторым (`Подробнее`), по правилу progressive disclosure.
- Замена программы: новая версия, старая → `replaced`. Уже выполненные дни не
  трогаются никогда.

> **MCP-часть сделана 2026-08-09 (ночь), клиентский обзор — нет.**
> `heys_assign_program`
> ([`tools.js`](../../yandex-cloud-functions/heys-mcp/lib/tools.js)) валидирует
> все дни через ту же `day.assignTraining`, что пишет по одному дню
> (`heys_assign_training`, слой 2) — одни правила, не копия; ошибка хотя бы
> одного дня отбивает весь вызов, ничего не пишется. Прошедшие проверку дни
> пишутся по одному через `writeDay`; сбой конкретного дня (stale write, сеть)
> не роняет остальные — ответ называет `written`/`failed` по датам, а индекс
> `heys_training_program` (client-scoped KV, схема 4.2) получает
> `status: partial`, когда записалась только часть.
>
> Индекс — кэш поверх дней, не источник правды (сам протокол это оговаривает,
> 4.2: «при расхождении правда за днями»), поэтому «замена программы, старая →
> `replaced`» этим вызовом сознательно НЕ реализована: `heys_assign_program`

> существующем индексе. Если куратор назначает вторую программу поверх первой
> активной, старая запись в индексе просто перезаписывается новой (нет второго
> writer'а состояния, которого можно было бы испортить) — явного перехода в
> `replaced` не происходит, потому что ничего не читает историю индекса: кто
> захочет узнать, что было раньше, сканирует дни по старому `programId`, как и
> предписывает 4.2. Дожимать до формального `replaced`-перехода имеет смысл,
> только если появится читатель истории программ — сейчас его нет.

### Слой 5. Права, конфликт, уведомление, тариф

- Куратор правит только `assigned`. После старта его правка идёт предложением в
  чат, а не записью в день.
- Точечное правило слияния для записей с `plan`: победитель определяется
  статусом (`started`/`done` старше `assigned`), а не «богатством». Без этого
  правка плана во время сессии стирает отмеченные подходы.
- Пуш «Артём назначил тренировки на неделю» поверх существующего контура.
- Гейт по тарифу Pro Спорт — **на сервере**, в MCP, а не только в интерфейсе.

> **Правка после старта — сделана 2026-08-09 (ночь), по дизайн-хэндофу «Правка
> куратора после старта».** Правило, из которого следует всё остальное:
> **предложение никогда не трогает отмеченные подходы**. Оно ложится только на
> то, к чему клиент ещё не приступал, поэтому «взять правку» безопасно всегда и
> диалога о рисках не нужно.
>
> Граница защиты — **подход, а не упражнение**. Первая версия дизайна защищала
> начатое упражнение целиком, и это убивало главный сценарий: куратор видит
> первый подход, понимает, что вес тяжёл, и хочет сбавить оставшиеся. Три
> правила: закрытый подход не меняется ничем и никогда; незакрытые подходы
> начатого упражнения правятся, включая их число; начатое упражнение нельзя
> убрать из плана. Связка — тот же инвариант этажом выше: не начата — заменяется
> целиком, начата — состав заморожен, правятся веса в незакрытых клетках;
> разбирать связку правка не имеет права никогда.
>
> Ядро: `TK.strength.applyPlanEdit` / `acceptPlanProposal` /
> `declinePlanProposal` / `expirePlanProposal`
> ([`heys_kernel_strength_v1.js`](../../apps/web/_kernel/heys_kernel_strength_v1.js),
> web-mirror сверен). Молчаливого «не применилось» быть не может: что не легло —
> возвращается в `rejected` и показывается обеим сторонам, иначе куратор решит,
> что его проигнорировали, и повторит правку через неделю.
>
> MCP: `heys_propose_training_edit` кладёт правку предложением в
> `plan.proposal`, живую запись не трогая — решает клиент; предпросмотр «что не
> ляжет» отдаётся куратору сразу, до отправки. Живое предложение всегда одно.
> Пропущенный день правку принимает (защищать нечего, но пропуск остаётся
> решением человека), завершённая тренировка — нет.
> `heys_withdraw_training_proposal` отзывает, следа в истории не оставляя.
>
> Клиент: `ProposalCard` на дне, полноэкранный `ProposalReview`, `ProposalStrip`
> внутри идущей тренировки и `ProposalOutcome` в итогах
> ([`heys_strength_proposal_ui_v1.js`](../../apps/web/strength/heys_strength_proposal_ui_v1.js)).
> Карточка перехватывает день только пока к тренировке не приступали; начатую
> она не подменяет — иначе правка запирала бы вход в конструктор, и человек не
> мог бы продолжить, не ответив на неё. В работе правка приходит полоской (не
> модалкой) и завершения не держит: неотвеченное предложение гаснет само при
> закрытии тренировки и остаётся строкой в истории дня. `planSnapshot` при
> принятии обновляется на согласованный план, прежний уходит в `previous` —
> иначе отчёт куратору (слой 6) показывал бы отклонение от плана, который обе
> стороны уже отменили.
>
> **Три дефекта, которые вскрыла только живая проверка, а не тесты:** (1)
> решение применялось после `api.close()` — патч доходил до состояния React, но
> на диск уже не сохранялся, и ответ клиента исчезал при перезагрузке; (2)
> снимок и предложение ссылались на **один** массив, а сериализация дня вырезает

> начатая тренировка оказывалась заперта: продолжить её, не ответив на правку,
> было нельзя. Все закрыты регресс-тестами; второй ловится только через
> сериализацию, в памяти он не виден вовсе.
>
> **Правило слияния — сделано тогда же.** `heys_sync_merge_v1.js` (+ CJS-зеркала
> `heys-api-rpc`/`heys-api-rest`, побайтово идентичные друг другу): приоритет по
> `plan.status` (`assigned` = 0, `started`/`done`/`skipped` = 1) участвует в
> выборе победителя, только когда у записей разный приоритет и хотя бы одна из
> них про план — обычные тренировки без `plan` мержаются как и раньше, без
> изменений. Это закрывает риск 2.5: куратор, надиктовавший план офлайн-клиенту
> в момент, когда remote ещё не увидел клиентский `started`, раньше мог выиграть
> merge по свежести/richness и стереть уже отмеченные подходы.
>
> MCP-guard из слоя 2 (`setStrengthWorkout` отказывает, если `plan.started`) и

> не видел клиентского `started` вовсе. Нужны оба.
>
> **Гейт по тарифу — сделан 2026-08-09 (ночь).** `requireProSportTier()` в

> [`heys_subscriptions_v1.js:449`](../../apps/web/heys_subscriptions_v1.js)),

> клиенту, но назначение работало для любого.
>
> **Пуш о назначении — закрыт через существующий контур, не автоматической
> отправкой.** `heys_reply_message` уже отправляет клиенту push при любом

> `sendPushToClient`, generic push «Новое сообщение от куратора») — отдельной
> push-инфраструктуры под эту фичу заводить не нужно. Но `heys_assign_program`/
> `heys_assign_training` **не** вызывают `heys_reply_message` сами: системная
> инструкция куратора прямо запрещает автоматическую отправку («Отвечать клиенту
> через heys_reply_message — по решению куратора, а не автоматически»,
> [`curator.js:438`](../../yandex-cloud-functions/heys-mcp/lib/curator.js)) —

> нарушением. Вместо этого описание `heys_assign_program` явно называет
> `heys_reply_message` следующим шагом, если куратор захочет предупредить
> клиента сейчас. Разослать пуш без спроса — не менее рискованно, чем не послать
> вовсе, поэтому решение осталось за человеком.

### Перенос тренировки (дизайн-ревью 2026-08-10, экраны 16a/16b/16f)

**Перенести ≠ пропустить** — различие, из которого следует всё остальное.
Перенос освобождает исходный день заранее и пропуском не считается: в отчёте
куратора это отдельная строка рядом с «выполнено» и «пропущено». Пропуск задним
числом остаётся пропуском навсегда — прошедший день не воскрешают, замена
приходит обычным `heys_assign_training` на свободную дату и живёт как отдельная
тренировка.

> **Сделано 2026-08-10.** Отдельного механизма нет и не нужно: перенос — то же
> назначение плана на новый день плюс след в обе стороны. Новый статус
> `plan.status = 'moved'` на исходном дне (`movedTo`), происхождение `movedFrom`
> на перенесённой записи.
>
> Статус `moved` заведён сразу в трёх местах, иначе он ломает уже сделанное:
> `NOT_PERFORMED_PLAN_STATUSES` в ядре нагрузки (иначе перенос удваивал бы
> нагрузку — и на исходном дне, и на новом), `PLAN_STATUS_PRIORITY` в merge (+
> оба CJS-зеркала) и счётчики `heys_get_program_status`.
>
> MCP: `heys_move_training` пишет **целевой день первым** — если второй записать
> не удастся, у клиента останется лишняя тренировка на новой дате, а не
> потерянная. Занятый день (три тренировки) перенос отклоняет.
>
> Клиент переносит **сам, без подтверждения куратора**: пока тот ответит, день
> уйдёт, и перенос превратится в пропуск. Шторка «Когда сможешь?» предлагает
> ближайшие дни; занятый день показан с пометкой «занят» и недоступен — лимит
> трёх решается выбором, а не диалогом «что убрать» посреди переноса. Пропуск
> остался доступен, но вторым действием («Совсем пропустить»).
>
> Неотвеченная правка куратора едет вместе с тренировкой: она про содержание, а
> не про дату.
>
> Evidence: 6 тестов `day.test.cjs`, 2 в `program-week-overview.test.js`,
> heys-mcp — 1028 зелёных.

### Конец цикла (дизайн-ревью 2026-08-10, экран 16e)

Программа доходила до последнего дня и молча заканчивалась: куратор к этому
моменту уже получал полный отчёт, клиент не видел даже факта завершения.

> **Сделано 2026-08-10.** `TK.strength.programGrowth` + `ProgramDoneScreen`.
> Контракт роста держится дословно, потому что каждое его условие закрывает свой
> способ соврать человеку: берём **рабочие веса, а не тоннаж** (тоннаж растёт и
> от лишних подходов, то есть покажет «рост» там, где человек просто дольше
> сидел в зале); упражнение идёт в счёт только если встречалось **в трёх
> тренировках** (на двух точках это шум); порог — **один шаг**, 2,5 кг или одно
> повторение (иначе в рост попадёт округление); максимум **три строки** по
> относительному приросту. Свой вес растёт повторами — иначе подтягивания не
> попали бы в итог никогда.
>
> Роста нет — заголовок «Что удержано»: постоянство, объём, закрытые подходы.
> Живая проверка вскрыла ещё один случай: при недоступном ядре экран показывал
> «Что удержано: 0 тренировок, 0 кг» — то есть сообщал человеку, что он не
> сделал ничего. Теперь блока в этом случае нет вовсе.
>
> Разбора «жим 70 вместо 75 три раза» и поимённого списка пропусков на
> клиентском экране намеренно нет: у куратора это рабочий инструмент, у клиента
> тот же текст читается как перечень провалов. Пропуски — одной строкой без
> имён.
>
> Evidence: 8 тестов `kernel-plan-edit.test.js` (контракт роста), 3 в
> `strength-proposal-ui.test.js` (экран), живая проверка расчёта на реальном
> ядре.

## Часть 7. Что проверить до начала работ

- Как выглядит будущий день в приложении сейчас: что показывают нормы, дневник
  питания и виджеты, нет ли ошибок. Аудит смотрел код навигации и спарклайнов,
  но живой экран будущего дня не открывал.
- Сверка калорий по решению 5 редизайна (авто-минуты по зонам) — она меняет ту
