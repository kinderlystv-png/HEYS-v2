# Протокол реализации: сводка дня на карточке клиента

**Дата:** 2026-08-02 **Область:** экран выбора клиента у куратора **Тип:**
продуктовая фича (миграция + cloud function + legacy UI)

## Зачем

Куратор не видел, кто из клиентов что внёс сегодня, не заходя в каждого. Бейджи
на карточках (`🔥 стрик`, `📅 последний визит`) считались из localStorage, то
есть показывали только клиентов, открытых на этом устройстве
(`CURATOR_WORKSPACE.md`, C30). Серверного источника сводки не существовало.

**Критерий готовности:** на экране выбора клиента под именем видно «🍽 · 💧 · 👟
· 🏋» за сегодня по каждому клиенту, включая тех, кого куратор в этой сессии не
открывал; незаполненное выделено цветом.

## Решение и что отклонено

Взят минимальный путь: один read-only SQL-агрегат + строка на существующей
карточке. Отклонено:

- **отдельный экран/дашборд куратора** — сводка нужна ровно там, где куратор и
  так выбирает клиента; новый экран добавил бы навигацию без пользы;
- **клиентский подсчёт по загруженным дням** — это и есть текущая поломка
  (localStorage виден только по открытым клиентам);
- **материализованная таблица со сводками** — второй источник правды рядом с
  `client_kv_store`, который придётся синхронизировать; при нынешнем числе
  клиентов один запрос по PK дешевле.

## UI-гейт

Цель — за один взгляд понять, у кого сегодня пробел. Главное действие — открыть
такого клиента (карточка кликабельна, как и раньше). Слой 1 — четыре метрики
строкой, незаполненное красным. Слой 2 отдельно не вводился: детали дня живут
внутри клиента, дублировать их на карточке значило бы утяжелить список. Не
скрывается ничего критического — пробелы и есть главный сигнал.

## Риски и открытые вопросы

- **Прод-функция уже в БД, а вызывать её пока некому.** Миграция применена, но
  cloud function не задеплоена: до шага 4 фронт получит `Function not allowed`.
  Сводка при ошибке не рендерится, карточка работает как раньше, поэтому
  промежуточное состояние безопасно — но пока это фича без включения.
- Стрик и «последний визит» остались на localStorage. Логично перевести и их на
  сервер, но это отдельная задача: формат стрика требует чтения диапазона дней.
- Обновление раз в 5 минут выбрано без замера нагрузки. Запрос дешёвый (одна
  строка KV на клиента по PK), но при росте числа клиентов это стоит
  перепроверить.
