# Флоу добавления еды: разбор по коду — 2026-08-09

**Зачем:** дизайнер собирает канвас «Добавление еды» и отказался рисовать
вслепую — на прошлых вкладках инвентарь по коду каждый раз менял решения. Здесь
факты, на которые можно опираться. Проверено четырьмя параллельными проходами по
исходникам (не по бандлам).

Смежные документы: [UI_V4_SPEC_2026-08-09](UI_V4_SPEC_2026-08-09.md) — решения
по пяти вкладкам, [`docs/ui/handoff-v4/`](../ui/handoff-v4/README.md) — макеты и
токены.

---

## 1. Сколько шагов от «+» до сохранённого приёма

**Семь экранов на мобильном.** Приём сохраняется уже на четвёртом, продукты —
надстройка сверху.

| #   | Что видит человек                                           | Условие                              |
| --- | ----------------------------------------------------------- | ------------------------------------ |
| 1   | Модалка «Выбрана другая дата»                               | только если выбранная дата ≠ сегодня |
| 2   | Полноэкранный гайд «Это — важно.» с тарелкой                | **каждый раз**, см. ниже             |
| 3   | Пикер времени: колёса часов и минут, тип приёма             |                                      |
| 4   | Самочувствие: настроение, самочувствие, стресс, комментарий | здесь приём **сохранён**             |
| 5   | Модалка выбора флоу «Добавить продукты в …»                 |                                      |
| 6   | Поиск продукта                                              |                                      |
| 7   | Граммовка, кнопка «Добавить»                                |                                      |

**Десктоп — другой путь и короче:** приём создаётся мгновенно с именем «Приём» и
пустым временем, шаги 3–5 отсутствуют. Гард даты и гайд с тарелкой остаются.

**Третий путь** — мобильный fallback, если модуль пикера не загрузился:
bottom-sheet из двух шагов, без модалки выбора флоу.

**Добавление продукта в существующий приём — два видимых шага:** поиск → граммы.
В мастере объявлено пять шагов, но три (`create`, `portions`, `harm`) помечены
скрытыми и всплывают только при создании нового продукта.

### Гайд с тарелкой — не пустое состояние, а обучалка на каждый приём

Полноэкранная плашка с фото тарелки, выносками «½ овощи и фрукты · ¼ белок · ¼
крупы» и четырьмя эффектами (сердце, сахар крови, мозг, кишечник) показывается
**при каждом создании приёма**. Флага «больше не показывать» нет: единственный
обход — параметр `skipPlateGuide`, и ни один вызов в кодовой базе его не
передаёт. Шесть вариантов картинки чередуются, но экран остаётся обязательным.

## 2. Режимы добавления: сколько продуктов за раз

Мультивыбора чекбоксами нет нигде. Вместо него три режима, задаваемые кнопками в
карточке приёма («⚡ Добавить 1 продукт», «2», «3», «4», «Добавить несколько»):

- **`single`** — после «Добавить» окно закрывается, экран скроллится к дневнику.
- **`repeat`** (кнопки 2/3/4) — окно **не закрывается**: счётчик уменьшается,
  выбранный продукт сбрасывается, возврат к поиску. N продуктов = N×2 шага в
  одном непрерывном окне. Граммовка предыдущего продукта переносится как
  подсказка «в прошлый раз».
- **`multi`** — после каждого продукта окно закрывается и показывается сводка:
  список приёма до шести позиций, «Итого» с цветом по качеству, «До нормы
  осталось N ккал», при переедании — «Похоже, приём уже тяжеловат». Кнопки в три
  ряда: «Завершить» / «Добавить последний», «Добавить ещё несколько», «ещё
  2/3/4». При выполненной норме заголовок меняется на «Норма выполнена» и
  запускается конфетти.

**Проблема `multi` для дизайна:** это мигание — окно закрывается, появляется
модалка, открывается новое окно, с задержками кадра и двух таймеров по 100 мс.
Бесшовный цикл в коде есть, но недостижим: выше стоит ранний выход, и в
дневниковом флоу срабатывает всегда именно он.

## 3. Откуда вызывается окно и показывается ли повторно

Плавающая кнопка 🍽️ **окно продукта не открывает** — она переключает вкладку на
дневник, скроллит к заголовку и через 800 мс запускает создание приёма, то есть
весь путь из семи шагов.

Прямые входы в окно добавления продукта: кнопки в карточке приёма, модалка сразу
после создания приёма, карточка рекомендации приёма в Инсайтах (с подставленным
поисковым запросом и граммовкой), самопереоткрытие после «Добавить последний».

Косвенный: баннер «Не заполнено приёмов» → кнопка «Заполнить» делает программный
клик по кнопке добавления в первом пустом приёме.

Повторный показ после сохранения — только в режиме `repeat`, см. выше.

## 4. Поиск продукта

### Что в выдаче

Строка результата: иконка категории, название с подсветкой совпадения, значок
общей базы, бренд, мета-строка «N ккал · Б x | Ж y | У z», счётчик «Исп.: N×»,
штрихкод. Фон карточки красится по вредности. Кнопки: избранное, штрихкод,
карандаш, удалить, скрыть.

**Ранжирование двухслойное.** Сначала движок умного поиска: релевантность по
типу совпадения (точное имя 100, начало слова 82, раскладка QWERTY 82, транслит
78, опечатка 45, фонетика 35) плюс бонусы за избранное и частоту. Затем второй
пересчёт поверх личных и общих кандидатов со своими весами. Дедуп по имени,
причём **приоритет у продукта с заполненными порциями**, а не у большего балла.

Лимиты жёсткие: личные 20, личные плюс общие 25, запрос в общую базу 30, частые
20, превью общей базы без запроса 12. Дебаунс 200 мс локально и 300 мс для общей
базы, минимум два символа.

### История и частые

Два переключаемых списка над выдачей, видны **только при пустой строке поиска**:

- **«⚡ Частые и избранные»** (по умолчанию) — окно 21 день, захардкожено. Балл
  = частота × затухание по давности. Группы: избранное с историей → используемое
  → избранное без истории → созданное за 48 часов. До 20 позиций.
- **«🕘 Недавние · 3 дня»** — сегодня и два предыдущих календарных дня, без
  лимита.

**Визуально эти списки неотличимы от результатов поиска** — та же карточка, тот
же счётчик использований. Единственный признак, в каком ты списке, — состояние
двух табов, которые исчезают при вводе текста.

### Распознавания фото нет, голосового ввода нет

Кнопка «Добавить фото» вешает снимок **на приём**, а не на продукт: клиент
сжимает до 800 px и JPEG 0.7, облачная функция складывает в объектное хранилище
и возвращает URL. Ни кандидатов, ни граммовки. Лимит 10 фото на приём.

Web Speech API в проекте реализован (русский язык, промежуточные результаты,
таймаут 10 с), но к добавлению еды не подключён ни в одном месте — работает
только в мессенджере с куратором. Возвращает строку, парсинга в продукт нет.

### Пресеты приёмов

Кнопка «Наборы» в шапке поиска. Хранятся локально. Три вида карточек:
рекомендованные из истории, свои сохранённые, пустое состояние с двумя кнопками.
Движок рекомендаций сканирует все дни в локальном хранилище, порог — комбинация
встречалась **не меньше трёх раз**, размер 2–8 продуктов, граммовка берётся как
мода по истории. Исключаются уже сохранённые, отклонённые и подмножества более
крупных комбинаций.

Внутри создания набора — **свой отдельный поиск**, примитивный `includes` по
имени с лимитом 8, без умного движка.

### Если продукт не найден

Создание нового продукта — **не форма с полями, а вставка текстовой строки**.
Есть кнопка «Скопировать промпт для ИИ»: человек идёт к внешней модели, получает
строку и вставляет обратно. Обязательны **двенадцать чисел**: ккал, углеводы,
простые, сложные, белок, жир, плохие, хорошие, транс, клетчатка, ГИ, вредность.
Кнопка «Добавить» заблокирована, пока строка не распарсилась. Название
необязательно — подставляется поисковый запрос.

После «Добавить» продукт в базу ещё не пишется: сначала шаг «Порции», затем
«Вредность», и только там сохранение.

## 5. Порция

**Четыре способа ввода на одном экране:** числовое поле (1–2000), кнопки «−/+»
шагом 10 г, ползунок (10–500, шаг 5), кнопки-порции.

**Значение по умолчанию** — каскад: граммовка из рекомендации → последняя порция
**именно этого продукта** → 100 г. Стандартная порция из карточки продукта
дефолтом не становится, она только рисуется кнопкой.

**Три набора кнопок-порций:** захардкоженные 50/100/150/200/300; порции
продукта, а при их отсутствии — автопорции по названию (около 80 паттернов: яйцо
60 г, ломтик хлеба 30 г, пельмени 5 шт 75 г, кусок пиццы 100 г, тарелка супа 300
г) с чёрным списком для жидкостей; пользовательские порции из редактора
продукта.

**Единица одна — граммы.** Поля единицы измерения у позиции нет. Штуки и стаканы
существуют только как подписи кнопок, число всегда в граммах, пересчёта нет:
ввести «2 штуки» нельзя, можно выбрать готовую порцию или набрать граммы.
Альтернативный режим ввода — ккал с обратным пересчётом, но он использует сырое
поле калорий и у продукта без него не работает.

### Редактирование

**Продукт у позиции заменить нельзя** — в модалке редактирования нет шага
поиска, только граммовка. Меняют удалением и добавлением заново.

Мобильный и десктопный пути разные: на мобильном граммовка — кнопка, открывающая
ту же модалку граммов; на десктопе — инлайновое числовое поле прямо в строке,
модалка не открывается.

Удаление: свайп на мобильном, крестик на десктопе. Есть отмена окном 4 секунды с
тостом, ставится метка удаления. Подтверждающего диалога нет. **Для изменения
граммовки отмены нет.**

Блок «Замени на …» в карточке — только текст, обработчика клика у него нет.

### Живой пересчёт

Калории и БЖУ пересчитываются на каждый рендер, до сохранения: строка калорий,
три плитки Б/Ж/У, итог по дню «+N ккал → съедено/норма (%)». Клетчатки, ГИ и
инсулиновой волны на этом экране нет.

**Калории считаются по NET Atwater: белок 3 ккал/г, а не 4.** Это системное
решение, не ошибка — планировщик держит рядом обе величины, валовую и чистую.
Следствие для макета: калории продукта не сойдутся с суммой БЖУ, посчитанной по
учебнику.

### Фото

Привязано к приёму, не к позиции. Загружается оптимистично: сразу видно
локально, параллельно уходит в облако. Миниатюры ленивые, с бейджем времени,
кружком «обработано» и часами для незалитых. Удаление с отменой 5 секунд,
реальное удаление из облака — только по истечении окна.

## 6. Название приёма и время

### Название человек не вводит текстом

Словарь: Завтрак, Перекус, Кофе-брейк, Обед, Перекус, Ужин, Перекус, Ночной
приём. Источников три, и они **дают разные ответы**:

1. **При создании** — по часам устройства, жёсткие границы: 06–10 завтрак, 10–12
   перекус, 12–15 обед, 15–18 перекус, 18–21 ужин, 21–03 ночной, 03–06 перекус.
2. **В предпросмотре пикера** — границы плавающие: если приёмов ещё нет,
   завтрак; иначе промежуток от первого приёма дня до 03:00 делится на шесть
   равных слотов. При завтраке в 07:00 слот 3 ч 20 мин, при завтраке в 11:00 — 2
   ч 40 мин.
3. **В дневнике после сохранения** — третья логика: первый приём дня **всегда**
   завтрак, дальше те же плавающие слоты, плюс коррекция по размеру приёма
   (крупный перекус повышается до обеда или ужина, а если такой уже был —
   понижается обратно).

**Следствие для дизайна: название в заголовке карточки может смениться само** —
когда человек добавит продукты и приём перевалит порог «крупного» (3 продукта,
или 200 г, или 300 ккал), либо когда добавит более ранний приём и сдвинутся все
слоты.

Ручной выбор есть — селектор в шапке карточки с вариантом «🔄 Авто». Кофе-брейка
в этом списке нет, его ставит только внешний коннектор.

### Время

Подставляется по часам устройства с округлением минут до пяти, человек сразу
видит колёса и может прокрутить. Порядок часов в колесе 03…23, затем 00, 01, 02
— сутки заканчиваются в три ночи, ночные часы хранятся как 24–26. Десктопный
путь время не спрашивает вообще, пишет пустую строку.

Изменение задним числом доступно тапом по бейджу времени; при сохранении приёмы
пересортировываются. Для чужой даты время всё равно подставляется текущее —
крутить колесо приходится вручную.

## 7. Что показывается по ходу и что предупреждает

| Где                               | Что видно                                                                                                  |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Список результатов поиска         | ккал/100 г, БЖУ/100 г, вредность **только цветом фона**                                                    |
| Экран граммовки                   | ккал, три плитки БЖУ, итог дня, вредность **только цветом шапки**                                          |
| Сводка после добавления (`multi`) | список приёма, «Итого» с цветом, остаток до нормы                                                          |
| Дневник после сохранения          | полный набор: ккал, У, простые/сложные, Б, Ж, вредные/полезные/супер, **клетчатка, ГИ, вредность** числами |

То есть клетчатка, гликемический индекс и число вредности появляются **только
после сохранения**. До него вредность передаётся цветом.

**Инсулиновая волна** пересчитывается сразу после добавления и видна в карточке
«Окно для сжигания жира» в дневнике, плюс раскрываемой секцией внутри приёма. До
сохранения она считается ровно для одного — предупреждения ниже. Прогноза «как
этот приём сдвинет волну» пользователю не показывают.

**Вредность** — шкала 0–10, обратная. Считается дозозависимо: макросы
масштабируются на граммы, ГИ и добавки нет, плюс штраф за калории порции
свыше 150. Тренировка снижает вред, и в шапке приёма тогда появляется «Еда
пойдёт в энергию, а не в жир». Расхождение в порогах: цвет и подсказка в строке
работают по границам 2/4/6, а категории («Полезный», «Нейтральный», «Вредный») —
по 1/2.5/4/5.5/7/8.5.

### Шесть предупреждений во всём флоу

1. **Гайд с тарелкой** — каждый раз, см. раздел 1.
2. **«Выбрана другая дата»** — жёсткий гард с двумя кнопками.
3. **Ночной час** — мягкая подсказка «запишется в <дата>» при часах 00–03.
4. **Инсулиновая волна** — «Расчётный постпрандиальный период ещё продолжается»,
   кнопки «Подождать» и «Всё равно добавить». Показывается **один раз**, только
   по нажатию «Далее», и пропускается при дефиците от 10 %, при чужой дате, при
   пустом дне и при времени дальше получаса от текущего.
5. **Дубль продукта в приёме** — «Уже добавлено N г… иначе еда посчитается
   дважды».
6. **«Приём уже тяжеловат»** — единственный намёк на перебор, и только **после**
   сохранения, в сводке.

**Отдельного «мало белка» нет.** Дефицит белка считается и влияет на цвет
колонки, но в поток добавления не выводится. Формулировки вроде «переедание»,
«тяжёлая еда ночью», «поздно» в коде есть, но пользователю не показываются — они
только переключают цвет и одну общую фразу.

---

## Что из этого стоит решать, а не просто рисовать

Список наблюдений, каждое — кандидат в отдельную задачу. Решения по ним нет.

- **Семь шагов до первого продукта** — главный кандидат на сокращение. Гайд с
  тарелкой без флага «больше не показывать» стоит первым в очереди.
- **Мигание в режиме `multi`** — бесшовный цикл в коде уже написан, но
  недостижим из-за раннего выхода.
- **Три разные логики названия приёма**, из-за которых заголовок меняется сам.
- **Частые, недавние и результаты поиска визуально неразличимы.**
- **Продукт у позиции нельзя заменить**, только удалить и добавить заново.
- **Создание продукта через вставку строки из двенадцати чисел** — работает, но
  предполагает поход к внешней модели посреди добавления еды.
- **Мёртвые механизмы:** история граммовок пишется и синхронизируется, но не
  читается никогда; история порций всегда пуста, потому что функция записи не
  вызывается, и подсветка «рекомендованной» порции из-за этого не работает.
- **Тумблер «Общие» включён по умолчанию**, поэтому запасной блок «Искать в
  общих» практически никогда не показывается.
- **Подтверждения деструктивных действий — нативные `confirm()`**, не в стиле
  модалок приложения.

# Слой глубже: то, чего нет на канвасе

Второй проход, после того как дизайнер собрал восемь экранов счастливого пути.
Три параллельные проверки: отказы и офлайн, ненарисованные состояния, всё за
пределами «клиент на мобильном».

## Молчаливая потеря функции

**Кнопка «Добавить фото» — единственный вход для фото приёма во всём
приложении** (`heys_add_product_step_v1.js:5526`), и живёт она в шапке поиска
продуктов. На канвасе её нет. Реализовать макет как есть — значит убрать
возможность прикрепить фото к приёму. Место у кнопки и правда неудачное: фото
относится к приёму, а не к продукту, логичнее перенести её на экран «Приём
собран».

## Дефекты, подтверждённые вторым проходом

- **«Итог дня» при правке граммовки всегда показывает ноль.** В edit-конфиг
  список продуктов передаётся пустым (`heys_add_product_step_v1.js:9998`), а
  строка итога ищет продукты именно в нём (`:8915`). Человек, который уже поел,
  видит «съедено 0 за день».
- **Тост «Приём создан» печатается безусловно** (`day/_meals.js:5042`),
  независимо от результата записи. `lsSet` не бросает исключение и возвращает
  `false`, которое нигде не читается (`heys_core_v12.js:245`) — при переполнении
  квоты приём остаётся на экране, но не в хранилище.
- **Одиночное добавление продукта при провале записи врёт UI**: пишет ошибку в
  консоль и всё равно делает `setDay` (`day/_meals.js:5195`). Групповое
  добавление в той же ситуации хотя бы прерывается (`:6149`).
- **Создание набора не подтверждается ничем** — ни тоста, ни анимации, экран
  просто возвращается к списку. Удаление набора идёт вообще без подтверждения.
- **Подсказка «Искать в общих» не показывается никогда**: она гейтится
  выключенным тумблером «Общие», а он включён по умолчанию.
- **Конфликт с куратором невидим.** Слияние дня разрешается тихо, ни тоста, ни
  маркера. Плюс кураторская правка может не появляться до 30 секунд, пока клиент
  что-то добавляет (окно блокировки внешних обновлений).
- **Статусы синхронизации живут только в атрибуте `title`**
  (`heys_app_shell_v1.js:3793`) — на телефоне их не прочитать.

## Отказы и офлайн

**Что работает офлайн:** запись дня, поиск по личным продуктам, добавление
существующего продукта, фото (уходит в очередь с бейджем ожидания).

**Что ломается:** создание нового продукта офлайн блокируется полностью и даёт
**два сообщения подряд** — тост «Продукт не сохранён в базу» и inline «Не
удалось завершить», а введённое теряется. Обходного пути для сетевой ошибки нет
(для ошибки размера — есть).

**С холодного офлайн-старта добавить еду нельзя вовсе:** группа плавающих кнопок
скрывается, поверх дня — оверлей «данные за сегодня не загружены».

**Ошибка общей базы неотличима от «ничего не найдено».** При сбое выдача не
обновляется: человек видит либо «Ничего не найдено», либо устаревшие результаты
прошлого запроса. Отмены запроса нет, поздний ответ перезаписывает свежий. В
худшем случае ожидание тянется около 55 секунд под подписью «⏳ Поиск...».

**Первого входа не существует как состояния.** При пустой личной базе показывают
только блок общей базы; если и она не подтянулась — пустой экран с подписью
«Общая база пока не загрузилась». Ни призыва создать первый продукт, ни
объяснения.

## Ненарисованные состояния

Обязательные к отрисовке:

- **Сканер штрихкода** — не полноэкранная камера, а модалка-карточка: пять
  состояний камеры со своими текстами, ручной ввод EAN/UPC всегда доступен, пять
  разных исходов сканирования (один продукт, несколько, ноль, сетевая ошибка,
  нераспознанный код), пять текстов ошибок камеры.
- **Просмотрщик фото** — полноэкранный оверлей с пинч-зумом до 5×, панорамой,
  свайпом вниз для закрытия, листанием, двойным тапом и клавиатурой. Плюс пять
  состояний миниатюры, включая «ожидает загрузки».
- **Создание нового продукта** — три шага. На последнем человек выбирает между
  значением вредности из вставленной строки и расчётом системы, с плашкой
  расхождения и раскрытым по умолчанию разбором формулы.
- **Оверлей «Наборы»** — список с рекомендациями и своими наборами, создание со
  своим упрощённым поиском, превью с исключением позиций и умножением.

Существующие, но не обязательные для этого канваса: полный редактор продукта на
три шага, менеджер штрихкодов, модалка копирования приёма, список недавних
приёмов, экран загрузки шага.

## Проблемы, которые макет должен решить, а не унаследовать

- **Тач-цели.** Кликабельные точки прогресса в шапке — **6×6 px**. Ниже 44 pt
  также: пресеты граммовки (~29), кнопки порций (~23), пять иконок 26×26 подряд
  в одной строке продукта, табы списков (32), крестик закрытия (~37 — 44
  объявлены у контейнера, а не у кнопки).
- **Кнопка «Добавить» уходит под клавиатуру.** Она внутри скроллящегося
  содержимого, не закреплена, после неё в разметке ещё четыре блока. Компенсации
  высоты нет нигде во флоу, модалка меряется в `vh`, автоскролла к кнопке нет.
- **Аппаратная «назад» на Android не перехватывается** — в установленном
  приложении уводит наружу, модалка остаётся с заблокированным скроллом. В
  других модулях проекта этот паттерн реализован, до еды не доехал.
- **Закрытие на середине теряет всё** — выбранный продукт и граммовку, черновика
  нет. Исключение: новый продукт уже записан в базу, но в приём не попадёт.
- **Крестик и «Готово» ведут себя одинаково** — оба прыгают к заголовку
  дневника. Позиция, откуда человек пришёл, сохраняется в коде, но никогда не
  восстанавливается.
- **Escape не закрывает основную модалку** (только вложенные оверлеи), клик по
  фону закрывает без подтверждения.
- **Доступности почти нет:** ни `role="dialog"`, ни фокус-ловушки, ни возврата
  фокуса, смена шага не объявляется, у большинства иконочных кнопок нет
  подписей.
- **Планшет и десктоп получают ту же колонку 420 px** — медиазапросов на
  расширение нет. При этом десктоп доступен только куратору или клиенту с
  отдельным разрешением, то есть широкий экран этого флоу — де-факто
  кураторский.

## Куратор

Отдельного кураторского флоу нет, экраны те же. Различия только на записи: новый
продукт публикуется сразу против отправки на модерацию, общий продукт клиенту
редактировать нельзя, порции идут через разные RPC. Кнопки в строке продукта по
роли не скрываются. Кураторский путь уже ломался на записи в дневник — в коде
остался комментарий об этом инциденте.

# Приёмка второго слоя канваса — 2026-08-11

Проверен `docs/ui/handoff-v4/canvas/Добавление еды.dc.html` (первый слой +
дорисованный второй, 15 экранов) против раздела «Ненарисованные состояния» этого
аудита и против исходников. Тип записи: **рекомендация агента по итогам ревью**,
не решение владельца. Вывод: **в текущем виде кодеру отдавать нельзя** — не
из-за краски, а из-за одного экрана, который противоречит модели продукта, и
из-за недорисованных ветвей, которые исполнитель вынужден будет придумать.

## Блокеры (без них исполнитель будет угадывать)

1. **Экран «Продукт · состав» несовместим с моделью продукта.** Нарисованы 8
   полей: Ккал, Белки, Жиры, Углеводы, Клетчатка, Сахар, ГИ, Вода. В коде
   вставляемая строка — 12 чисел: Ккал, Углеводы, Простые, Сложные, Белок, Жиры,
   Вредные жиры, Полезные жиры, Транс-жиры, Клетчатка, ГИ, Вред
   (`heys_add_product_step_v1.js:6450`). Различия:
   - нет `simple100/complex100` и `badFat100/goodFat100/trans100` — а вредность
     считается именно по ним (`heys_harm_v1.js:489–495`: trans, simple, badFat,
     sodium против fiber, protein, goodFat), и день считает по ним же
     (`heys_day_stats_vm_v1.js`, `heys_day_caloric_balance_v1.js`);
   - «Ккал», «Жиры», «Углеводы» нарисованы полями ввода, а в коде они
     **производные, read-only** (`heys_core_v12.js:4222–4224`); первый слой того
     же канваса сам пишет, что калории считаются по NET Atwater;
   - «Вода, г» — поля нет в модели вообще (`rg water100` пусто);
   - нет «Бренд», хотя поле есть с 2026-07-02 и участвует в дедупликации.
2. **Шаг 3 «Вредность» потерял модерацию.** В коде на этом шаге клиент видит «на
   модерацию», куратор — «сразу доступен всем»
   (`heys_add_product_step_v1.js:6538`), плюс исходы «заявка отправлена», «уже
   на модерации», «не удалось отправить» (`:8161–8208`). На макете — ни строки.
   Это единственное место, где клиент узнаёт, что его продукт ещё не общий.
3. **Нет состояния «не удалось сохранить продукт».** Сегодня отказ даёт два
   сообщения подряд и теряет введённое (см. «Отказы и офлайн»); макет это не
   лечит и не описывает.
4. **Сканер: из пяти состояний камеры и пяти исходов нарисованы два.** Есть
   «наведение», «код прочитан, продукта нет», «найден». Нет: нераспознанный код
   (сам канвас отложил его в «Дальше»), несколько совпадений, сетевая ошибка,
   отказ в доступе к камере, камера занята/отсутствует. Плюс контейнер сменён: в
   коде это модалка-карточка с постоянно доступным ручным вводом
   (`BarcodeScannerModal`, `heys_add_product_step_v1.js:3210`), на макете —
   полноэкранный тёмный видоискатель с ручным вводом за кнопкой. Смена
   контейнера допустима как решение, но должна быть названа решением.
5. **Внутреннее противоречие по наборам.** Первый слой: «удаление и
   переименование — по долгому нажатию», у каждой строки кнопка «Добавить».
   Второй слой: «правка и удаление — по тапу на строку», главное действие —
   плюс. Один и тот же список, два разных жеста.
6. **Нет экрана «Собрать новый набор»** — кнопка есть с первого слоя, экрана нет
   ни в одном слое; в аудите он числится обязательным (упрощённый поиск,
   исключение позиций, умножение).

## Мелкое, чинится за один заход

- Иконка штрихкода и плейсхолдер строки поиска остались на тоне `.35` (≈2,4:1) —
  при том что правило второго слоя переводит интерактивные подписи на `.55`.
  Иконка штрихкода — единственный вход в сканер, то есть интерактивный контрол.
- Девять цветов канваса не ложатся на роли песочной палитры (`#a75c2b`,
  `#f2ede6`, `#cf8144`, `#f3e0d2`, `#f0d8c4`, `#e6cfa8`, `#d9b98a`, `#141210`,
  `#2b1608`) — остальные совпадают с `002-ui-v4-palette-roles.css` один в один.
  Либо свести к ролям, либо назвать девять новых токенов, иначе тёмная и синяя
  палитры их не подхватят.
- «12 400 продуктов» вшито в копирайт трёх экранов — нужно решение: живое число
  или формулировка без числа.
- Счётчик «399» в шапке так и остался без объяснения («нарисованы как есть, до
  разбора»).

## Осталось за пределами макета

Требования названы прозой, экранов нет и, вероятно, не нужно: закреплённая над
клавиатурой кнопка «Добавить», перехват аппаратной «назад», черновик при выходе
на середине, возврат в позицию входа, `role="dialog"` и фокус-ловушка. По
черновику решения нет вообще — что именно сохраняется при выходе, спрашивать или
молча, — исполнителю понадобится ответ.

Тёмная и синяя палитры сознательно отложены отдельной волной; вёрстку это не
блокирует, если она идёт через роли `--v4-*`, а не через хексы канваса.

## Приёмка добора — 2026-08-11, второй проход

Все шесть блокеров закрыты, проверено по файлу и по коду:

- состав приведён к модели: ккал/жиры/углеводы помечены «авто», появились
  простые/сложные и вредные/полезные/транс, «Вода, г» снята, «Бренд» добавлен;
  порядок чисел в варианте C совпадает с парсером (`heys_core_v12.js:301` —
  последние 12 токенов строки);
- модерация стоит до кнопки «Сохранить», с кураторским вариантом строки;
- нарисованы три исхода заявки и отказ сохранения одним сообщением;
- сканер — четыре ветви, ручной ввод в каждой; полноэкранный видоискатель назван
  решением;
- жест наборов один (тап), долгое нажатие снято из обоих слоёв;
- «Собрать новый набор» нарисован.

Остаётся до вёрстки (не блокирует выбор варианта):

1. **Стейл-заметка на листе создания продукта.** «Четыре редких поля — во второй
   ярус: клетчатка, сахар, ГИ и вода» противоречит и «вода убрана», и варианту
   A, где раскрытий три и вода не упоминается. Заметку переписать под выбранный
   вариант.
2. **Исходов модерации в коде пять, на макете три.** Не хватает «продукт уже
   есть в общей базе» (`status === 'exists'`) и потери PIN-сессии
   (`heys_add_product_step_v1.js:8189` и `:8197–8207` — `invalid_session` ведёт
   к повторному вводу PIN, отложенной отправкой это не лечится).
3. **«Отправим куратору, когда появится сеть» — обещание без механизма.**
   Очереди повторной отправки заявки в коде нет (`createPendingProduct`
   вызывается один раз, при ошибке только тост). Либо менять формулировку, либо
   ставить очередь отдельной задачей.
4. **«Сохранить только себе» — новое поведение, а не экран.** Сегодня создание
   продукта офлайн блокируется целиком (см. «Отказы и офлайн»). Кнопка требует
   локального сохранения продукта с последующей синхронизацией.
5. **Вариант C, если его выберут:** на экране нет поля названия, а парсер берёт
   имя из текста перед числами; и возвращена кнопка «Скопировать запрос» — тот
   самый уход к внешней модели, который канвас сам отверг в разделе «Не
   рисовал».
6. **Цвета вне ролей — по-прежнему открыто** (сам канвас это фиксирует): семь
   хексов не встречаются в `002-ui-v4-palette-roles.css` вовсе, ещё четыре взяты
   из песочной тёмной. Свести к ролям до вёрстки, иначе тёмная и синяя палитры
   их не подхватят.
7. «12 400 продуктов» осталось в одной прозаической заметке (на экранах снято).

### Решения владельца — 2026-08-11

- **Состав продукта — вариант A** (основное плюс три раскрытия). Основание:
  единственный из трёх не спорит с progressive disclosure из `CLAUDE.md`; B даёт
  девять полей сразу, C возвращает «скопировать запрос» — уход к внешней модели,
  который канвас сам отверг, и теряет поле названия, хотя парсер берёт имя из
  текста перед числами. Пересмотр уместен только при данных, что строку приносят
  почти всегда: тогда C, но с названием и без кнопки запроса.
- **Черновик при выходе — спрашивать, не хранить.** Диалог показывается, когда
  есть что терять (выбран продукт или введены граммы); слоя хранения черновиков
  не заводим. Закрывает реальную потерю данных при выходе по «назад» и тапу по
  фону, не создавая протухающих черновиков.

## Приёмка финального добора — 2026-08-11, третий проход

Семь пунктов внесены и проверены: диалог выхода с названием и граммовкой, два
недостающих исхода модерации («уже есть в общей базе», «нужно войти заново» с
кнопкой PIN), текст про отправку заявки без обещания автоповтора, пометка, что
«Сохранить только себе» — работа в хранилище, B и C с датой и причиной отказа,
«12 400» снято, стейл-заметка про сахар и воду переписана.

Тёмные значения канваса совпадают с ролями песочной тёмной один в один

## Канвас принят — 2026-08-11, четвёртый проход

Оба хвоста закрыты, проверено на самом файле:

- **Переполнений нет ни на одном из 33 экранов** (`.sc`:
  `scrollHeight > clientHeight + 2` — ноль совпадений; закреплённые полки внизу
  ничего не перекрывают). Три раскрытия состава свёрнуты в одну строку «Состав
  подробнее · 6 значений», экран стал короче на 108 px, «Вставить строку из
  буфера» видна. Подпись про ручной ввод переехала на полку к самой кнопке.
- **Цвета сведены к ролям.** `#a75c2b` больше не используется (осталось одно
  упоминание в прозе), обе подложки внимания заменены на `--v4-accent-bg`
  `#f0dcc6`. Вне ролей осталась только заглушка-градиент фотографии (`#e6cfa8`,
  `#d9b98a`, `#c9a273`) — интерфейсом не является.

**Одна новая роль под регистрацию: текст на терракотовой кнопке.** Дизайнер
предложил `#2b1608`, тёмный вариант `#1a0f04`. Обоснование верное, число в
подписи — нет: бумага `#fffaf1` на акценте `#c67139` даёт **3,47:1**, а не 2,9
(порог 4,5 всё равно не проходит). Проверенные значения: `#2b1608` на `#c67139`
— 4,77:1, `#1a0f04` на тёмном акценте `#cf8144` — 6,17:1.

Роль заводится в `002-ui-v4-palette-roles.css` для всех четырёх палитр, а не
только песочных. На синем акценте `#2e7cc0` тёмно-коричневый не работает
(3,9:1), белый там даёт 4,41:1 — то есть синей паре нужны свои значения, и это
вопрос к дизайнеру, а не механический перенос.

Статус: **канвас можно отдавать в вёрстку.** Открытые вопросы, не блокирующие
старт: очередь повторной отправки заявки на модерацию и локальное сохранение
продукта офлайн («Сохранить только себе») — обе задачи в данных, не в разметке,
и помечены на самом листе.

### Два хвоста в данных: решения и очерёдность — 2026-08-11

Оба промпта написаны, но **запуск отложен до ПДн-контура** (решение владельца по
итогам ревью промптов): клиентов пока нет, обе задачи чинят потери, которых
сегодня некому испытать, а в дереве лежит чужая незакоммиченная работа, включая
`apps/web/day/_meals.js` и `heys_tasks_kv.cjs` в двух облачных функциях.
«Сохранить только себе» — pre-launch, до первых реальных клиентов; очередь
модерации — после.

Развилки закрыты заранее, чтобы исполнитель их не выбирал:

- **Два fire-and-forget вызова `createPendingProduct`
  (`heys_add_product_step_v1.js:4866`, `:9456`) в очередь не идут.** Это не
  заявка на новый продукт, а привязка штрихкода к уже существующему: локально
  код сохранён (`commitPersonalProduct` с источником `barcode-update`), теряется
  только обогащение общей базы. Цена потери низкая, механика — другая.
- **Политика повтора:** попытка при возврате сети и при следующем открытии
  приложения, не по таймеру. Паузы 1 мин / 5 мин / 30 мин / 2 ч / 12 ч — это
  **минимальный интервал между попытками, а не расписание**: пришёл повод раньше
  паузы — попытка пропускается, позже — выполняется сразу. Конец один —
  **исчерпание пяти попыток**; отдельного TTL нет, иначе два таймера считают
  одно и то же и первый всегда выигрывает.
- **Исчерпание попыток** — не тост (человека может не быть на экране), а
  состояние на самом продукте: строка «в общую базу не отправлено» и действие
  «отправить заявку». Это единственный новый элемент интерфейса в задаче, на
  канвасе его нет.
- **Продукт удалён локально, пока заявка в очереди** — заявка выбрасывается
  вместе с ним, **молча**. Человек удалял продукт, а не заявку; сообщение про
  механику, которую он не заводил, только шумит.
- **Идемпотентность отложенной синхронизации** — по `id` продукта (uuid выдаётся
  при создании, `heys_core_v12.js:446`); overlay уже сверяет строки по `id` и
  `shared_origin_id` (`:4718`). Очередь хранит одну запись на `id`,
  синхронизация делает upsert по нему, ответ `pending_dup` считается успехом.
- **Такой же продукт появился в общей базе, пока личный лежал офлайн** — личный
  не трогаем: он уже стоит в приёмах, и переписывать его чужими числами значит
  менять съеденное задним числом. Заявка при ответе `exists` закрывается.
  Автослияния нет (инвариант №7 — никаких решений по форме данных).
- **`invalid_session` при повторе** — та же ветка, что и на первой попытке:
  запись выбрасывается, показывается запрос PIN. В очереди не копится.

### Очерёдность и одна коллизия — 2026-08-11

Порядок работ (решение владельца): вёрстка флоу еды сейчас → «Сохранить только
себе» → очередь заявок на модерацию → вход, когда ляжет правка PIN и придут
новые экраны от дизайнера.

**Лист «Исходы и отказ» — общий у двух задач.** Его верстает задача по флоу еды
и его же трогает «Сохранить только себе». Последовательно это безопасно,
параллельно — нет: обоим исполнителям сказать прямо, что экран один, и второй
приходит на уже свёрстанный, а не рисует свою версию.
