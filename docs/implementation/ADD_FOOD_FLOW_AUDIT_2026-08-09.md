# Флоу добавления еды: разбор по коду — 2026-08-09

**Зачем:** дизайнер собирает канвас «Добавление еды» и отказался рисовать
вслепую — на прошлых вкладках инвентарь по коду каждый раз менял решения. Здесь
факты, на которые можно опираться. Проверено четырьмя параллельными проходами по
исходникам (не по бандлам).

Смежные документы: [UI_V4_SPEC_2026-08-09](UI_V4_SPEC_2026-08-09.md) — решения
по пяти вкладкам, [`docs/ui/handoff-v4/`](../ui/handoff-v4/README.md) — макеты и
токены.

---

## 1. Сколько шагов от «+» до сохранённого приёма

**Семь экранов на мобильном.** Приём сохраняется уже на четвёртом, продукты —
надстройка сверху.

| #   | Что видит человек                                           | Условие                              |
| --- | ----------------------------------------------------------- | ------------------------------------ |
| 1   | Модалка «Выбрана другая дата»                               | только если выбранная дата ≠ сегодня |
| 2   | Полноэкранный гайд «Это — важно.» с тарелкой                | **каждый раз**, см. ниже             |
| 3   | Пикер времени: колёса часов и минут, тип приёма             |                                      |
| 4   | Самочувствие: настроение, самочувствие, стресс, комментарий | здесь приём **сохранён**             |
| 5   | Модалка выбора флоу «Добавить продукты в …»                 |                                      |
| 6   | Поиск продукта                                              |                                      |
| 7   | Граммовка, кнопка «Добавить»                                |                                      |

**Десктоп — другой путь и короче:** приём создаётся мгновенно с именем «Приём» и
пустым временем, шаги 3–5 отсутствуют. Гард даты и гайд с тарелкой остаются.

**Третий путь** — мобильный fallback, если модуль пикера не загрузился:
bottom-sheet из двух шагов, без модалки выбора флоу.

**Добавление продукта в существующий приём — два видимых шага:** поиск → граммы.
В мастере объявлено пять шагов, но три (`create`, `portions`, `harm`) помечены
скрытыми и всплывают только при создании нового продукта.

### Гайд с тарелкой — не пустое состояние, а обучалка на каждый приём

Полноэкранная плашка с фото тарелки, выносками «½ овощи и фрукты · ¼ белок · ¼
крупы» и четырьмя эффектами (сердце, сахар крови, мозг, кишечник) показывается
**при каждом создании приёма**. Флага «больше не показывать» нет: единственный
обход — параметр `skipPlateGuide`, и ни один вызов в кодовой базе его не
передаёт. Шесть вариантов картинки чередуются, но экран остаётся обязательным.

## 2. Режимы добавления: сколько продуктов за раз

Мультивыбора чекбоксами нет нигде. Вместо него три режима, задаваемые кнопками в
карточке приёма («⚡ Добавить 1 продукт», «2», «3», «4», «Добавить несколько»):

- **`single`** — после «Добавить» окно закрывается, экран скроллится к дневнику.
- **`repeat`** (кнопки 2/3/4) — окно **не закрывается**: счётчик уменьшается,
  выбранный продукт сбрасывается, возврат к поиску. N продуктов = N×2 шага в
  одном непрерывном окне. Граммовка предыдущего продукта переносится как
  подсказка «в прошлый раз».
- **`multi`** — после каждого продукта окно закрывается и показывается сводка:
  список приёма до шести позиций, «Итого» с цветом по качеству, «До нормы
  осталось N ккал», при переедании — «Похоже, приём уже тяжеловат». Кнопки в три
  ряда: «Завершить» / «Добавить последний», «Добавить ещё несколько», «ещё
  2/3/4». При выполненной норме заголовок меняется на «Норма выполнена» и
  запускается конфетти.

**Проблема `multi` для дизайна:** это мигание — окно закрывается, появляется
модалка, открывается новое окно, с задержками кадра и двух таймеров по 100 мс.
Бесшовный цикл в коде есть, но недостижим: выше стоит ранний выход, и в
дневниковом флоу срабатывает всегда именно он.

## 3. Откуда вызывается окно и показывается ли повторно

Плавающая кнопка 🍽️ **окно продукта не открывает** — она переключает вкладку на
дневник, скроллит к заголовку и через 800 мс запускает создание приёма, то есть
весь путь из семи шагов.

Прямые входы в окно добавления продукта: кнопки в карточке приёма, модалка сразу
после создания приёма, карточка рекомендации приёма в Инсайтах (с подставленным
поисковым запросом и граммовкой), самопереоткрытие после «Добавить последний».

Косвенный: баннер «Не заполнено приёмов» → кнопка «Заполнить» делает программный
клик по кнопке добавления в первом пустом приёме.

Повторный показ после сохранения — только в режиме `repeat`, см. выше.

## 4. Поиск продукта

### Что в выдаче

Строка результата: иконка категории, название с подсветкой совпадения, значок
общей базы, бренд, мета-строка «N ккал · Б x | Ж y | У z», счётчик «Исп.: N×»,
штрихкод. Фон карточки красится по вредности. Кнопки: избранное, штрихкод,
карандаш, удалить, скрыть.

**Ранжирование двухслойное.** Сначала движок умного поиска: релевантность по
типу совпадения (точное имя 100, начало слова 82, раскладка QWERTY 82, транслит
78, опечатка 45, фонетика 35) плюс бонусы за избранное и частоту. Затем второй
пересчёт поверх личных и общих кандидатов со своими весами. Дедуп по имени,
причём **приоритет у продукта с заполненными порциями**, а не у большего балла.

Лимиты жёсткие: личные 20, личные плюс общие 25, запрос в общую базу 30, частые
20, превью общей базы без запроса 12. Дебаунс 200 мс локально и 300 мс для общей
базы, минимум два символа.

### История и частые

Два переключаемых списка над выдачей, видны **только при пустой строке поиска**:

- **«⚡ Частые и избранные»** (по умолчанию) — окно 21 день, захардкожено. Балл
  = частота × затухание по давности. Группы: избранное с историей → используемое
  → избранное без истории → созданное за 48 часов. До 20 позиций.
- **«🕘 Недавние · 3 дня»** — сегодня и два предыдущих календарных дня, без
  лимита.

**Визуально эти списки неотличимы от результатов поиска** — та же карточка, тот
же счётчик использований. Единственный признак, в каком ты списке, — состояние
двух табов, которые исчезают при вводе текста.

### Распознавания фото нет, голосового ввода нет

Кнопка «Добавить фото» вешает снимок **на приём**, а не на продукт: клиент
сжимает до 800 px и JPEG 0.7, облачная функция складывает в объектное хранилище
и возвращает URL. Ни кандидатов, ни граммовки. Лимит 10 фото на приём.

Web Speech API в проекте реализован (русский язык, промежуточные результаты,
таймаут 10 с), но к добавлению еды не подключён ни в одном месте — работает
только в мессенджере с куратором. Возвращает строку, парсинга в продукт нет.

### Пресеты приёмов

Кнопка «Наборы» в шапке поиска. Хранятся локально. Три вида карточек:
рекомендованные из истории, свои сохранённые, пустое состояние с двумя кнопками.
Движок рекомендаций сканирует все дни в локальном хранилище, порог — комбинация
встречалась **не меньше трёх раз**, размер 2–8 продуктов, граммовка берётся как
мода по истории. Исключаются уже сохранённые, отклонённые и подмножества более
крупных комбинаций.

Внутри создания набора — **свой отдельный поиск**, примитивный `includes` по
имени с лимитом 8, без умного движка.

### Если продукт не найден

Создание нового продукта — **не форма с полями, а вставка текстовой строки**.
Есть кнопка «Скопировать промпт для ИИ»: человек идёт к внешней модели, получает
строку и вставляет обратно. Обязательны **двенадцать чисел**: ккал, углеводы,
простые, сложные, белок, жир, плохие, хорошие, транс, клетчатка, ГИ, вредность.
Кнопка «Добавить» заблокирована, пока строка не распарсилась. Название
необязательно — подставляется поисковый запрос.

После «Добавить» продукт в базу ещё не пишется: сначала шаг «Порции», затем
«Вредность», и только там сохранение.

## 5. Порция

**Четыре способа ввода на одном экране:** числовое поле (1–2000), кнопки «−/+»
шагом 10 г, ползунок (10–500, шаг 5), кнопки-порции.

**Значение по умолчанию** — каскад: граммовка из рекомендации → последняя порция
**именно этого продукта** → 100 г. Стандартная порция из карточки продукта
дефолтом не становится, она только рисуется кнопкой.

**Три набора кнопок-порций:** захардкоженные 50/100/150/200/300; порции
продукта, а при их отсутствии — автопорции по названию (около 80 паттернов: яйцо
60 г, ломтик хлеба 30 г, пельмени 5 шт 75 г, кусок пиццы 100 г, тарелка супа 300
г) с чёрным списком для жидкостей; пользовательские порции из редактора
продукта.

**Единица одна — граммы.** Поля единицы измерения у позиции нет. Штуки и стаканы
существуют только как подписи кнопок, число всегда в граммах, пересчёта нет:
ввести «2 штуки» нельзя, можно выбрать готовую порцию или набрать граммы.
Альтернативный режим ввода — ккал с обратным пересчётом, но он использует сырое
поле калорий и у продукта без него не работает.

### Редактирование

**Продукт у позиции заменить нельзя** — в модалке редактирования нет шага
поиска, только граммовка. Меняют удалением и добавлением заново.

Мобильный и десктопный пути разные: на мобильном граммовка — кнопка, открывающая
ту же модалку граммов; на десктопе — инлайновое числовое поле прямо в строке,
модалка не открывается.

Удаление: свайп на мобильном, крестик на десктопе. Есть отмена окном 4 секунды с
тостом, ставится метка удаления. Подтверждающего диалога нет. **Для изменения
граммовки отмены нет.**

Блок «Замени на …» в карточке — только текст, обработчика клика у него нет.

### Живой пересчёт

Калории и БЖУ пересчитываются на каждый рендер, до сохранения: строка калорий,
три плитки Б/Ж/У, итог по дню «+N ккал → съедено/норма (%)». Клетчатки, ГИ и
инсулиновой волны на этом экране нет.

**Калории считаются по NET Atwater: белок 3 ккал/г, а не 4.** Это системное
решение, не ошибка — планировщик держит рядом обе величины, валовую и чистую.
Следствие для макета: калории продукта не сойдутся с суммой БЖУ, посчитанной по
учебнику.

### Фото

Привязано к приёму, не к позиции. Загружается оптимистично: сразу видно
локально, параллельно уходит в облако. Миниатюры ленивые, с бейджем времени,
кружком «обработано» и часами для незалитых. Удаление с отменой 5 секунд,
реальное удаление из облака — только по истечении окна.

## 6. Название приёма и время

### Название человек не вводит текстом

Словарь: Завтрак, Перекус, Кофе-брейк, Обед, Перекус, Ужин, Перекус, Ночной
приём. Источников три, и они **дают разные ответы**:

1. **При создании** — по часам устройства, жёсткие границы: 06–10 завтрак, 10–12
   перекус, 12–15 обед, 15–18 перекус, 18–21 ужин, 21–03 ночной, 03–06 перекус.
2. **В предпросмотре пикера** — границы плавающие: если приёмов ещё нет,
   завтрак; иначе промежуток от первого приёма дня до 03:00 делится на шесть
   равных слотов. При завтраке в 07:00 слот 3 ч 20 мин, при завтраке в 11:00 — 2
   ч 40 мин.
3. **В дневнике после сохранения** — третья логика: первый приём дня **всегда**
   завтрак, дальше те же плавающие слоты, плюс коррекция по размеру приёма
   (крупный перекус повышается до обеда или ужина, а если такой уже был —
   понижается обратно).

**Следствие для дизайна: название в заголовке карточки может смениться само** —
когда человек добавит продукты и приём перевалит порог «крупного» (3 продукта,
или 200 г, или 300 ккал), либо когда добавит более ранний приём и сдвинутся все
слоты.

Ручной выбор есть — селектор в шапке карточки с вариантом «🔄 Авто». Кофе-брейка
в этом списке нет, его ставит только внешний коннектор.

### Время

Подставляется по часам устройства с округлением минут до пяти, человек сразу
видит колёса и может прокрутить. Порядок часов в колесе 03…23, затем 00, 01, 02
— сутки заканчиваются в три ночи, ночные часы хранятся как 24–26. Десктопный
путь время не спрашивает вообще, пишет пустую строку.

Изменение задним числом доступно тапом по бейджу времени; при сохранении приёмы
пересортировываются. Для чужой даты время всё равно подставляется текущее —
крутить колесо приходится вручную.

## 7. Что показывается по ходу и что предупреждает

| Где                               | Что видно                                                                                                  |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Список результатов поиска         | ккал/100 г, БЖУ/100 г, вредность **только цветом фона**                                                    |
| Экран граммовки                   | ккал, три плитки БЖУ, итог дня, вредность **только цветом шапки**                                          |
| Сводка после добавления (`multi`) | список приёма, «Итого» с цветом, остаток до нормы                                                          |
| Дневник после сохранения          | полный набор: ккал, У, простые/сложные, Б, Ж, вредные/полезные/супер, **клетчатка, ГИ, вредность** числами |

То есть клетчатка, гликемический индекс и число вредности появляются **только
после сохранения**. До него вредность передаётся цветом.

**Инсулиновая волна** пересчитывается сразу после добавления и видна в карточке
«Окно для сжигания жира» в дневнике, плюс раскрываемой секцией внутри приёма. До
сохранения она считается ровно для одного — предупреждения ниже. Прогноза «как
этот приём сдвинет волну» пользователю не показывают.

**Вредность** — шкала 0–10, обратная. Считается дозозависимо: макросы
масштабируются на граммы, ГИ и добавки нет, плюс штраф за калории порции
свыше 150. Тренировка снижает вред, и в шапке приёма тогда появляется «Еда
пойдёт в энергию, а не в жир». Расхождение в порогах: цвет и подсказка в строке
работают по границам 2/4/6, а категории («Полезный», «Нейтральный», «Вредный») —
по 1/2.5/4/5.5/7/8.5.

### Шесть предупреждений во всём флоу

1. **Гайд с тарелкой** — каждый раз, см. раздел 1.
2. **«Выбрана другая дата»** — жёсткий гард с двумя кнопками.
3. **Ночной час** — мягкая подсказка «запишется в <дата>» при часах 00–03.
4. **Инсулиновая волна** — «Расчётный постпрандиальный период ещё продолжается»,
   кнопки «Подождать» и «Всё равно добавить». Показывается **один раз**, только
   по нажатию «Далее», и пропускается при дефиците от 10 %, при чужой дате, при
   пустом дне и при времени дальше получаса от текущего.
5. **Дубль продукта в приёме** — «Уже добавлено N г… иначе еда посчитается
   дважды».
6. **«Приём уже тяжеловат»** — единственный намёк на перебор, и только **после**
   сохранения, в сводке.

**Отдельного «мало белка» нет.** Дефицит белка считается и влияет на цвет
колонки, но в поток добавления не выводится. Формулировки вроде «переедание»,
«тяжёлая еда ночью», «поздно» в коде есть, но пользователю не показываются — они
только переключают цвет и одну общую фразу.

## Что из этого стоит решать, а не просто рисовать

Список наблюдений, каждое — кандидат в отдельную задачу. Решения по ним нет.

- **Семь шагов до первого продукта** — главный кандидат на сокращение. Гайд с
  тарелкой без флага «больше не показывать» стоит первым в очереди.
- **Мигание в режиме `multi`** — бесшовный цикл в коде уже написан, но
  недостижим из-за раннего выхода.
- **Три разные логики названия приёма**, из-за которых заголовок меняется сам.
- **Частые, недавние и результаты поиска визуально неразличимы.**
- **Продукт у позиции нельзя заменить**, только удалить и добавить заново.
- **Создание продукта через вставку строки из двенадцати чисел** — работает, но
  предполагает поход к внешней модели посреди добавления еды.
- **Мёртвые механизмы:** история граммовок пишется и синхронизируется, но не
  читается никогда; история порций всегда пуста, потому что функция записи не
  вызывается, и подсветка «рекомендованной» порции из-за этого не работает.
- **Тумблер «Общие» включён по умолчанию**, поэтому запасной блок «Искать в
  общих» практически никогда не показывается.
- **Подтверждения деструктивных действий — нативные `confirm()`**, не в стиле
  модалок приложения.
