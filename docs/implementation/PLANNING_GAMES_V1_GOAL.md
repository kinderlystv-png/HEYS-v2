# Цель: три лёгкие мини-игры в Planning

> **Статус:** финальный промпт после архитектурного и продуктового аудита.
> Документ предназначен для назначения Codex как самостоятельной цели.
> Реализация, staging, commit, push, PR и deploy этим документом не выполнены.

## Промпт цели

Ты работаешь в репозитории `HEYS-v2`.

Реализуй три законченные, визуально аккуратные и очень лёгкие мини-игры в
подвкладке «Задачи → Игры»:

1. «Собери слово» — игра на слоговое чтение для ребёнка 7–8 лет.
2. «Маршрут робота» — спокойная логическая игра на планирование
   последовательности действий.
3. «Цветной след» — динамическая offline-аркада про замыкание контуров и захват
   территории.

Это должны быть полностью играбельные версии v1, а не заглушки, концепты или
демонстрационные прототипы.

Главная системная цель: почти нулевая стоимость до открытия конкретной игры.
Код, данные и CSS каждой игры загружаются только после клика по её карточке.

Никаких тяжёлых игровых движков, новых npm-зависимостей, WebGL, Web Workers,
серверной логики, сетевого мультиплеера, внешних ассетов, фонового прогрева или
новой архитектурной платформы.

---

# 1. Приоритеты

Работай в следующем порядке:

P0. Корректность механик, настоящий on-demand loader и полная очистка ресурсов.

P1. Три законченные игровые сессии с понятным детским UX.

P2. Тесты, bundle isolation, документация и browser smoke.

P3. Визуальная полировка строго внутри performance-бюджета.

Если требования конфликтуют, упрощай визуальную часть или игровую механику, но
не нарушай lazy-loading, lifecycle cleanup и ownership.

Не создавай универсальный игровой фреймворк. Реализуй ровно то, что необходимо
этим трём играм.

# 2. Организация работы

Используй одного главного агента и ровно трёх игровых субагентов.

Не имитируй работу субагентов текстом. Если среда фактически не поддерживает
субагентов, явно сообщи об этом и не выдавай последовательную работу одного
агента за параллельную.

Используй субагентов только для независимых частей, которые действительно
выгодно выполнять параллельно. В этой задаче такими частями являются три
изолированных игровых модуля; общий shell, loader, навигация, документация и
интеграция остаются у главного агента.

До запуска субагентов главный агент обязан:

1. Изучить существующую архитектуру.
2. Зафиксировать общий runtime-контракт.
3. Зафиксировать точный ownership.
4. Записать контракт и ownership в
   `docs/implementation/PLANNING_GAMES_UI_PROTOCOL.md`.
5. Передать каждому субагенту только его файлы, API и тестовые инварианты.

Все общие файлы изменяет только главный агент.

## 2.5. Handoff субагентов

Каждый субагент обязан сообщить главному агенту:

- какие файлы изменены;
- какая механика реализована;
- какой публичный `api` зарегистрирован;
- какие тесты запускались;
- результаты тестов;
- размеры JS и CSS;
- какие ограничения или риски остались.

Главный агент не принимает handoff вслепую.

Он обязан проверить:

- фактический diff;
- отсутствие правок вне ownership;
- соответствие runtime-контракту;
- отсутствие side effects до mount;
- cleanup после unmount;
- тестовые инварианты;
- размеры файлов;
- отсутствие общих CSS-селекторов.

# 3. Shared workspace и безопасность Git

В этом workspace могут одновременно работать агенты из других чатов.

В этом же workspace могут параллельно работать агенты из других чатов. Перед
правками проверь текущее состояние файлов и `git status`, изменяй только свой
согласованный scope, не откатывай и не перезаписывай чужие изменения. Если
обнаружено пересечение по тем же файлам или тесно связанным контрактам,
используй доступный межзадачный канал: сообщи владельцу точные файлы/контракты,
согласуй границы и одного writer'а. Пока ждёшь ответа, продолжай только
независимую часть. Если канала нет или ownership не согласован, остановись и
явно сообщи о конфликте вместо молчаливого разрешения. Перед handoff или
освобождением scope отправь владельцу краткий итог: что изменено, какие проверки
прошли и какие риски остались.

Перед любыми правками выполни:

- `git status --short`
- `git diff -- apps/web/heys_planning_v1.js apps/web/heys_app_shell_v1.js apps/web/styles/main-deferred.css apps/web/styles/modules/908-planning-games.css apps/web/__tests__/planning-games-ui.test.js apps/web/__tests__/planning-home-subtab.test.js docs/reference/systems/PLANNING.md docs/implementation/PLANNING_GAMES_UI_PROTOCOL.md`

Текущие Games-файлы уже могут быть dirty или untracked после предыдущей задачи.

Не считай их чистой baseline.

Не пересоздавай их с нуля, пока не изучишь текущий diff.

Запрещено использовать для разрешения конфликтов:

- `git reset`
- `git checkout --`
- `git restore`
- `git clean`
- `git stash`
- откат чужих коммитов
- перезапись чужих файлов целиком

Изменяй только согласованный scope.

Если обнаружено пересечение по тем же файлам или тесно связанным
runtime-контрактам:

1. Используй доступный межзадачный канал.
2. Сообщи владельцу точные файлы и контракты.
3. Согласуй одного writer.
4. Пока ждёшь ответа, продолжай только независимую работу.
5. Если канала нет или ownership не согласован, остановись и явно сообщи о
   конфликте.

Перед освобождением scope отправь владельцу краткий итог:

- что изменено;
- какие проверки прошли;
- какие риски остались.

# 7. Общий UX-гейт

Цель интерфейса — дать ребёнку три короткие понятные игры без визуального или
когнитивного перегруза.

Основное действие: открыть выбранную карточку и сразу понять, как начать.

Слой 1:

- заголовок «Игры»;
- три игровые карточки.

Слой 2:

- fullscreen-dialog;
- название;
- короткая инструкция;
- состояние загрузки или ошибки;
- видимая кнопка назад;
- перезапуск;
- пауза в динамической игре;
- понятная причина результата.

Не используй в клиентском UI формулировку «подготовка к школе».

В 7–8 лет ребёнок обычно уже учится.

Категория первой игры — «Чтение».

Интерактивные цели:

- минимум 48×48 CSS px;
- достаточный промежуток между соседними кнопками;
- доступность touch, mouse и keyboard.

Общий визуальный язык:

- чисто;
- тепло;
- спокойно;
- премиально;
- без неона;
- без стилистики магазина мобильных игр;
- без растровых картинок;
- без внешних шрифтов;
- без тяжёлых теней;
- без blur-фильтров;
- светлая и тёмная темы;
- корректный `prefers-reduced-motion`.

# 9. Fullscreen-shell

Сохрани существующий принцип книжного reader:

- portal;
- `role="dialog"`;
- `aria-modal="true"`;
- фоновые элементы получают `inert`;
- body scroll lock;
- закрытие по Escape;
- видимая кнопка назад;
- возврат фокуса на исходную карточку.

При закрытии полностью восстанови прежние значения:

- `inert`;
- `aria-hidden`, если оно изменялось;
- body overflow и связанные классы;
- фокус.

Не предполагай, что исходное значение всегда отсутствовало.

## 9.1. Focus trap

Исправь текущий focus trap.

Запрещено при каждом Tab возвращать фокус только на кнопку назад.

Используй паттерн reader:

1. При каждом Tab заново получай список доступных focusable-элементов внутри
   dialog.
2. Учитывай элементы, появившиеся после lazy-load.
3. Обычный Tab должен перемещаться между игровыми контролами естественно.
4. На последнем элементе Tab переводит на первый.
5. На первом элементе Shift+Tab переводит на последний.
6. Disabled, hidden и `tabindex="-1"` элементы не включаются.
7. Если доступен только один контрол, фокус остаётся на нём.
8. После загрузки игры не отбирай фокус у пользователя без необходимости.

Номер справа в header бери из metadata выбранной игры: `01`, `02`, `03`.

Не хардкодь `01`.

# 11. Loader state machine

Общий loader остаётся в `apps/web/heys_planning_v1.js`.

Для каждого `gameId` храни metadata:

- `id`;
- `title`;
- `category`;
- `number`;
- `scriptUrl`;
- `styleUrl`;
- `expectedModuleId`;
- `preloaderType`.

Для каждого `gameId` храни независимое runtime-состояние:

- `idle`;
- `loading`;
- `ready`;
- `error`.

Переходы:

- `idle → loading` после пользовательского клика;
- `loading → ready` только после готовности JS, CSS и ожидаемого модуля;
- `loading → error` при ошибке JS, CSS или отсутствии регистрации;
- `error → loading` после Retry;
- `ready` сохраняется до перезагрузки приложения.

## 11.1. Условия загрузки

Loader обязан:

- начинать загрузку только после клика по карточке;
- сразу открыть fullscreen-shell;
- сразу показать прелоадер выбранной игры;
- параллельно начать загрузку JS и CSS;
- не монтировать игру до готовности обоих ресурсов;
- добавлять `?v=${encodeURIComponent(HEYS.version)}`, если версия существует;
- не добавлять пустой `?v=`;
- использовать same-origin относительные URL;
- соблюдать существующий CSP nonce, если он необходим;
- использовать независимый cached Promise для каждого `gameId`;
- coalesce параллельные запросы одной игры;
- не создавать повторные `<script>` и `<link>`;
- не загружать B или C при открытии A;
- после `script.onload` проверять ожидаемую регистрацию модуля;
- считать отсутствие модуля ошибкой;
- корректно переживать закрытие dialog во время загрузки;
- не монтировать игру в уже закрытый или заменённый shell.

## 11.2. Session token

Каждому открытому экземпляру fullscreen-shell присвой уникальный token.

После завершения async-load перед mount проверь:

- shell ещё существует;
- token совпадает;
- активный `gameId` не изменился;
- shell не находится в процессе закрытия.

Сам сетевой запрос можно не отменять, но поздний результат не должен монтировать
компонент.

## 11.3. Resource nodes

Каждый динамический node получает диагностические атрибуты:

- тип ресурса;
- `gameId`;
- URL;
- номер попытки.

Используй стабильный `data-*` контракт для тестов.

Не ищи ресурсы только по нечёткому совпадению URL.

## 11.4. Ошибки и Retry

JS и CSS отслеживаются независимо.

Если ресурс не загрузился:

- удали failed node;
- сбрось failed Promise;
- сохрани успешно загрузившийся второй ресурс;
- не создавай его повторно;
- переведи игру в `error`;
- покажи Retry.

Если script загрузился, но модуль не зарегистрирован:

- считай script невалидным;
- удали его node;
- сбрось JS-состояние;
- не монтируй игру;
- разреши повторную попытку.

Retry обязан реально создать новую попытку для отсутствующего или failed
ресурса.

Не добавляй искусственный timeout загрузки без существующего проектного
паттерна.

# 12. Runtime-контракт игровых модулей

Каждый игровой script синхронно при выполнении регистрирует:

`HEYS.PlanningGames.modules[gameId] = { Component, api }`

Namespace создаётся идемпотентно.

Не перезаписывай существующие соседние namespaces.

## 12.1. Component

`Component` получает props:

- `onExit`
- `reducedMotion`
- необязательный `seed` для тестового harness

Компонент:

- не запускается до mount;

- не пишет в storage;
- не выполняет сеть;
- не отправляет аналитику.

`api` содержит:

- `version: 1`;
- чистые функции механики;
- функции валидации статического контента;
- deterministic entry points для тестов.

Вызов `api` не должен:

- создавать DOM;
- запускать RAF;
- запускать timeout или interval;
- подписываться на события;
- обращаться к сети или storage.

Минимальный game-specific API:

### Word Builder

- `validateContent()`
- `createSession({ seed })`

### Robot Route

- `validateLevels()`
- `createSession({ seed })`

### Color Trail

- `createWorld({ seed })`
- `stepWorld(world, input, fixedDelta)`
- `closeTrail(world, actorId)`
- `getTerritoryPercent(world, actorId)`
- `validateWorld(world)`

Названия можно минимально адаптировать к существующему стилю, но общий смысл и
тестируемость должны сохраниться.

# 13. Lifecycle-контракт

- таймеры;
- RAF;
- intervals;
- listeners;

- Canvas context;

- пометить экземпляр уничтоженным;
- очистить ссылки на Canvas и offscreen canvas.

Каждый callback после асинхронной задержки сначала проверяет, что экземпляр ещё

Не оставляй глобальные обработчики между открытиями игры.

# 16. Игра 1 — «Собери слово»

Цель — тренировать слоговое чтение и понимание структуры простых русских слов.

Одна сессия:

- 6 разных слов;
- примерно 2–3 минуты;
- без таймера;
- без штрафов.

## 16.1. Модель данных

Используй структуру, эквивалентную:

- `id`
- `answer`
- `correctSyllables`
- необязательный `distractor`

Каждый правильный слог:

- имеет уникальный option ID;
- содержит отображаемый текст.

Distractor:

- имеет отдельный уникальный option ID;
- не входит в `correctSyllables`.

Инварианты:

- `answer === correctSyllables.map(item => item.text).join('')`;
- правильных слогов 2–3;
- distractor максимум один;
- видимых кнопок 2–4;
- word ID уникальны;
- option ID уникальны в пределах раунда;
- повторяющийся текст слога допустим, например два одинаковых слога;
- все слова написаны кириллицей;
- `Ё` не заменяется на `Е`;
- никаких смешанных латинских символов.

## 16.2. Банк слов

Подготовь минимум 30 вручную проверенных слов.

Для v1 используй только:

- простые общеупотребительные слова;
- 2–3 слога;
- понятные ребёнку 7–8 лет;
- однозначное деление;
- простые случаи без спорного стечения согласных на границе слогов.

Не используй:

- редкие слова;
- профессиональные термины;
- имена собственные;
- аббревиатуры;
- слова с несколькими допустимыми учебными вариантами деления;
- сомнительные автоматические результаты syllabification;
- случайно сгенерированные слоги.

Пример:

- `РА`
- `КЕ`
- `ТА`
- ответ: `РАКЕТА`

Статический банк слов и distractors находится только в game-specific JS.

## 16.3. Формирование сессии

Используй подменяемый seeded RNG и Fisher–Yates или эквивалентное честное
перемешивание.

Сессия состоит из:

- раундов 1–2: два правильных слога, без distractor;
- раундов 3–4: три правильных слога, без distractor;
- раундов 5–6: два или три правильных слога и максимум один очевидный
  distractor.

В одной сессии:

- ровно 6 слов;
- слова не повторяются;
- порядок слогов перемешан;
- distractor не образует альтернативный правильный ответ.

## 16.4. Механика

- Сверху крупно показывается целевое слово.
- Ниже находятся перемешанные кнопки-слоги.
- Ребёнок нажимает слоги по порядку.
- Выбранные слоги заполняют строку ответа.
- Выбранная кнопка временно disabled.
- Drag-and-drop не использовать.
- Проверка происходит после заполнения количества позиций, равного числу
  правильных слогов.

## 16.5. Feedback

При успехе:

- слово собирается целиком;
- появляется спокойная подсветка;
- статус: «Готово»;
- появляется кнопка «Дальше».

При ошибке:

- статус: «Попробуй ещё»;
- нет красного креста;
- нет звука ошибки;
- нет потери жизни;
- выбранные слоги возвращаются;
- ребёнок может сразу повторить.

После двух ошибок на одном слове:

- мягко выдели первый правильный слог;
- не раскрывай весь ответ;
- сбрось счётчик ошибок после успешного ответа.

После шести слов:

- короткий нейтральный результат;
- кнопка «Сыграть ещё»;
- кнопка выхода через `onExit`.

Все timeout, использованные для краткого feedback, хранятся и очищаются на
unmount.

Постоянного animation loop нет.

Игра полностью event-driven.

## 16.6. Тесты Word Builder

Проверь:

- минимум 30 слов;
- уникальные word ID;
- уникальные option ID;
- корректную сборку `answer`;
- 2–3 правильных слога;
- максимум один distractor;
- 2–4 видимых option;
- distractor не входит в ответ;
- повторяющиеся тексты слогов не ломают ID;
- ровно 6 разных слов в сессии;
- правильное распределение сложности;
- deterministic seed;
- правильный и неправильный ответ;
- hint после двух ошибок;
- отсутствие сети и storage;
- cleanup timeout после unmount.

# 17. Игра 2 — «Маршрут робота»

Цель — тренировать пространственное планирование и короткие алгоритмические
последовательности.

Одна сессия:

- 5 маршрутов;
- без таймера;
- без наказания за попытки.

## 17.1. Модель уровня

Каждый уровень содержит:

- уникальный `id`;
- `tier`;
- размер поля;
- `start`;
- `goal`;
- `obstacles`;
- `expectedShortestPath`;
- `hintFirstMove`.

Координаты:

- целые;
- находятся внутри поля;
- не дублируются.

## 17.2. Набор уровней

Подготовь минимум 12 статических вручную проверенных уровней:

### Tier 1

- поле 4×4;
- маршрут 3–4 шага;
- без препятствия или с одним очевидным препятствием.

### Tier 2

- поле 4×4 или 5×5;
- одно-два препятствия;
- короткий обход.

### Tier 3

- поле 5×5;
- маршрут 5–8 шагов;
- понятный, но не прямой обход.

Запрещены:

- ключи;
- двери;
- телепорты;
- переключатели;
- движущиеся препятствия;
- дополнительные типы клеток.

Программа ограничена 12 командами.

## 17.3. Формирование сессии

Используй подменяемый seeded RNG.

Сессия содержит 5 разных уровней:

- один из Tier 1;
- два из Tier 2;
- два из Tier 3.

Уровни не повторяются.

Повторная игра создаёт новую сессию только в памяти.

## 17.4. Механика

Поле состоит из обычных DOM-ячеек.

Ребёнок набирает программу кнопками:

- `↑`
- `↓`
- `←`
- `→`

Доступны:

- «Удалить ход»;
- «Начать заново»;
- «Поехали».

Во время выполнения программы:

- кнопки добавления команд disabled;
- повторный запуск disabled;
- робот исполняет команды по очереди.

Клавиатура:

- стрелки добавляют соответствующую команду;
- WASD добавляет соответствующую команду;
- Backspace удаляет последний ход;
- Enter запускает программу;
- клавиши обрабатываются только внутри активной игры;
- не перехватывай ввод в обычных кнопках или других полях.

## 17.5. Выполнение программы

Чистый reducer обязан:

- не выпускать робота за границы;
- не проводить через препятствия;
- фиксировать достижение цели сразу;
- остановить оставшиеся команды после достижения цели.

Ошибка возникает, если:

- команда ведёт за границу;
- команда ведёт в препятствие;
- программа завершилась до достижения цели.

При ошибке:

- робот возвращается на start;
- введённая программа сохраняется;
- ребёнок может удалить или добавить команды;
- попытка не штрафуется.

После двух неудачных запусков уровня:

- подсвети только `hintFirstMove`;
- hint должен быть первым шагом хотя бы одного кратчайшего маршрута.

При успехе:

- спокойная подсветка;
- кнопка перехода к следующему уровню.

После пяти маршрутов:

- короткий результат;
- «Сыграть ещё»;
- выход.

## 17.6. Анимация

- Никакого Canvas.
- Никакого RAF.
- Никакого постоянного loop.
- Допустимы только короткие CSS transitions и последовательные timeout во время
  выполнения программы.
- Reduced motion выполняет программу без промежуточных перемещений.
- Все timeout очищаются при restart, close и unmount.

## 17.7. Тесты Robot Route

Для каждого уровня запускай BFS.

Проверь:

- start внутри поля;
- goal внутри поля;
- obstacles внутри поля;
- start и goal не совпадают;
- start и goal не входят в obstacles;
- obstacles уникальны;
- уровень достижим;
- BFS-длина совпадает с `expectedShortestPath`;
- `hintFirstMove` начинает хотя бы один кратчайший путь;
- reducer не выходит за границы;
- reducer не проходит через obstacle;
- успех фиксируется сразу;
- лишние команды после goal не исполняются;
- программа ограничена 12 командами;
- session содержит 5 разных уровней нужных tier;
- fixed seed даёт одинаковую сессию;
- timeout очищаются при unmount.

# 18. Игра 3 — «Цветной след»

Это оригинальная offline-игра с одним игроком и тремя локальными ботами.

Не используй:

- WebGL;
- physics engine;
- сторонние библиотеки;
- npm-пакеты;
- сервер;
- WebSocket;
- multiplayer;
- storage;
- аналитику.

## 18.1. Игровой цикл

Игрок безопасен внутри своей территории.

После выхода из своей территории:

- начинается активный уязвимый след;
- чем дольше вылазка, тем длиннее остаётся открытый след;
- отдельного штрафа за расстояние нет.

После возвращения в свою территорию:

- контур анализируется;
- при валидном замыкании окружённая область и след становятся территорией
  игрока;
- при отсутствии реально окружённой области след просто очищается и территория
  не меняется.

Другой актор может:

- пересечь открытый след и сбросить его владельца;
- замкнуть собственный контур вокруг части чужой территории;
- перекрасить реально окружённый участок.

Твёрдая территория сама по себе не наносит поражение.

## 18.2. Состояния экрана

После загрузки модуль находится в состоянии `ready`, но раунд ещё не идёт.

Покажи:

- короткую инструкцию;
- кнопку «Начать».

Таймер 90 секунд начинается только после нажатия «Начать».

Состояния:

- `ready`;
- `running`;
- `paused`;
- `result`.

Во время `running` доступна видимая кнопка паузы.

При `visibilitychange` в hidden:

- немедленно останови simulation;
- отмени RAF;
- переведи игру в `paused`.

После возвращения на вкладку:

- не продолжай автоматически;
- покажи «Продолжить»;
- после продолжения сбрось накопленный delta.

В `result`:

- loop остановлен;
- input игры отключён;
- показывается только процент территории игрока;
- нет рейтинга;
- нет сравнения с другими детьми;
- доступны «Сыграть ещё» и выход.

## 18.3. Поле и акторы

Логическое поле:

- width: 64 клетки;
- height: 96 клеток;
- всего 6144 клетки.

Акторы:

- 1 игрок;
- 3 бота;
- максимум 4 актора.

Начальные территории:

- не пересекаются;
- расположены с достаточным расстоянием;
- имеют фиксированные или seeded anchors;
- дают каждому актору небольшое ядро;
- не создают столкновение сразу после старта.

Рекомендуемый размер начального ядра:

- 5×5 клеток или меньше, если это лучше соответствует балансу.

## 18.4. Представление данных

Используй typed arrays:

- `owner: Uint8Array`
- `trail: Uint8Array`
- `visited: Uint8Array`
- `newTrailMask: Uint8Array` или эквивалент
- заранее выделенную очередь `Int32Array` для flood-fill

Значения:

- `0` — нейтральная клетка;
- `1–4` — actor ID.

Для каждого актора храни заранее выделенный буфер клеток текущей вылазки или
эквивалентную структуру без аллокаций в hot loop.

Не создавай новые массивы, Map, Set или объекты на каждом simulation tick.

Небольшой фиксированный массив из четырёх actor-state допустим.

## 18.5. Движение игрока

Игрок движется с постоянной скоростью.

Управление pointer:

- `pointerdown` задаёт цель и включает pointer capture;
- `pointermove` только обновляет последние координаты цели;
- не вызывает React setState;
- `pointerup` освобождает capture;
- после pointer-up движение продолжается по последнему курсу;
- обработай `pointercancel`;
- обработай `lostpointercapture`.

Змейка плавно поворачивает к последней точке пальца или мыши.

Используй ограниченную скорость поворота, а не мгновенный teleport направления.

Добавь небольшую dead zone около головы, чтобы исключить дрожание направления.

Координаты pointer корректно переводятся из CSS-размера Canvas в логические
координаты поля.

Keyboard fallback:

- стрелки;
- WASD.

Клавиши изменяют желаемое направление.

Не блокируй стрелки глобально вне активной игры.

Canvas должен быть focusable и иметь понятный `aria-label`.

## 18.6. След

Внутри своей территории актор:

- не оставляет след;
- считается безопасным.

При переходе из своей территории наружу:

- начинается новая вылазка;
- каждую пройденную внешнюю клетку добавляй в активный след.

При возвращении в любую клетку своей территории:

- попытайся закрыть контур.

Если buffer следа переполнен:

- безопасно сбрось актора;
- не выходи за пределы typed arrays.

## 18.7. Swept-grid

На каждом tick используй swept-grid/DDA или эквивалентный дискретный проход по
всем пересечённым клеткам.

Быстро движущийся актор не должен:

- перескакивать через чужой след;
- перескакивать через собственный след;
- пропускать возвращение в территорию;
- оставлять разрывы в своём trail.

DDA пишет клетки в заранее выделенный per-actor buffer текущего tick.

## 18.8. Двухфазный simulation tick

Не изменяй world последовательно для каждого актора.

Используй двухфазный tick.

### Фаза A — намерения

Для всех активных акторов:

1. Рассчитай новое положение.
2. Рассчитай swept cells.
3. Сохрани intended movement в заранее выделенные buffers.
4. Не изменяй `owner` и `trail`.

### Фаза B — столкновения

На общем снимке мира определи:

1. Пересечение существующего активного trail.
2. Самопересечение.
3. Пересечение intended paths двух акторов.
4. Совпадение конечных head cells.
5. Обмен head cells за один tick.

### Фаза C — reset marks

Сначала отметь всех акторов, которые должны быть сброшены.

Не выполняй reset немедленно в середине проверки другого актора.

### Фаза D — commit движения

- Акторы, помеченные на reset, не записывают новый trail.
- Выжившие акторы записывают движение.
- Атакующий продолжает движение, если сам не попал под другое правило.

### Фаза E — замыкания

- Только выжившие акторы могут закрывать контур.
- Одновременные замыкания обрабатываются в стабильном порядке `actorId`.

Так результат не зависит от порядка итерации массива акторов.

## 18.9. Порядок коллизий

На каждом simulation tick:

1. Рассчитать swept paths всех акторов.
2. Пересечение активного чужого trail сбрасывает владельца trail.
3. Самопересечение сбрасывает самого актора.
4. Одновременное head-to-head сбрасывает обоих.
5. Shared intended cell двух голов считается head-to-head.
6. Обмен предыдущими head cells считается head-to-head.
7. Только выжившие акторы записывают движение.
8. Только выжившие акторы закрывают контуры.
9. Одновременные закрытия идут по `actorId`.

Если два актора одновременно пересекли следы друг друга, оба владельца могут
быть сброшены.

Одна клетка не может иметь двух владельцев.

## 18.10. Reset актора

При reset:

- очисти только незамкнутый trail актора;
- уже захваченная территория остаётся;
- актор переходит в короткое состояние respawn;
- не используй отдельный real-time timeout, если это можно выразить simulation
  timestamp;
- во время respawn актор не участвует в коллизиях;
- затем мягко верни его в собственную территорию.

Если у актора не осталось собственной территории:

- создай маленькое новое ядро;
- используй детерминированный безопасный поиск позиции;
- не размещай ядро поверх активной головы или trail;
- не допускай выхода за поле;
- редкий O(grid) поиск здесь допустим, потому что это не hot loop.

Не показывай:

- «Ты погиб»;
- «Убит»;
- жизни;
- полный game over.

Допустимый нейтральный текст:

- «След прерван»
- «Возвращаемся»

## 18.11. Валидное замыкание

Возвращение в свою территорию само по себе ещё не гарантирует захват.

Замыкание считается валидным только если новый trail вместе с существующей
территорией создаёт хотя бы одну реально окружённую клетку.

Если после анализа:

- не найдено ни одной окружённой клетки вне trail,

то:

- trail очищается;
- `owner` не изменяется;
- процент территории не увеличивается.

Это исключает захват простой полосы при коротком выходе и немедленном возврате.

## 18.12. Алгоритм захвата территории

Не используй polygon geometry.

Новый trail во время анализа рассматривается как временный барьер через
`newTrailMask`.

Не обязательно заранее изменять `owner`.

Если всё же временно меняешь `owner`, обязан полностью сохранять и
восстанавливать предыдущих владельцев при невалидном замыкании. Предпочтителен
вариант без временной мутации `owner`.

Алгоритм:

1. Построй `newTrailMask` из активной вылазки actor.
2. Считай барьерами:
   - текущую территорию actor;
   - `newTrailMask`.

3. Запусти 4-neighbor flood-fill по остальным клеткам.
4. Seeds:
   - доступные клетки всех четырёх краёв поля;
   - клетки живых голов соперников.

5. Всё достижимое от края считается внешним миром.
6. Компонент, достижимый от живой головы соперника, защищён от перекраски.
7. Чужая твёрдая территория считается проходимой для анализа.
8. После seed flood-fill проверь закрытые компоненты, соприкасающиеся с
   `newTrailMask`.
9. Захватывай только закрытые компоненты, соприкасающиеся с новым trail.
10. Не захватывай старую внутреннюю полость, не связанную с текущей вылазкой.
11. Подсчитай окружённые клетки, не включая сам trail.
12. Если окружённых клеток ноль, откати вылазку без изменения `owner`.
13. Если окружённые клетки есть, в одном JS tick:
    - назначь actor владельцем trail;
    - назначь actor владельцем захваченных компонентов;
    - очисти `trail`;
    - очисти `newTrailMask`;
    - обнови territory cache.

Flood-fill выполняется только при замыкании, а не каждый кадр.

## 18.13. Боты

Используй небольшую FSM:

- `HOME`
- `EXIT`
- `SIDE`
- `RETURN`
- необязательная короткая `ATTACK`

Боты:

- принимают решения примерно 10 раз в секунду;
- используют seeded RNG;
- движутся со скоростью 85–95% скорости игрока;
- выходят на 4–10 клеток;
- делают боковой участок 3–8 клеток;
- возвращаются раньше при длинном trail;
- возвращаются раньше при близком сопернике;
- иногда пытаются пересечь короткий близкий чужой trail;
- не преследуют ребёнка постоянно;
- не играют идеально;
- не используют A\*;
- не выполняют полный BFS каждый decision tick.

Для атаки используй только лёгкую локальную эвристику:

- ограниченный радиус;
- проверка нескольких candidate headings;
- Manhattan distance или локальный score;
- отсутствие тяжёлого pathfinding.

Вероятность атаки должна быть небольшой и seeded.

Главная цель бота — иногда расширять собственную территорию, а не охотиться за
игроком.

## 18.14. Производительность Canvas

Используй:

- один видимый Canvas;
- максимум один внутренний offscreen canvas для редко меняющейся территории;
- один RAF-driver;
- fixed simulation step 30 Гц;
- bots decision 10 Гц;
- render не чаще 30 Гц;
- accumulator;
- максимум три catch-up шага за кадр;
- discard большого delta после pause или hidden;
- DPR `Math.min(devicePixelRatio || 1, 1.5)` или эквивалентный лимит;
- максимум 4 actor;
- 6144 логические клетки.

Не используй `setInterval` для game loop.

RAF существует только в состоянии `running`.

Offscreen territory canvas обновляется только:

- после успешного замыкания;
- после reset core;
- после нового раунда;
- после resize, если это необходимо.

Не создавай массивы и объекты в hot loop.

Не вызывай React setState:

- из `pointermove`;
- на каждом simulation tick;
- на каждом render.

DOM HUD обновляй не чаще четырёх раз в секунду, предпочтительно раз в секунду
для таймера и процента.

Не используй:

- `shadowBlur`;
- частицы;
- screen shake;
- glow;
- blur;
- Canvas text в каждом кадре;
- сложные градиенты в hot loop;
- перерисовку статической территории примитив за примитивом каждый кадр.

`touch-action: none` применяется только к игровому Canvas.

## 18.15. Resize

Canvas сохраняет логическое соотношение поля 64:96.

На мобильном:

- помещается по доступной ширине и высоте;
- не создаёт горизонтальный overflow.

На desktop:

- имеет разумный max-size;
- не растягивается на весь широкий экран.

Для resize разрешён один `ResizeObserver` только во время mount.

Observer обязан отключаться на unmount.

## 18.16. Reduced motion

«Цветной след» является игрой с существенным движением, поэтому полностью
отключить движение нельзя без разрушения механики.

При `prefers-reduced-motion`:

- отключи декоративные пульсации;
- отключи лишние переходы;
- не добавляй zoom, shake или частицы;
- сохрани только движение, необходимое для игры;
- оставь render limit 30 Гц.

## 18.17. Тесты Color Trail

Обязательно проверь:

- `owner`, `trail` и buffers имеют правильный размер;
- spawn cores не пересекаются;
- DDA создаёт непрерывный trail;
- быстрый объект не перескакивает через trail;
- короткий выход и возврат без окружённой клетки ничего не захватывает;
- корректный контур захватывает нужный компонент;
- старый несвязанный внутренний компонент не захватывается;
- компонент с живой головой соперника защищён;
- чужой контур может перекрасить реально окружённый кусок;
- чужая территория проходима для flood-fill анализа;
- пересечение trail сбрасывает правильного владельца;
- атакующий продолжает движение;
- самопересечение сбрасывает самого себя;
- simultaneous head-to-head сбрасывает обоих;
- результат не зависит от порядка actor array;
- одновременные замыкания идут по `actorId`;
- одна клетка имеет одного owner;
- процент всегда 0–100;
- fixed seed даёт одинаковый мир и bot decisions;
- territory остаётся после reset;
- при полном отсутствии территории создаётся новое ядро;
- pause останавливает simulation;
- hidden останавливает simulation;
- result останавливает simulation;
- close/unmount отменяет RAF;
- close/unmount удаляет listeners и observer.

6. Повторно открой загруженную игру.
7. Убедись, что нет нового resource node и нового запроса.

Для проверки прелоадера разрешено задержать ответ через browser routing.

Для проверки Retry:

- один раз искусственно отклони JS или CSS;
- проверь error state;
- нажми Retry;
- разреши второй запрос;
- проверь успешный mount.

## 24.3. Gameplay smoke

Проверь:

### «Собери слово»

- одна полная сессия из шести слов;
- правильный ответ;
- ошибка;
- hint после двух ошибок;
- повторная игра.

### «Маршрут робота»

- добавление команд;
- удаление команды;
- столкновение с obstacle;
- исправление программы;
- успешный маршрут;
- один полный набор из пяти уровней.

### «Цветной след»

- игра не стартует до «Начать»;
- pointer управляет курсом;
- pointer-up сохраняет курс;
- keyboard fallback работает;
- выход из территории создаёт непрерывный след;
- валидная петля добавляет территорию;
- короткая невалидная петля не добавляет территорию;
- чужой актор может пересечь trail;
- pause останавливает движение;
- hidden останавливает движение;
- возврат на вкладку не запускает игру автоматически;
- result останавливает loop;
- повтор создаёт новый мир.

## 24.4. Cleanup smoke

До загрузки игрового кода в test harness инструментируй:

- `requestAnimationFrame`;
- `cancelAnimationFrame`;
- `setTimeout`;
- `clearTimeout`;
- `setInterval`;
- `clearInterval`;
- `addEventListener`;
- `removeEventListener`;
- `ResizeObserver`, если используется.

После закрытия каждой игры проверь баланс созданных и очищенных ресурсов.

Не добавляй production debug-panel только ради smoke.

Допустим тестовый wrapper в isolated harness.

## 24.5. Layout и accessibility smoke

Проверь:

- нет горизонтального overflow;
- нет обрезанных кнопок;
- back всегда доступен;
- pause всегда доступна во время аркады;
- touch targets не меньше 48×48;
- Tab не застревает на Back;
- Escape работает;
- focus возвращается на карточку;
- Canvas не отключает прокрутку вне собственной области;
- светлая и тёмная темы;
- reduced motion.

Если полный app-flow останавливается на штатной auth или consent boundary:

- не обходи её;
- используй isolated in-memory harness с реальными source и CSS;
- явно укажи ограничение;
- не заявляй, что проверен полный authenticated flow.

# 26. Критерии готовности

Задача считается завершённой только если:

1. В каталоге находятся три законченные карточки.
2. Каждая карточка открывает fullscreen-dialog.
3. Каждая игра имеет собственный прелоадер.
4. Ни один игровой JS или CSS не загружается до клика.
5. Загружается только выбранная игра.
6. Повторное открытие не создаёт дубликаты ресурсов.
7. «Собери слово» содержит минимум 30 проверенных слов.
8. Сессия Word Builder содержит шесть разных слов.
9. Word Builder корректно работает с distractor.
10. «Маршрут робота» содержит минимум 12 решаемых уровней.
11. BFS подтверждает `expectedShortestPath`.
12. Сессия Robot Route содержит пять разных уровней.
13. «Цветной след» реализует непрерывный trail.
14. Реализовано валидное замыкание.
15. Невалидная петля не даёт территорию.
16. Реализован захват окружённого компонента.
17. Реализовано откусывание чужой территории.
18. Компонент с живой головой защищён.
19. Реализовано пересечение уязвимого trail.
20. Работают три локальных бота.
21. Коллизии не зависят от порядка actor array.
22. Работают touch, mouse и keyboard.
23. Пауза и Page Visibility останавливают аркаду.
24. После закрытия нет фоновой нагрузки.
25. Игры не используют сеть, storage или аналитику.
26. Focus trap не блокирует игровые контролы.
27. Точечные тесты проходят.
28. Bundle isolation подтверждён.
29. Scoped legacy preview выполнен.
30. `docs:reference:check` проходит.
31. Mobile smoke выполнен.
32. Desktop smoke выполнен.
33. Размеры находятся внутри бюджета либо превышение честно зафиксировано.
34. Commit, push, PR, deploy и полная legacy-сборка не выполнялись.
