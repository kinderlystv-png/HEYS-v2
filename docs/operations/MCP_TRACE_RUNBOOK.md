# Как достать MCP-трейс — с любого устройства

> **Назначение:** за одну минуту получить цепочку вызовов MCP по конкретному
> обмену — с телефона, из веба, с любой из рабочих машин. Одинаково для человека
> и для любого ИИ в проекте.
>
> **Источник правды по цифрам и стоимости сценариев** —
> [`yandex-cloud-functions/heys-mcp/TIMING_LOG.md`](../../yandex-cloud-functions/heys-mcp/TIMING_LOG.md).
> Этот файл отвечает только на вопрос «как достать», не «сколько должно быть».

---

## Короткий ответ

**Один вызов `tasks_mcp_trace` в кураторском Claude.** Это MCP-инструмент, а не
скрипт: телефон, веб и любая машина ходят одним и тем же путём. Ни `yc`, ни
`psql`, ни клон репозитория для этого не нужны.

| Что нужно                   | Что сказать Claude         | Что вызывает ИИ                           |
| --------------------------- | -------------------------- | ----------------------------------------- |
| Последние обмены за сегодня | «разбери трейс за сегодня» | `tasks_mcp_trace({})`                     |
| Один конкретный обмен       | «разбери обмен 11:38»      | `tasks_mcp_trace({ heading: '11:38' })`   |
| Другой день                 | «трейс за 17 августа»      | `tasks_mcp_trace({ date: '2026-08-17' })` |

Без `heading` возвращаются все размеченные обмены дня — медленнее и объёмнее, но
это правильный первый вызов, когда точное время неизвестно. Дальше сузить.

---

## Пять ловушек

Каждая из них уже стоила разбора вслепую. Порядок — по частоте.

**1. `taskDay` — это не календарная дата.** Сутки считаются с 03:00 МСК, как у
`tasks_checkpoint`. Прогон в 02:13 лежит во **вчерашнем** дне, и запрос за
календарное «сегодня» вернёт `transcript_empty` или чужие обмены.

**2. Один обмен часто разъезжается на два соседних `heading`.** Пример из 18.08:
одна реплика про кофе и сырники дала блоки `11:38` и `11:39` с одинаковым
текстом. Три `heys_get_day` и два `heys_log_meal` видны, только если считать оба
блока вместе. **Число вызовов всегда суммируй по соседним одинаковым репликам**,
иначе приёмка покажет ложное «уложились».

**3. Инструкции и описания инструментов клиент забирает один раз — при старте
сессии.** После деплоя старый чат продолжает работать по старому тексту.
**Приёмку после деплоя гонять только в новом чате**, иначе замеряешь прошлую
версию и делаешь вывод о ней.

**4. Обмен без записи в дневник и без `tasks_checkpoint` не размечен.** Метка
`[mcp session=… seq=… ts=…]` появляется в стенограмме от пишущих инструментов и
чекпоинта. Неразмеченные блоки в отчёт не попадают — их число видно в
`blocks_without_mark`. Пустой разговор трейсом не разобрать, это не поломка.

**5. Retention.** `mcp_call_events` в Postgres — **180 суток** (дальше
`telemetry_retention_exceeded`). Stdout в Cloud Logging — **3 суток**, и это
единственный источник для `upstream_calls` и `cold_start`.

## Как читать ответ

| Поле                        | Что значит                                                       |
| --------------------------- | ---------------------------------------------------------------- |
| `confirmed_tools` / `_ms`   | `session_id` совпал с меткой стенограммы — это точно этот обмен  |
| `probable_tools` / `_ms`    | только попал в окно ±5 мин — может быть чужим                    |
| `wall_span_ms`              | стена от первого вызова до последнего                            |
| `confirmed_ms`              | сколько из неё реально заняли инструменты HEYS                   |
| `gaps_ms`                   | паузы **между** вызовами — время модели, не наше                 |
| `flow_steps[].gap_after_ms` | где именно модель думала дольше всего                            |
| `duplicates`                | лишние круги: `heys_get_day×3` — это три ожидания вместо одного  |
| `flow_warnings`             | `duplicate:*` — лишний вызов; `long_gap_after:*` — думала модель |

**Главный вопрос разбора — число вызовов, а не миллисекунды.** В живом обмене
18.08 инструменты HEYS отработали 6,9 с при стене 299 с: всё остальное — паузы
модели. Оптимизировать `duration_ms` там, где 97 % времени в `gaps_ms`,
бессмысленно; убирать надо сами круги.

## Ошибки и что они значат

| Код                            | Причина и что делать                                            |
| ------------------------------ | --------------------------------------------------------------- |
| `transcript_empty`             | нет стенограммы за этот день — почти всегда перепутан `taskDay` |
| `heading_not_found`            | неверное ЧЧ:ММ или блок без метки — позови без `heading`        |
| `invalid_heading`              | формат не ЧЧ:ММ                                                 |
| `telemetry_retention_exceeded` | дата старше 180 суток — данных уже нет                          |
| `telemetry_db_timeout`         | повтори; сузь окно через `heading`                              |
| `tasks_not_configured`         | коннектор поднят без `HEYS_TASKS_CLIENT_ID`                     |

## Когда MCP не хватает — CLI

Нужен только в трёх случаях, и только на машине с репозиторием и `yc`.

| Случай                                                 | Команда                                                                                                   |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| Нужны `upstream_calls` / `cold_start` по одному вызову | `yc serverless function logs d4epjmd9lnk059u29bg8 --limit 30`                                             |
| Обмен не размечен, а разобрать надо                    | `yc logging read --group-id e23ndggvq798r3v3eepq --since 1h --filter 'message: "mcp_call"' --format json` |
| Агрегаты за неделю, «что дорожает»                     | `node scripts/mcp-stats.mjs --days 7`                                                                     |

Всегда задавай `--limit N`: без него `function logs` ведёт себя как `tail -f` и
не завершается. Log group — только `e23ndggvq798r3v3eepq`;
`--group-name default` и id из `logging group list` телеметрии heys-mcp **не
содержат**.

Базовая линия p50 перед деплоем и полный разбор ловушек CLI —
[`TIMING_LOG.md` § «Проверка за 30 секунд»](../../yandex-cloud-functions/heys-mcp/TIMING_LOG.md).

## Приёмка после деплоя heys-mcp

Порядок, который даёт честный ответ:

1. Новый чат с коннектором — иначе действуют инструкции до деплоя (ловушка 3).
2. Живая фраза, ради которой правили.
3. `tasks_mcp_trace({})` — без `heading`, чтобы увидеть соседние блоки.
4. Сложить вызовы по всем блокам с этой репликой (ловушка 2).
5. Сверить с ожиданием: сколько вызовов должно быть и есть ли `duplicate:*`.

Разбор конкретных прогонов и цифры по сценариям накапливаются в
[`TIMING_LOG.md` § «Круги агента»](../../yandex-cloud-functions/heys-mcp/TIMING_LOG.md).
