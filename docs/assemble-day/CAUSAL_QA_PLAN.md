## Цель gate

QA доказывает четыре свойства: воспроизводимость, отсутствие безвыходных
состояний, причинное влияние контекста и отсутствие универсальной стратегии.
Красивый средний итог кампании не заменяет эти проверки.

## Уровни проверки

### 1. Schema и registries

- каждый initial state проходит `GameStateV2`;
- все event/action/task/commitment ID разрешаются;
- content paths входят в allowlist schema;
- версии scenario, calibration, price book и RNG заданы;
- Action Registry и Event Registry не содержат исполняемого кода;
- каждый долгосрочный эффект имеет причину.

### 2. Golden reducer fixtures

Тесты покрывают десять этапов `CAUSAL_REDUCER_PROTOCOL.md`, переход через
полночь, сон, отсрочку платежа, caps шкал и RNG vectors. Golden fixture хранит
input JSON, action ID, expected state hash, event ID и journal entries.

### 3. Контрфактические пары

Обязательны десять пар из `08_VERTICAL_SLICE.md`:

1. срочная рабочая задача после нормального сна и двух коротких ночей;
2. заказ еды при достаточном и низком резерве;
3. просьба партнёру при сбалансированной и перекошенной нагрузке;
4. обычная тренировка при нормальном и тяжёлом восстановлении;
5. кофе утром без активной дозы и вечером после 180 мг;
6. быстрая рабочая задача при фокусе 75 и 35;
7. отмена семейного плана заранее и после двух нарушений;
8. такси при высоком и отрицательном прогнозе резерва;
9. встреча с друзьями перед выходным и ранним дедлайном;
10. ранний сон при некритичном и срочном рабочем хвосте.

Пара проходит, если меняются минимум два элемента из доступности, времени,
усилия, риска, порядка и прогноза результата. Журнал обязан назвать изменившие
результат входы.

Планирование дополнительно проверяется одинаковым исходным state: выбранный
фокус и защищённое окно облегчают только явно aligned действие; альтернативный
план лишает его подготовки или создаёт authored конфликт. Матрица включает все
36 допустимых стартовых планов (`3` пары границ × `12` разных пар фокусов), а
журнал обязан назвать `planningCapacity.attention.*` либо
`planningCapacity.ruleSlots.*`.

### 4. Массовая симуляция

Фиксируется набор из 10 000 уникальных seed. Каждый seed проходит все семь
политик, поэтому полный прогон содержит 70 000 campaign-policy runs и 10 000
сопоставимых seed-блоков.

Политики детерминированы при одинаковом наборе action offers:

| ID                 | Правило выбора                                                                |
| ------------------ | ----------------------------------------------------------------------------- |
| `maximize_work`    | максимальный ожидаемый прогресс работы, затем меньший риск                    |
| `protect_family`   | выполнить ближайшее семейное обязательство, затем снизить семейный перекос    |
| `protect_recovery` | уменьшить тяжёлый дефицит, затем защитить сон                                 |
| `save_money`       | минимальная денежная цена среди practically available действий                |
| `buy_time`         | минимальная эффективная длительность при достаточном cash                     |
| `balanced`         | минимизировать максимум нормализованных work/family/recovery/finance deficits |
| `random_valid`     | seeded выбор среди practically available действий                             |

Политика не обходит requirements и не видит скрытый будущий roll.

## Метрики и пороги

| Метрика                          | Расчёт                                                                                             |   Gate |
| -------------------------------- | -------------------------------------------------------------------------------------------------- | -----: |
| `terminalLockCount`              | развилки без доступного действия                                                                   |    `0` |
| `heavyStateStabilizationRate`    | тяжёлые состояния с доступным стабилизирующим путём / все тяжёлые состояния                        | `100%` |
| `ordinaryTwoChoiceRate`          | обычные развилки с минимум двумя practically available действиями / все обычные развилки           | `≥98%` |
| `hardSingleChoiceRate`           | доля допустимых одноходовых жёстких обязательств                                                   |  `≤2%` |
| `actionDominanceRate`            | доля контрфактических контекстов категории, где действие выигрывает по всем шести policy utilities | `≤70%` |
| `policyGlobalDominanceCount`     | политики, лучшие одновременно по деньгам, работе, семье, состоянию и сну                           |    `0` |
| `largeExternalPerDayMax`         | максимум крупных внешних помех за день                                                             |   `≤1` |
| `largeExternalPerWeekMax`        | максимум крупных внешних помех за неделю                                                           |   `≤4` |
| `boundaryStepRate`               | шаги с energy/mood/tension на 0 или 100 / все шаги                                                 | `≤20%` |
| `unexplainedLongTermChangeCount` | долгосрочные diff без journal source                                                               |    `0` |
| `reproMismatchCount`             | несовпавшие повторные state hash                                                                   |    `0` |
| `personalizationAdvantageCount`  | изменение вероятности успеха только из-за признака HEYS                                            |    `0` |

Тяжёлое состояние определяется условиями `D56`: `energy < 25`, `tension > 80`,
`hunger > 85`, `sleepDebtMin > 300` или `financialPressure > 85`.

`actionDominanceRate` использует шесть отдельных QA-функций полезности,
соответствующих политикам без `random_valid`. Действие считается доминирующим в
контексте, только если оно не хуже по всем шести функциям и лучше хотя бы по
одной. Единый пользовательский балл жизни не создаётся.

## Дополнительные распределения

Отчёт сохраняет, но не использует как самостоятельный pass/fail:

- частоту каждого action и event;
- причины недоступности действий;
- распределение сна, голода, напряжения, cash и рабочего хвоста по дням;
- частоту отсрочки платежа и время восстановления прогноза резерва;
- число broken/renegotiated commitments;
- длину причинных цепочек;
- долю повторных действий по привычностям;
- результаты пяти недельных целей.

Нулевой выбор authored action или event означает недостижимый контент и требует
разбора до UI, даже если формальные пороги прошли.

## Формат отчёта

```ts
interface CausalQaReportV2 {
  reportVersion: 2;
  createdAt: string;
  schemaVersion: 2;
  scenarioId: string;
  scenarioVersion: string;
  calibrationVersion: string;
  priceBookVersion: string;
  rngAlgorithm: string;
  codeRevision: string;
  seedCount: 10000;
  policyIds: string[];
  runCount: number;
  gates: Record<string, { value: number; threshold: string; passed: boolean }>;
  distributions: Record<string, unknown>;
  failures: QaFailureV1[];
}
```

Помимо сохранённых D60 gates отчёт v2 требует
`heavyMultiStabilizationRate >= 0.85` и `echoEventCoverageRate = 1`; фактический
stabilizer определяется preview того же reducer, а не declarative tag.

`createdAt` относится только к артефакту отчёта и не участвует в симуляции.
`codeRevision` фиксирует проверенный исходник; пустое значение запрещено в
итоговом gate-отчёте.

## Классификация ошибки

```ts
interface QaFailureV1 {
  seed: string;
  policyId: string;
  dayIndex: number;
  stepIndex: number;
  gate: string;
  stateHash: string;
  eventId?: string;
  actionId?: string;
  replayKey: string;
}
```

Каждая ошибка воспроизводится одним `replayKey`, который кодирует версии, seed,
policy и позицию. Отчёт не сохраняет персональные данные.

## Решение по результату

- Любой fail инварианта детерминизма, terminal lock или необъяснённого
  долгосрочного изменения блокирует UI-этап.
- Пороговый fail баланса ведёт к новой `calibration v0.2`; команда не
  переписывает старый отчёт.
- Изменение product contract получает новый D-ID или новую версию существующего
  решения. Балансировка внутри принятого принципа меняет только
  calibration/price book.
- Исключение допускается только с ID, воспроизводимым seed, причиной и отдельным
  решением команды; список исключений входит в отчёт.

## Критерий выхода

Этап causal QA завершён, когда schema и golden tests проходят, 10
контрфактических пар меняют геометрию решения, массовый отчёт проходит все
gates, а каждый authored action и event достигается хотя бы в одном валидном
прогоне.
