## Контракт шага

Reducer является чистой функцией:

```ts
interface StepInputV1 {
  state: GameStateV2;
  openEvent: EventInstanceV1;
  actionId: string;
}

interface StepOutputV1 {
  state: GameStateV2;
  appliedAction: ActionOfferV1;
  nextEvent: EventInstanceV1;
  journalEntries: CausalEntryV1[];
  stateHash: string;
}

type ReduceStepV1 = (
  input: StepInputV1,
  registries: RegistriesV1,
) => StepOutputV1;
```

Функция не читает часы устройства, сеть, localStorage, HEYS state или глобальный
RNG. Ошибка валидации возвращается до клонирования state и не изменяет счётчики
RNG.

## Атомарный planning-step

`reducePlanningStep` принимает ровно две разные недельные границы из трёх и
разные главный/поддерживающий фокусы. Он одним шагом заменяет `weeklyRules` и
`monthlyPriorities`, добавляет две записи журнала и не меняет `clock`,
`scenarioCursor`, `activeEventId`, RNG, очередь или event ledger. После первого
action-step план заблокирован.

`getPlanningView` до подтверждения возвращает два rule slots, распределение трёх
единиц внимания `2+1`, давление и конфликты. При построении `ActionOffer` движок
применяет planning geometry только по authored `priorityAlignment` и тегам окна
события; каждая причина содержит конкретный `planningCapacity.*` input path. UI
не повторяет эти условия.

## Порядок расчёта

Порядок обязателен для каждой реализации.

### 1. `validate`

- проверить schema и версии state;
- убедиться, что `openEvent` соответствует `dayIndex` и `stepIndex`;
- убедиться, что `actionId` входит в событие;
- вычислить `DecisionContextV1` по исходному state;
- построить `ActionOfferV1` и проверить требования, ресурсы и жёсткие окна;
- зафиксировать снимок условий `preActionContext`.

Неуспех завершает вызов без частичного результата.

### 2. `advanceEnvironment`

- определить эффективную длительность действия;
- продвинуть `clock.minuteOfDay` и при необходимости `dayIndex`;
- применить распад кофеина, рост голода, базовый расход энергии и созревание
  временных эффектов за прошедший интервал;
- уменьшить `satietyWindowMin` и счётчики `after_steps`;
- не применять цену денег и инвентаря на этом этапе.

Время списывается один раз. Оператор `advance_time` из эффекта добавляет
заявленное дополнительное время после базовой длительности и запускает те же
фоновые правила.

### 3. `applyCosts`

- списать `moneyRub` и порции;
- применить цену усилия по `calibrationVersion` и `preActionContext`;
- записать известные затраты как причинные источники.

`cashRub` не уходит ниже нуля. Несовпадение с результатом `validate` считается
ошибкой детерминизма, и транзакция откатывается.

### 4. `applyImmediateEffects`

- применить `immediateEffects` в порядке массива;
- применить `conditionalEffects`, чьи условия истинны в `preActionContext`;
- выполнять clamp после каждого оператора;
- выполнить bounded roll только после детерминированных операторов действия.

### 5. `scheduleEffects`

- преобразовать относительный trigger в абсолютный;
- проверить уникальность ID;
- добавить эффекты в очередь;
- отсортировать очередь по trigger и ID.

### 6. `resolveCommitments`

- закрыть явно выполненные обязательства;
- применить пересогласование или нарушение, объявленное действием;
- перевести обязательства с прошедшим сроком в допустимый контрактом статус;
- не создавать нарушение молча, если действие честно пересогласовало срок до
  дедлайна.

### 7. `updateDerivedContext`

Пересчитать голод, сонливость, фокус задач, готовность ко сну, давление
дедлайна, финансовое давление, семейный перекос и давление вариантов. Эти
значения не добавляются в `GameStateV2`.

### 8. `collectEventCandidates`

Собрать кандидатов из обязательств, pending effects, causal triggers, внешних
шаблонов и возможностей. Отфильтровать cooldown, caps, бюджет, несовместимые
теги и события без практически доступных действий.

### 9. `selectNextEvent`

- применить приоритет источников из `EVENT_SCHEMA.md`;
- выбрать по hard window, urgency и ID;
- при равенстве выполнить один seeded roll;
- материализовать `EventInstanceV1`;
- сохранить выбранный `templateId` как `activeEventId` и записать фактические
  trigger paths в causal journal;
- применить разрешённые `onOpenEffects` и повторно построить action offers;
- проверить антиспираль `D56` и порог доступности `D60`.

Если материализация нарушает gate, reducer отклоняет шаблон как ошибку контента
и пробует следующего кандидата. Если кандидатов не осталось, результатом
является `terminal_lock` test failure; движок не создаёт скрытый вариант.

### 10. `appendCausalJournal`

- сравнить применённые изменения с исходным state;
- записать источники цены, механизмы, изменённые пути и уровень уверенности;
- объединить мелкие изменения одного источника в понятную цепочку;
- вычислить canonical state hash;
- вернуть новый state и событие.

Журнал описывает фактический diff. Неприменившийся эффект не попадает в
объяснение результата.

## Детерминированный RNG

Версия v1 использует `fnv1a-mulberry32-v1`:

1. Сформировать строку `campaignSeed + ':' + seedKey + ':' + occurrence`.
2. Получить unsigned 32-bit seed через FNV-1a.
3. Выполнить один шаг Mulberry32 и получить число в `[0, 1)`.
4. Увеличить `rng.occurrences[seedKey]` после успешного применения результата.

`seedKey` задаёт действие или генератор. Отмена транзакции не увеличивает
occurrence. Реализация обязана иметь golden fixtures для FNV-1a, Mulberry32 и
преобразования диапазона.

Целочисленный bounded result:

```text
result = min + floor(random01 × (max - min + 1))
```

## Атомарность

Reducer работает на клоне state. Он публикует новый state только после всех
десяти этапов и финальной schema validation. Любая ошибка возвращает
структурированный код, этап и ID контента. Частичный state, журнал или RNG
counter наружу не выходят.

```ts
interface ReducerErrorV1 {
  code:
    | 'invalid_state'
    | 'stale_event'
    | 'unavailable_action'
    | 'invalid_content'
    | 'invariant_violation'
    | 'terminal_lock';
  stage: string;
  entityId?: string;
  details: string[];
}
```

## Переход через полночь и сон

Обычное действие может пересечь полночь, но не завершает сон автоматически. Сон
является явным действием с `sleepOpportunityMin`. Его reducer-путь применяет
формулы `5.9–5.10` из `09_CALIBRATION_QA.md`, переносит незакрытые задачи и
обязательства, обновляет скользящие семейные нагрузки и открывает первый якорь
нового дня.

Когда авторский контент заканчивается, шаг закрывает последний день ночным сном
и переводит часы на утро следующего дня. После `D72` это исчерпание контента, а
не финал кампании и не terminal state: горизонт остаётся открытым, а конкретный
день окончания больше не зашит в код и выводится из последнего слота.

## Границы периодов принадлежат редьюсеру

После `D72` границы применяет сам шаг: он определяет завершённый день по
authored slots, вычисляет закрытые день, неделю и месяц по календарю
`PeriodState` и применяет их ровно один раз, записывая идентификаторы в
`periods.appliedBoundaries`. Недельные лимиты сбрасываются только вместе с
закрытием своей недели, а устойчивые последствия не обнуляются.

Чистая функция `getPeriodBoundaries(before, after)` больше не считает границы
заново: она возвращает разницу применённых идентификаторов, поэтому второго
источника истины нет. Clock не является единственным сигналом: следующий event
может быть materialized раньше своего anchor.

`PeriodSummary` строится после reducer commit из итогового state и существующего
causal journal. Повторный вызов или checkpoint replay дают тот же объект и не
добавляют journal entries, revision либо RNG occurrence.

## Стабильность версий

На результат влияют пять версий:

- `schemaVersion`;
- `scenarioVersion`;
- `calibrationVersion`;
- `priceBookVersion`;
- `rng.algorithm`.

Отчёт QA хранит все пять. Изменение порядка этапов, RNG или семантики оператора
требует новой версии соответствующего контракта и новых golden fixtures.

## Обязательные тесты reducer

1. Неуспешная валидация не меняет state hash и RNG counters.
2. Цена времени применяется один раз.
3. Условие действия читает `preActionContext`.
4. Созревшие эффекты применяются в стабильном порядке.
5. Clamp выполняется после каждого оператора.
6. Нулевой баланс не становится отрицательным.
7. Пересогласование до срока не создаёт broken commitment.
8. Один input при тех же registries даёт тот же state hash.
9. Журнал содержит каждое долгосрочное изменение и не содержит выдуманного
   результата.
10. Следующее событие проходит бюджет, cooldown, антиспираль и practical
    availability gate.
11. Границы дня, недели и месяца применяются редьюсером ровно один раз по
    `periods.appliedBoundaries`; повторный расчёт, reload и replay не создают
    второй summary, второй reducer-step и второй сброс недельных лимитов.
