> Обновлено: 2026-08-01

## Почему документ разделён

Предыдущий монолит одновременно содержал продуктовую концепцию, реестр решений,
доменные спецификации, UI, числовую калибровку, QA, гипотезы и историю
изменений. Это затрудняло ревью, создавало повторения и делало неясным
ownership.

Документация теперь разделена **не по этапам обсуждения и не по будущим файлам
кода**, а по устойчивым продуктовым bounded contexts. Каждый факт должен иметь
один основной модуль-владелец; остальные документы ссылаются на него, а не
создают независимую версию.

## С чего начинать работу

Агент, который продолжает разработку, читает
[`HANDOFF_FOR_IMPLEMENTER.md`](./HANDOFF_FOR_IMPLEMENTER.md) целиком до первой
правки: там фактическое состояние кода, инварианты, порядок шага игры, команды
проверки и список, по которому идёт ревью. Очередь работ и копируемые промпты —
в [мегаплане](./assemble_prodution_megaplan.md).

## Правила работы

1. Принятое решение получает постоянный ID в `10_DECISION_REGISTER.md`.
2. Его предметное следствие вносится в один модуль-владелец.
3. Гипотеза остаётся в `11_HYPOTHESES_BACKLOG.md`, пока не проверена или не
   принята отдельным решением.
4. Изменение коэффициента calibration фиксируется новой версией в журнале
   `09_CALIBRATION_QA.md`; продуктовый принцип не открывается заново без
   отдельного решения.
5. Новая система не создаёт новый документ автоматически. Новый модуль
   появляется только при отдельном ownership, самостоятельном цикле изменений и
   заметном объёме.
6. Архивный монолит не редактируется.
7. `12_ROADMAP.md` владеет крупными фазами, а
   [`assemble_prodution_megaplan.md`](./assemble_prodution_megaplan.md) —
   текущей исполнимой очередью, gates и копируемыми промптами. При расхождении
   next step каноничен мегаплан.
