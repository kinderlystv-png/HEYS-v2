# HEYS-v2 — Bug post-mortems

Reference of past root-cause analyses. The architecture docs (
[ARCHITECTURE.md](ARCHITECTURE.md), [DEBUGGING.md](DEBUGGING.md)) describe
**current** invariants. This file describes **how we got there** — what was
broken, what was fixed, and the pattern to watch for.

## Манифест каталога отстаёт от строк — облачный каталог не приезжает (2026-08-22)

Найдено при проверке восстановления из бэкапа (задача про непроверенный бэкап
после инцидента 21.08). **Дефект не устранён**, здесь зафиксированы факты.

**Что видно.** Каталог продуктов — это пара ключей в `client_kv_store`: строки в
`heys_products_overlay_v2` и сторож целостности
`heys_products_overlay_v2_rpc_manifest` (`rowCount` + хеш строк). В живой базе
пара разошлась у двух клиентов из трёх:

| Клиент     | Строк | `rowCount` | Строки обновлены | Манифест обновлён | `assemble()`          |
| ---------- | ----- | ---------- | ---------------- | ----------------- | --------------------- |
| `4545ee50` | 296   | 278        | 21.08 20:46      | 11.08 21:20       | не собирается         |
| `ccfe6ea3` | 151   | 146        | 22.08 00:29      | 21.08 21:15       | `generation_mismatch` |
| `02e1aff8` | 7     | 7          | 13.08 20:31      | 13.08 20:31       | `complete`            |

Согласован ровно тот клиент, у которого оба ключа записаны одним действием. У
остальных строки уехали вперёд, манифест остался от прошлой публикации.

**Чем это грозит.** `codec.assemble()` сверяет хеш и длину и при несовпадении
возвращает `ok: false`, а вызывающий код в `heys_storage_supabase_v1.js` на это
отвечает `if (!assembled.ok) return out;` — вся семья ключей выбрасывается из
облачного снимка **молча**. На старом устройстве человек ничего не замечает:
каталог живёт в локальном хранилище. На новом устройстве каталог приедет пустым.
Ошибки в интерфейсе при этом нет — ровно та же тихая потеря, что и 21.08.

**Проверено фактом, а не рассуждением:** живые значения выгружены из прода и
прогнаны настоящим кодеком приложения — `generation_mismatch`, хеш строк
`58029:8f39486a` против `55914:77ded3d1` в манифесте.

**Что сделано.** Восстановление каталога описано и проверено —
[Scenario 9 в DISASTER_RECOVERY_RUNBOOK.md](../../yandex-cloud-functions/DISASTER_RECOVERY_RUNBOOK.md),
инструмент `restore-products-catalog.js` пересчитывает манифест по строкам тем
же кодеком и откатывается, если записанное состояние клиент не примет. Это лечит
следствие: процедура приводит пару в согласованное состояние, но следующая
публикация продуктов разведёт её снова.

**Причина найдена.** Три инструмента MCP — `heys_create_product`,
`heys_update_product`, `heys_delete_product` — писали
`upsertKV(OVERLAY_KEY, rows)` и на этом останавливались. Слов `rpc_manifest`,
`OverlayShardCodec`, `createSingle` во всём `heys-mcp/lib/` не встречалось ни
разу. Веб-клиент так не умеет: у него оба пути записи пишут манифест последним —
«commit marker written last».

Совпадение точное на обоих клиентах: 151 − 146 = 5, и ровно 5 позиций созданы
после снятия манифеста; 296 − 278 = 18, и ровно 18 — после. Третий клиент
согласован: ему продукты через куратора не заводили. Пять «лишних» у первого —
еда, заведённая 21.08 в 21:15–21:27, то есть **через одиннадцать секунд** после
ручного восстановления пара развалилась снова.

**Что сделано.** Запись каталога в MCP идёт через `products.saveOverlayRows`:
строки, затем манифест, посчитанный тем же кодеком, что и в браузере. Кодек
лежит зеркалом `yandex-cloud-functions/shared/overlay-shard-codec.js`,
байт-в-байт с клиентским; расхождение ловит `cmp` в `test-functions.sh` — сервер
и браузер обязаны считать один и тот же хеш. Отказ на манифесте возвращается
ошибкой, а не тихим успехом: рассогласованная пара хуже незаписанного продукта.

Тихое выбрасывание стало громким: `reportOverlayAssemblyFailure` называет
причину, клиента и отправляет в Scenario 9 руководства по восстановлению, по
одному сообщению на пару «клиент + причина». «Не доверяем данным» больше не
выглядит как «данных нет».

**Проверки:** `heys-mcp/__tests__/overlay-manifest-pair.test.cjs` (пара
принимается настоящим кодеком после каждой записи, включая цепочку из четырёх
продуктов подряд), `apps/web/__tests__/overlay-assembly-failure-loud.test.js`.
Обе проверки прогнаны от обратного: возврат старого поведения даёт красные.

**Что осталось.** Пары, уже разошедшиеся в проде, новый код не чинит задним
числом — их приводит в порядок Scenario 9.

## Каталог продуктов затёрт до одной строки (2026-08-21)

Днём человек не смог добавить продукт, к вечеру обнаружилось, что личный каталог
из 146 позиций в облаке заменён одной — той, что добавили час назад. История еды
за месяцы на сервере уцелела, каталог — нет.

**Цепочка.** У клиента 1302 KV-ключа, из них 147 — личные файлы задачника
(`heys_tasks_*`): стенограммы, журналы, архивы. Приложение их не показывает и
выбрасывало фильтром ПОСЛЕ загрузки. В алфавите они идут подряд и собирались в
страницу на `offset=1200`, состоящую из них целиком; при `select=k,v` она не
влезала в лимит тела ответа облачной функции (~1,1 МБ) и падала
детерминированно. Дальше три усилителя:

1. Деление страницы пополам срабатывало только на код 502. Под параллельной
   загрузкой шлюз отвечает 503, а часть отказов вообще не доходила до клиента:
   на ошибке шлюз подставляет `Access-Control-Allow-Origin: '*'`, запрос идёт с
   credentials, браузер блокирует ответ целиком — остаётся «Failed to fetch».
2. Упавшая страница обнуляла ВСЁ уже скачанное: шесть успешных страниц (1200
   ключей) выбрасывались, синхронизация возвращала «офлайн».
3. Каталог на устройстве оставался пустым — и человек добавил продукт.
   `ensurePersonalProductCommitted` собрал новый каталог из локального (пустого)
   плюс один продукт и опубликовал в облако.

**Почему не спас shrink-guard.** Он есть в `writeRaw` и сравнивает новый список
с ЛОКАЛЬНЫМ предыдущим. Локальный был пуст, ноль меньше единицы не бывает —
«уменьшения» нет, защита молчит. Пустой локальный каталог это не факт, а
незнание.

**Что сделано.** Задачник не покидает базу: REST-функция научилась оператору
`notlike`, клиент просит `notlike.k=heys_tasks_*` (1302 → 1089 ключей).
Стартовая страница 200 → 100, пол деления 50 → 10, распознаются оба кода отказа
и замаскированный CORS сетевой сбой при живой сети. Упавшая страница больше не
обнуляет доехавшие: данные записываются, статус `partial`, отметка синхронизации
снимается — следующий заход идёт полным, а не дельтой. И главное: каталог не
публикуется, пока облако молчит и локальный каталог пуст (инвариант 11).

**Восстановление.** Легаси-зеркало `heys_products` (сжатая строка, 36 КБ)
уцелело — в нём были все 146. Расшифровали штатным алгоритмом, манифест
целостности пересчитали тем же кодеком, что и приложение
(`OverlayShardCodec. createSingle`), записали одной транзакцией; прежнее
состояние осталось рядом под ключами `__before_restore_20260821`. Первая попытка
откатилась на проверке типа — и вовремя: только тогда заметили манифест и не
записали рассогласованное состояние.

**Паттерн на будущее.** Пустое локальное состояние нельзя принимать за истину и
публиковать поверх облака — сначала убедись, что облако отвечало. И фильтруй
чужой scope ДО загрузки, а не после: то, что выбрасывается на клиенте, всё равно
успевает сломать страницу.

**Проверки:** `sync-bootstrap-oversized-page.test.js`,
`overlay-publish-guard.test.js`, `usage-stats-refresh-on-history.test.js`,
`add-product-onadd-contract.test.js`.

## UI v4 classic-drift: вложенный `var(--sand, var(--classic, #литерал))` (2026-08-12)

При перекраске еды (prompt-food) и ранее виджетов Главной в CSS попал
антипаттерн: `var(--v4-sand-роль, var(--v4-роль, #литерал))`. На classic/blue
внешняя sand-роль задана, но внутренняя generic-роль (`--v4-ink`,
`--v4-ok-fill`, `--v4-accent-bg`…) тоже задана в палитре — и её значение
синее/зелёное. Литерал в конце не срабатывает, а `ui-v4-classic-drift` ловит
сдвиг относительно канона классики (20 мест, гейт деплоя).

**Рецепт (owner 2026-08-12, A5):** во внешнем `var()` только sand-роль и
литерал. Classic/generic-роль внутрь не вкладывать:
`var(--v4-sand-ink, #201e1d)`, не `var(--v4-sand-ink, var(--v4-ink, #201e1d))`.
Для подложек внимания в еде — `var(--v4-sand-accent-bg, #f0dcc6)` по образцу
`--v4-sand-hero`; не подставлять `--v4-accent-bg` (на classic синяя `#dbeafe`).

**Проверка:** `node scripts/ui-v4-check-classic-drift.mjs` и
`cd apps/web && npx vitest run __tests__/ui-v4-classic-drift.test.js`.

## Экран входа: любой отказ сервера выдавался за неверный PIN (2026-08-11)

Вход по PIN отключён на сервере 2026-08-11 (временная мера против перебора,
решение владельца): `verify_client_pin_v3` заменена заглушкой, которая отвечает
`{success:false, error:'pin_login_disabled', message:'Вход по PIN временно отключён…'}`.
Клиент при этом показывал «PIN не подошёл» — человек решал, что забыл код, и шёл
в поддержку с несуществующей проблемой.

Причина — три места, где причина отказа терялась:

| Где                                 | Что схлопывалось                                              |
| ----------------------------------- | ------------------------------------------------------------- |
| `heys_auth_v1.js`, ветка транспорта | любая ошибка кроме `rate_limited` → `invalid_credentials`     |
| `heys_auth_v1.js`, ветка `!success` | то же самое, серверный `message` не читался вообще            |
| `heys_auth_v1.js`, ветка без сессии | `success:true` без `client_id`/`session_token` → «PIN не тот» |

Заглушка только вскрыла дефект. Тем же путём молча терялся и живой код: миграция
`database/2026-08-11_pin_lockout_by_phone.sql` вернула блокировку по номеру
клиента и отвечает `pin_rate_limited`, а клиент ждал `rate_limited` — значит
заблокированный клиент тоже читал «PIN не подошёл» вместо «слишком много
попыток».

**Фикс.** `classifyServerLoginError()` в `heys_auth_v1.js`: в
`invalid_credentials` сводятся только явные коды неверного кода
(`invalid_credentials`/`invalid_pin`/`wrong_pin`) и пустой ответ, `rate_limited`
и `pin_rate_limited` — в ограничитель, а любой незнакомый код уезжает на экран
как есть вместе с серверным текстом (`serverError`, `serverMessage`). Отказ без
выданной сессии получил свой код `session_not_issued`, обрыв связи —
`network_error`. В `heys_login_screen_v1.js` добавлена ветка
`pin_login_disabled`, а общий fallback показывает серверный текст вместо «Не
удалось войти».

**Инвариант.** «PIN не подошёл» на экране входа — это только явный отказ по
коду. Новый серверный код не требует правки клиента: он покажется своим текстом.

**Корень оказался общим для всех трёх находок: словаря кодов между SQL и
клиентом не было, соответствие не проверял никто.** Механизм есть с обеих
сторон, ошибка живёт ровно между ними и вскрывается только жалобой клиента.
Поэтому коды собраны в один словарь `LOGIN_SERVER_ERRORS` (`heys_auth_v1.js`), а
`__tests__/login-error-codes-contract.test.js` сверяет три стыка: код из
актуальной `verify_client_pin_v3` обязан быть в словаре; код с трактовкой
`explained` обязан иметь ветку на экране; код, который возвращает сам
`loginClient`, обязан иметь ветку на экране. Новый код на сервере без принятого
решения, что о нём читает человек, роняет сборку.

Тест окупился на первом же прогоне: нашёл путь `catch (e)`, где клиенту
показывался текст JS-исключения (`res.message`). Теперь текст исключения живёт
только в `_debug`, а на экране — понятная фраза; из общего fallback
`res.message` убран, чтобы техническая строка не могла всплыть снова.

**Локальный счётчик неудач считает только реально неверный код.** Раньше
`registerFail` вызывался на любой ветке отказа: при падении бэкенда человек
через десять попыток оказывался заблокирован в собственном браузере, ни разу не
ошибившись. Перебор PIN это не ослабляет — подбор всегда даёт
`invalid_credentials`, а настоящая защита — серверная блокировка по номеру
клиента.

Регрессия: `apps/web/__tests__/heys-auth-login-client.test.js` (21 тест),
`apps/web/__tests__/login-error-codes-contract.test.js` (5 тестов).

### Паттерн: контракт кодов между слоями

Дефект был не в коде сервера и не в коде клиента, а в зазоре между ними: обе
стороны исправны, соответствие не проверяет никто, расхождение всплывает жалобой
клиента. Рецепт повторяем и стоит один тестовый файл:

1. собрать коды в один словарь на стороне потребителя, с трактовкой каждого (у
   входа это `wrong_pin` / `rate_limit` / `explained`), а не россыпью условий по
   файлам;
2. вывести поведение из словаря — классификатор читает его, а не свой список;
3. тестом сверить оба конца: код, который возвращает источник (SQL-функция,
   cloud function, API), обязан быть в словаре; код словаря обязан иметь
   осознанную ветку в UI;
4. проверить, что тест роняет сборку: добавить код без ветки и убедиться, что
   падение называет и код, и что вместо объяснения увидит человек.

Отдельно проверять допущения самого теста: `login-error-codes-contract.test.js`
выбирает актуальную миграцию по дате в имени и падает с внятным текстом, если
файлов с этой датой два, если имя без даты или если в выбранном файле нет
определения функции. Тест, который тихо сверяет пустоту, хуже отсутствующего.

Где тот же зазор вероятен (не проверено, кандидаты по числу веток на коды
ответа): `heys_trial_intake_v1.js`, `heys_trial_queue_v1.js`,
`heys_add_product_step_v1.js`, `heys_messenger_v1.js`,
`heys_storage_supabase_v1.js`.

## Вкладка «Отчёты»: четыре вызова несуществующих функций (2026-08-09)

Найдено аудитом кода: четыре места на вкладке «Отчёты» звали функции, которых
нет ни в одном модуле. Ни одно не падало — промах глушили optional chaining и
проверки `typeof`, поэтому в консоли было чисто, а поведение молча ломалось.

| Фантом                         | Что молча ломалось                                       |
| ------------------------------ | -------------------------------------------------------- |
| `HEYS.openProfileModal`        | ссылка «Укажи целевой вес» кликалась и не делала ничего  |
| `window.__loadPostboot3Ui`     | модалка месячных отчётов залипала на «Загружаем модуль…» |
| `HEYS.store.getCurrentProfile` | кэш отчётов не сбрасывался при добавлении еды            |
| `HEYS.products.buildIndex`     | ГИ и вредность в отчётах считались по нулям              |

**1. `HEYS.openProfileModal`.** Проп протаскивался через
`heys_day_stats_block_v1.js` в `heys_day_stats_v1.js`, но определения не было
нигде. Запасной путь `document.querySelector('[data-tab="profile"]')` тоже
промахивался: атрибут `data-tab` встречался во всём `apps/web` ровно один раз —
в этой самой строке. Дополнительно вскрылось, что образец, на который ссылались
(`setActiveTab('profile')`, `heys_app_shell_v1.js:3379`), сам мёртв дважды:
`setActiveTab` только деструктурируется из props в `AppHeader`, но никем не
передаётся, а вкладки `'profile'` не существует — профиль живёт под ключом
`'user'`. Рабочий механизм — `HEYS.App.setTab` / `HEYS.ui.switchTab`, которые
регистрирует `heys_app_tab_state_v1.js`.

**2. `window.__loadPostboot3Ui`.** Неверный неймспейс: реальный глобал —
`HEYS.__loadPostboot3Ui` (`heys_postboot3_facade_v1.js`). Из-за промаха
срабатывал ранний `return`, `setReportsModuleTick` не вызывался, и зависимость
`reportsModuleTick` в модалке была мертва — если открыть отчёты раньше
idle-загрузки чанка, модалка не выходила из состояния загрузки.

**3. `HEYS.store.getCurrentProfile`.** `getClientId()` всегда возвращал
`'guest'`, а `getStorageKey` собирал ключ в перевёрнутом порядке
(`heys_dayv2_<дата>_guest`) вместо канонического `heys_<clientId>_dayv2_<дата>`.
Подпись кэша читала несуществующие ключи, получалась константной — кэш не
сбрасывался никогда. Клиентов на unscoped legacy-ключах это не задевало:
запасной путь `localStorage.getItem('heys_dayv2_<дата>')` у них работал.

**4. `HEYS.products.buildIndex`.** Индекс строит
`HEYS.models.buildProductIndex`, и ему нужен список продуктов; вызов без
аргумента вернул бы пустой индекс, а `undefined` уходил в `getDayTotals` →
`getProductFromItem(it, undefined)`, и позиции без инлайновых
`kcal100`/`protein100` давали нули.

**Фикс.** `HEYS.App.setTab('user')` вместо мёртвой модалки (мёртвый проп убран
из обоих файлов); `window.HEYS?.__loadPostboot3Ui`;
`HEYS.utils.getCurrentClientId`

- канонический порядок частей ключа; локальный `buildProductIndex()` поверх
  `HEYS.products.getAll()`. В подпись кэша добавлено число продуктов — иначе
  отчёт, построенный до загрузки каталога, залипал бы в кэше с нулевыми ГИ.
  Регрессия: `apps/web/__tests__/reports-tab-phantom-calls.test.js` (12 тестов,
  проверены на падение на старом коде).

**Отдельно про доставку.** `heys_day_stats_v1.js` и `heys_day_stats_vm_v1.js` не
входят ни в один бандл — их инжектит `heys_day_stats_bundle_loader_v1.js`, а
ключ `?v=` собирается как «хеш boot-day + константа `DAY_STATS_LAZY_VERSION`».
Правка только этих файлов не меняет ключ, и юзеры получают закешированную
версию: константу надо бампать руками.

**Pattern.** Optional chaining на вызове чужого API (`X?.y?.()`) превращает
опечатку в неймспейсе и вызов несуществующего метода в тихий no-op — навсегда.
Там, где промах означает сломанную фичу, а не деградацию, нужен либо явный
`typeof` с логом, либо тест, который держит связку «вызов ↔ определение». Здесь
четыре таких промаха прожили до аудита при зелёных тестах и чистой консоли.

### Догон: ещё два переключателя вкладки в шапке

Всплыло от первой находки: она ссылалась на `setActiveTab('profile')`
(`heys_app_shell_v1.js`) как на рабочий образец, а образец оказался мёртв
дважды. `setActiveTab` в `AppHeader` только деструктурировался из props, но
никем не передавался — в `heys_app_shell_props_v1.js` его нет. И вкладки
`'profile'` не существует: профиль живёт под ключом `'user'`. Кнопка «Настройки»
в дропдауне аккаунта не делала ничего.

Рядом нашлось хуже — не тихий no-op, а падение. `handlePushBadgeClick` в
`AppHeader` звал `switchTabWithUndoCommit`, объявленный через `const` внутри
`AppTabsNav` — соседнего компонента, не родителя. Для `AppHeader` этого имени
нет в области видимости вообще, то есть клик по бейджу пушей у подписанного
юзера давал `ReferenceError`, а не переход в настройки. Тихим этот промах не был
— просто по нему никто не приходил.

Лечение общее: хелпер поднят на уровень модуля как `commitUndoAndSwitchTab`,
`AppTabsNav` держит тонкую обёртку со старой сигнатурой (шесть её вызовов не
тронуты), оба контрола шапки зовут хелпер напрямую с реальным `setTab` из props.
Мёртвый `setActiveTab` убран из деструктуризации целиком. Регрессия:
`apps/web/__tests__/app-header-tab-switch.test.js` — статическая проверка
областей видимости плюс исполнение самого хелпера (8 из 10 падают на старом
коде).

**Pattern.** Хелпер, объявленный `const` внутри компонента, для соседнего
компонента невидим — но линтер и тесты этого не ловят, если ветка кода редкая.
Общий обработчик, нужный двум компонентам, должен жить на уровне модуля, а не
копироваться по имени.

**Остаётся.** `HEYS.products.buildIndex` — фантом ещё примерно в 25 местах:
`heys_weekly_reports_v2.js` (экран «Итоги недели»),
`insights/pi_analytics_api.js`, `widgets/widget_data.js`,
`heys_day_bundle_v1.js`. Корневое лечение — определить
`HEYS.products.buildIndex` в `heys_core_v12.js` поверх `getAll()` +
`HEYS.models.buildProductIndex`, тогда чинятся все точки разом. Сделано в
коммите `75ea5a760` (`heys_core_v12.js`) — метод определён в ядре, все десять
точек вызова ожили.

## Запись тренировок через коннектор: удаление гасило соседнюю, модель врала числами (2026-08-08)

Найдено независимым аудитом сразу после выкатки записи тренировок. Тесты были
зелёные (968/968) и ни одну из находок не покрывали.

### Потеря данных

**Удаление гасило соседнюю тренировку.** Коннектор проставляет
`source: 'curator_mcp'` во все свои записи. В `trainingDeletionSignature`
(`heys_sync_merge_v1.js:157`) из-за этого всегда срабатывала ветка `fields:`, а
запасной путь `zones:` — единственное, что различало тренировки без времени —
стал мёртвым. Две кардио за день давали одну подпись
`fields:cardio||curator_mcp||`, и tombstone гасил обе. Для двух силовых коллизия
была гарантированной: там `type` всегда `strength`, а `time` необязателен.

Лечится в корне: у каждой записи коннектора теперь уникальный `id`, а в
`trainingDeletionSignature` ветка `id:` идёт первой. Слот `training.id` читался
в трёх местах, но никто его не заполнял — понадобился passthrough в
`heys_models_v1.js`, иначе модель вырезала бы `id` при первом открытии дня.

**Четвёртая тренировка терялась при удалении.** `slice(0, 3)` скопирован из
приложения, но там всего три слота, а коннектор писал сколько угодно. Теперь
список не обрезается, а запись четвёртой отбивается с объяснением.

**Позиционный merge терял сдвинутые строки.** Удаление сдвигает массив влево, а
у записей коннектора свой `updatedAt` (у записей приложения его нет, они падают
на `day.updatedAt`). После сдвига строка сравнивалась с чужой позицией: три
тренировки a/b/c при удалении a давали `[b, b, —]` — c терялась, b задваивалась.
Теперь удаление поднимает штамп всем оставшимся, повторяя поведение приложения.

**Блоб без потолка.** 2000 упражнений × 200 подходов = 25.9 МБ в
`client_kv_store` за 253 мс; один кривой вызов делал день клиента неоткрываемым.
Введены пределы на упражнения, подходы, длину названия и заметки, минуты зоны.

### Модель нагрузки врала

**Готовность структурно не могла стать положительной.** Окно равнялось
постоянной времени: за 42 дня экспонента с τ=42 прогревается на 63%, поэтому CTL
всегда занижен. На идеально ровной нагрузке `tsb` выходил −36.5, и куратор читал
это как хроническое перенапряжение. Теперь ряд стартует со среднего по окну —
стандартное допущение «до окна человек тренировался примерно так же».

Именно этот дефект дал у Александры «готовность −217»: величина была в
значительной степени артефактом окна, а не её состоянием.

**Уверенность была константой.** `daysOfHistory` брался как длина ряда, а ряд
плотный и всегда равен окну — значит всегда 42, и порог `high` недостижим.
Клиенту, заведённому вчера, писали «история 42 дн». Теперь считаются дни, за
которые блоб реально есть.

**Фолбэк MET подставлял чужую зону.** `mets[i] || mets[mets.length - 1]` при
отсутствующем MET брал анаэробные 8 вместо дефолта своей зоны: 30 минут зоны 1
давали 240 MET-минут вместо 75 — расхождение с калорийным расчётом в 3.2 раза.

**Строковые минуты обнулялись.** `typeof x === 'number'` отбрасывал `'30'` из
исторических блобов, хотя калорийный путь их принимает.

### Незадокументированное изменение тоннажа

Сведение двух формул в ядро (коммит `75f6a1725`) попутно изменило поведение на
исторических данных: старый `computeDayTotalTonnage` не имел legacy-пути
`sets × reps × вес` и давал по таким строкам 0, новый считает их полностью. Для
дня со строкой `{sets:3, reps:10, weightKg:'100'}` тоннаж вырос с 0 до 3000. Это
исправление, а не регресс, но в сообщении коммита его не было.

### Паттерн

**Зелёные тесты не значат, что кода достаточно.** Все находки лежали в коде,
покрытом 968 проходящими тестами: тесты проверяли то, что автор задумал, и не
проверяли того, о чём он не подумал. Независимый аудит с воспроизведением на
настоящем `mergeDayData` нашёл за один проход четыре сценария потери данных.

## Расход завышался на ~320 ккал/день: двойной MET, протухший возраст, недозаполненные дни (2026-08-08)

Продолжение разбора нормы. После того как сервер начал считать её сам, стало
видно, что завышена сама формула. Проверено энергобалансом за 31 день:

|                                                  | Расход (base) | +остаточный TEF ≈ полный расход |
| ------------------------------------------------ | ------------- | ------------------------------- |
| Было                                             | 2280          | ~2364                           |
| Стало                                            | 2166          | ~2250                           |
| Факт (вес 91.1 → 91.2 при среднем приходе ~2157) |               | **~2157**                       |

Про TEF важно не ошибиться, как ошиблись при первом подходе: приложение считает
калории в **NET Atwater** (белок 3 ккал/г — его термоэффект уже вшит в
коэффициент, `proteinTEF = 0` в `heys_tdee_v1.js`). Поэтому остаточный TEF — это
только углеводы и жиры, ~84 ккал при этих макросах, а не ~200, как кажется по
привычному «10% от съеденного». Прикидка через 10% завышает ошибку модели вдвое.

Практический итог для клиента с целевым дефицитом −10%: цель = база × 0.9, а
поддержание = база + остаточный TEF. До правок это давало реальный дефицит ~105
ккал/день, после — ~207 при той же настройке. То есть настройка не менялась, а
дефицит удвоился — раньше половину съедала завышенная база.

### Три причины

**1. Возраст брался из протухшего поля.** В блобе профиля лежало `age: 30` при
дате рождения 1988 года. И приложение (`calcBMR`: `+p.age || 30`), и коннектор
(`Number(p.age) || ageFromBirthDate(...)`) предпочитали поле дате. Карточка
профиля при этом показывала 38, потому что `profile.js` перезаписывает `age`
вычисленным — то есть на экране 38, а в BMR 30. Плюс 40 ккал каждый день.

Мест, где возраст разрешается заново, оказалось **три**, и решающим было не то,
что нашли первым: `getProfile()` в `heys_day_utils.js` собирает урезанную копию
профиля для всей вкладки дня и жёстко ставила `age: +p.age || 30`, выбрасывая
`birthDate`. Пока это место не починили, правки в `calcBMR` и в коннекторе
ничего не меняли на экране — до расчёта просто не доезжала дата рождения.

**2. Один MET считался дважды.** BMR покрывает все 24 часа на уровне 1 MET, а
активность добавлялась по брутто-MET. 140 минут быта по MET 2.5 давали +559
ккал, из которых ~224 уже сидели в BMR. То же с зонами тренировок (2/3/5/8).
Теперь везде нетто: `netKcalPerMin(met) = kcalPerMin(met − 1)`.

Композиций формулы было **две**: `heys_tdee_v1.js` и отдельная сборка по частям
в `heys_day_utils.js:getActiveDaysForMonth`, которая кормит `baseTarget` прошлых
дней. Починены обе — иначе приложение и сервер разъехались бы снова.

**3. Недозаполненный дневник превращался в разрешённую прибавку.** Порог, ниже
которого расчёт долга перестаёт верить дню, был `optimum / 3` (33%), а баннер с
вопросом «голодание или не всё внесено» показывался ниже 50%. День на 53% нормы
(875 из 1638) не вызывал вопроса и уходил в окно как настоящий недобор 763 ккал
— а завтрашняя норма на эту величину поднималась. За пять дней система вернула
+841 ккал при целевом дефиците ~200/день.

Оба порога сведены к 70%. На реальных данных за 31 день это отсекает ровно пять
дней с явным недологом (986, 772, 806, 1294, 875) и ни одного лишнего; при 33%
не отсекалось ни одного.

### Чего намеренно не сделали

- **NEAT-пол не добавлен.** Гипотеза была, что двойной счёт MET компенсирует
  отсутствие минимального расхода сверх BMR. Калибровка её опровергла: модель и
  так завышала, пол увёл бы ещё дальше (при 15% → TDEE 2647 против факта 2157).
- **Остаточное завышение ~93 ккал не «подкручено».** Это либо неполный дневник
  (недоотчёт 20–30% — обычное дело), либо остаточный оптимизм модели. Из
  имеющихся данных не разделяется, а лишний коэффициент — это подгонка. Величина
  того же порядка, что погрешность допущения «недозаполненные дни были по 2000».
- **Считать «день не дозаполнен» по числу приёмов — отказались.** Один-два
  приёма в день это нормальный режим, а не пропуск. Признак — калории плюс явный
  ответ пользователя, а не форма данных (инвариант №7 в `CLAUDE.md`).

### Паттерн

**Калибровать по результату, а не по теории.** Обе правки формулы выглядели
разумно и по отдельности, но только сверка с фактическим энергобалансом
показала, какая из них нужна, а какая сделала бы хуже.

## MCP отдавал норму дня из протухшего кэша отрисовки (2026-08-08)

Нашла Александра 07.08.2026: коннектор куратора отдал норму 1282 ккал, когда в
приложении в тот же момент стояло 2209. Два вызова `heys_get_day` по одному и
тому же дню с разницей в 15 минут дали 1282 и 2209 — между ними никто не менял
ни шаги, ни тренировку. Изменилось одно: клиент открыл экран.

### Корень

`dailyNorm` (`yandex-cloud-functions/heys-mcp/lib/day.js`) безусловно
предпочитал `day.savedDisplayOptimum`, когда он > 0. А это не норма, а **кэш
отрисовки**: его пишет только браузер из `useCaloricDisplayState`
(`apps/web/heys_day_caloric_display_state.js`) и только пока клиент держит день
открытым, с троттлингом 2 с и мёртвой зоной 5 ккал. Записи куратора через MCP
кэш не трогают — он замерзает на моменте последнего просмотра, пока входы, из
которых он посчитан (шаги, тренировки, вес), продолжают меняться.

У Александры 1282 — слепок утра, до 13 320 шагов и 79 минут тренировки.

Ошибка не косметическая: норма — знаменатель всего. «1735 из 1282» читается как
перебор на 453 ккал, «1735 из 2209» — как недобор 474. Знака у ошибки нет: если
клиент открыл день после рефида, кэш наоборот завышен. И тихо: `note` гласил
«Норма, которую клиент видит в приложении».

### Что сделано

Первым заходом был стопгап — отпечаток входов рядом с кэшем и сверка на
свежесть. Он снимал большую часть расхождения, но зависимость от «зайти в
приложение» только уменьшал: поправку на долг всё равно брали из кэша, а у дня,
который клиент не открывал, её не было вовсе. Поэтому доведено до конца: сервер
считает норму целиком и кэш для решений не читает.

**1. Ядро расчёта долга вынесено из React-хука** в
[heys_day_caloric_debt_core_v1.js](heys_day_caloric_debt_core_v1.js) — дословно,
скриптом, без правки формул. Хук зовёт его и деструктурирует 28 промежуточных
значений; советы и аналитика остались на месте. Ядро зеркалится в
`heys-mcp/lib/web-mirror/`, так что формула долга одна на приложение и сервер.

**2. Сервер считает норму целиком** (`heys-mcp/lib/day.js`, `dailyNorm`): база
по TDEE, надбавка за вчерашнюю тренировку, долг/перебор зеркальным ядром по окну
из трёх прошлых дней, загрузочный день через зеркальный `getRefeedOptimum`.
Порядок веток повторяет `heys_day_caloric_display_state.js`. Источник теперь
`computed` (или `estimate`, если окна прошлых дней нет).

**3. `savedDisplayOptimum` больше не источник числа.** Он возвращается в
`norm.parts.client_saw`, и при расхождении `note` называет его вслух — молчать
об этом нельзя, именно так протухший кэш и прожил незамеченным.

**4. `normText` (`lib/tools.js`) называет источник своим именем.** Раньше «та,
что видит клиент» стояло у всего, кроме `estimate`.

### Что важно знать про слепые зоны сервера

Вопреки первоначальному разбору, множитель цикла сервер считает сам:
`heys_cycle_v1.js` лежит в зеркалах и берёт `day.cycleDay` из блоба. NDTE тоже
оказался доступен: `calculateNDTE` — чистая функция, а вчерашний блоб серверу
виден напрямую. Не используется только `getPreviousDayTrainings` из зеркала — он
берёт `new Date()` процесса, а функции Yandex Cloud живут в UTC, поэтому
затухание уехало бы на три часа; сервер собирает входы сам и берёт час из
`MOSCOW_TZ`.

Точного совпадения с экраном «в любой момент» не бывает по построению: NDTE
затухает по часам, поэтому число в приложении меняется в течение дня само.

### Грабли

- `heys_iw_utils.js` молча выходит, если `heys_iw_constants.js` ещё не загружен.
  Порядок в `MIRRORED_FILES` обязан совпадать с
  `scripts/legacy-bundle-config.mjs`. Тихий выход ничего не ронял, поэтому в
  загрузчик зеркал добавлены явные проверки: без них NDTE стал бы нулём без
  единой ошибки.
- Внешний `try/catch` в хуке превращает любую ошибку в `null`, а `null` тихо
  снимает надбавку с экрана. Поэтому список из 28 имён для деструктуризации
  вычислен скриптом и проверен `eslint --rule no-undef`, а не глазами.
- `fakeApi` в тестах отдавал один и тот же блоб на любой ключ `heys_dayv2_*` —
  окно долга набивалось копиями сегодняшнего дня. Фейк сделан date-aware.

### Паттерн

**Кэш отрисовки — не источник правды для читателя, который не рисует.** Если
поле пишет один клиент в одном контексте (открытый экран), а читают его другие
(коннектор, аналитика, календарь), оно обязано нести отпечаток входов, по
которому читатель проверит актуальность. Иначе расхождение всплывает не как
ошибка, а как правдоподобное число.

  клиент шлёт устаревший blob.
- UI handler `setGrams` (apps/web/day/\_meals.js:4421) выставляет
  `item.updatedAt` и `meal.updatedAt` явно.

**2. Централизованный stamping (commit
`ad3b4493 fix(sync): stamp day mutations centrally`):**

- `stampDayv2ChangedEntities` в storage interceptor штампует изменённые
  meals/items/trainings по diff prev/next dayv2 в LS — handlers больше не
  обязаны помнить про timestamps. setItem из любого handler'a автоматически
  получает корректные стампы.
- Затем pure helpers вынесены в `heys_sync_merge_v1.js` (UMD-wrapped), доступны
  тестам через CJS-копию.

**3. HMR-safe резолв + порядок чеков (2026-06-04, follow-up):**

- `resolveDayMutationTs` больше не инжектит `Date.now()` при `nextTs=0` и **не
  использует `prevTs+1`** — возвращает `0` всегда, когда caller не передал
  day-level `updatedAt`. При `mutationTs=0` весь stamper возвращает payload как
  есть (без модификаций и без emit'a tombstone'ов). Причина: interceptor патча
  `localStorage.setItem` стампит **до** того, как payload дойдёт до HMR-guard'a
  в `saveClientKey` (`if (!value.updatedAt && !value.schemaVersion)`). Любой
  авто-инжект TS вкладывал бы HMR/bad-state writer в LS, а следующий upload
  через saveClientKey уже видел бы валидный updatedAt и пропускал guard.
  Реальные user-mutation handlers (например `setGrams` в `day/_meals.js` через
  `markUndoWindow(3000)`) всегда выставляют `day.updatedAt` явно — stamper
  делает item/meal/training-level stamps ТОЛЬКО производными от него.
- Stamper в `saveClientKey` теперь вызывается **после** HMR-чека —
  defense-in-depth, чтобы auto-инжект (если когда-нибудь вернётся) не мог обойти
  guard.
- Stale-cloud guard на pull-стороне
  ([heys_storage_supabase_v1.js:12275](apps/web/heys_storage_supabase_v1.js#L12275),
  `if (localUp > remoteUp) return false`) остался без изменений, но теперь
  безопасен: stamper не инфлирует local TS в будущее.

### Что НЕ закрыто этими фиксами (ceiling)

- **Clock-skew**: вся LWW-логика опирается на `Date.now()` устройства. Спешащий
  телефон со stale данными может выиграть конфликт. Окончательный фикс —
  server-revision write-merge (L4+, см. project_sync_revision_rollout),
  deferred.
- **L3 server-revision pull-gate** source-fixed 2026-06-14: после того как
  клиент увидел server-revision checkpoint, no-revision pull больше не может
  перезаписать ключ, для которого уже известна local revision. Остающийся
  ceiling — write-merge/CAS для device-clock конфликтов и production
  deploy/bundle.

### Pattern to watch

1. **Никогда не правь handler-by-handler.** Параллельные агенты легко попадают в
   дубль-копии (см. `heys_day_meal_handlers.js` → `day/_meals.js`). Логику,
   которую можно вывести из diff prev/next в storage layer, выводи там, а не
   размазывай по handlers. Stamper делает это для timestamps и теперь для
   item-deletion.
2. **CJS/ESM mirror checks** обязательны для любого кода, который дублируется
   между client и serverless function.
3. **Не инжектить timestamps если caller их не передал.** Stamper при
   `nextDay.updatedAt = 0` возвращает payload как есть (ни `Date.now()`, ни
   `prev+1`). Clock-skew инфляция блокирует legitimate pulls в stale-cloud guard
   ([heys_storage_supabase_v1.js:12275]); `prev+1` тоже опасен — interceptor
   стампит до HMR-guard'a. Реальные user-mutation handlers всегда выставляют
   `day.updatedAt` явно.
4. **Tombstone-aware promotion в stamper.** Если `item.id` уже в
   `prev.deletedItemIds`, stamper НЕ повышает `item.updatedAt` до `mutationTs`.
   Stale React-стейт, пишущий удалённый item обратно с свежим `day.updatedAt`,
   без guard'a получил бы свежий item-стамп и обошёл tombstone-фильтр на merge.
   Истинное re-добавление безопасно: caller выставляет
   `item.updatedAt = Date.now() > tombstoneTs` — фильтр пропускает.

### Сопутствующее: RPC 500 `log_client_event_by_session`

Параллельно расследовали 500 на boot'е (POST
`/rpc?fn=log_client_event_by_session`). Гипотезы про SQL constraint / pgcrypto /
jsonb size / ts cast — **все основаны на «SQL exception доходит до Yandex
catch»**. Не дочитали
`EXCEPTION WHEN OTHERS THEN RETURN jsonb_build_object('success', false, 'error', SQLERRM)`
в SQL функции (`database/2026-05-25_client_event_log.sql:110-113`). Этот
catch-all **физически блокирует** все exception'ы → клиент получил бы 200 OK с
`{error: SQLERRM}`, не 500. Реально 500 = JS-уровень exception в Yandex функции.
Изначально defer'нули (commit 48244ecf), но root cause найден через несколько
часов — см. POSTSCRIPT ниже.

#### POSTSCRIPT (через несколько часов): root cause найден — TYPE_HINTS

**Реальная причина** (нашёл пользователь, не я): в
`yandex-cloud-functions/heys-api-rpc/index.js` есть таблица `TYPE_HINTS` со
списком RPC функций, для которых JS-массивы сериализуются как `::jsonb` (через
`JSON.stringify` перед `client.query`). `log_client_event_by_session`
**отсутствовал** в этой таблице. Без hint pg-driver сериализовал JS-массив
объектов как Postgres array literal (`{1,2,3}` text), не как jsonb → pg-driver
throws JS-уровня **без SQLSTATE** → catch на index.js:2785 возвращает generic
`INTERNAL_ERROR` без detail → клиент видел 500.

За сутки с момента деплоя миграции (2026-05-25) **ни одно событие** не
записалось в `client_event_log` через RPC. Каждый flush батча падал
deterministic'ом. Подтверждено в БД: при первом запросе после deploy (commit
20000a69 = `fix(api-rpc): add jsonb type hint`) первое же событие
(sync-products) записалось с id=2.

#### Урок (4-й случай каскадной ошибки в этой же сессии)

Я после «catch-all глушит SQL → значит не SQL» пошёл **горизонтально** улучшать
диагностику (3 миграции: RAISE NOTICE → WARNING → GET STACKED DIAGNOSTICS), а не
**вверх** — в JS Yandex функции где формируются параметры запроса. Лечение
симптома, не root cause.

Правильный путь: **catch-all поймал → exception источник в одном слое ВЫШЕ,
читай call site**. Для SQL функции это JS код где `client.query(sql, params)`
вызывает её — там TYPE_HINTS, prepared statement build, connection pool.
**Большинство 500 от RPC начинается именно тут**, не в SQL.

См. `feedback_partial_reads_cascade.md` (user-memory) → раздел «Расширение
правила: один слой выше когда catch-all поймал» для полного паттерна.

**Бонус ценность диагностических миграций**: «горизонтальные» фиксы не пропали
зря — после следующего 500 в любой `log_*` функции pg server log получит полный
SQLSTATE/DETAIL/HINT (RAISE WARNING + GET STACKED DIAGNOSTICS) + Yandex CF log
получит detailed error info (needsDetailedLog whitelist расширен на `log_*`).
Root cause этого инцидента fixed, но улучшенная диагностика остаётся как safety
net для будущих похожих случаев.

### Урок 1: catch-all инвертирует exception-hypotheses

Для утверждений «X вызывает Y» — читать тело функции X **до конца** ДО
формулировки гипотезы. Если у X есть catch-all (`try/catch`,
`EXCEPTION WHEN OTHERS`, fallback chain, generic error handler) — он **физически
блокирует** все exception-based выводы «снизу-вверх». Помечать такие гипотезы
«невозможно по конструкции» прежде чем перебирать root causes.

Паттерн повторился дважды в одной сессии (swipe save + RPC 500). См. user-memory
`feedback_partial_reads_cascade.md`.

### Урок 2: `EXCEPTION WHEN OTHERS THEN RETURN` — системный паттерн

Grep по `database/*.sql` нашёл **~45 occurrences в 26 файлах**. Не каждое
использование — антипаттерн: для business RPC возврат `{success: false}` —
правильное поведение. Но для **debug/logging/audit** функций глушение SQLSTATE /
detail / hint / where делает диагностику из prod-логов Yandex невозможной (catch
на index.js:2760 видит только generic `error.message`).

Action items (записано в todo.md, 48244ecf):

- Расширить `needsDetailedLog` whitelist в
  `yandex-cloud-functions/heys-api-rpc/index.js:2745` на
  `log_client_event_by_session` (иронично — log-функция без полного prod-лога).
- Для debug-RPC (`log_client_event_by_session`, `*_audit_*`, `track_*`) —
  добавить `RAISE NOTICE` стек-trace перед `WHEN OTHERS THEN RETURN`. Логически
  эквивалентно, но pg-логи получат detail.
- Poison-pill detection в client-side `_flush` (`heys_event_log_v1.js`): если
  batch упал N раз подряд — drop'нуть head event и попробовать остаток. Иначе
  один битый event навсегда блокирует всю очередь.

### Урок 3: deferred config.save vs immediate writes — design tension

StepModal config.save фаерится только на финале — сознательный контракт
(«крестик = не сохранять»). Но для **критичных полей** (вес, замеры)
пользователь интуитивно ожидает «ввёл — сохранилось». Решение: immediate write в
day-snapshot (черновик), profile-level state (TDEE/BMR база) — только финалом.
Для других полей (sleep, mood, supplements) — оставлено deferred; если
аналогичные жалобы — применить точечно, не менять контракт глобально.

1. **`lint-direct-localstorage-writes`** — Wave 2 добавил код в

### Урок

Worktree isolation защищает агентов друг от друга **во время работы**, но при
merge в main срабатывают cross-cutting эффекты:

- **Line numbers** в allowlist привязаны к абсолютной позиции в файле —

- **Bundle hashes** генерируются из контента — изменение в любом source-файле →

- **whats-new entries** в `releases[]` массиве — два агента могут добавить
  entries параллельно, git merge оставит оба, но порядок может быть неверный.

### Workflow для будущих parallel merges

После merge всех worktree, **до push**, последовательно:

1. `node scripts/lint-direct-localstorage-writes.mjs` — если ❌, вручную
   обновить line numbers в `scripts/bootstrap-bypass-allowlist.txt`.
2. `git log -1 --format=%h` — посчитать новый hash, добавить `whats-new.json`
   entry, commit `chore(release): bump whats-new build hash to <HASH>`.
3. `pnpm test && pnpm lint && pnpm tsc` — финальный gate.
4. `git push` — теперь pre-push hook пройдёт.

## Orphan-баннер + cleanup hardening (2026-05-24)

День `2026-05-23` (клиент `4545ee50…`) показывал баннер «1 продукт не найден в
базе» на штатной сессии без видимой причины. Расследование вскрыло **класс
проблем** одновременно:

### Что нашли

1. **Три product_id из meal-items вообще отсутствуют в personal overlay** —
   `p_1769271889662_72os3b`, `p_1769271889661_x9nqxy`, `p_1769271889661_ina83q`
   (хлеб, творожный сыр, твёрдый сыр). Формат `p_<timestamp>_<random6>` —
   typical для `restoreFromSharedBase`
   ([heys_core_v12.js:2780](heys_core_v12.js#L2780)), массового импорта shared →
   personal. Timestamp 1769271889661 = 24 января.
2. В overlay-снимке от 10 мая (backup-key) этих 3 id **уже не было** — значит
   удалены до 10 мая. **Tombstone не проставлен** (отсутствуют в
   `heys_deleted_ids`).
3. Имена точно совпадают с тремя записями в `shared_products`. Только 2 из 3
   успевают резолвиться через shared-кеш — один остаётся в orphan-tracker из-за
   race между `getDayData` inline-tracking (на каждый re-render) и
   `recalculate()` (запускается только на shared cache load /
   heysProductsUpdated / date change).
4. `renderOrphanAlert.trulyUnresolved` фильтр
   ([heys_day_orphan_alert.js:50](heys_day_orphan_alert.js#L50)) использует
   только `HEYS.products.getById()` без fallback в shared cache — поэтому баннер
   показывает даже разрешимых orphan'ов.

### Корневая причина исчезновения 3 продуктов

`cloud.cleanupProducts()`
([heys_storage_supabase_v1.js](heys_storage_supabase_v1.js)) и мёртвый
`cleanupProductRecord` использовали shape-inference filter
`.filter(p => p && typeof p.name === 'string' && p.name.trim().length > 0)` —
тот же класс бага, что снёс 366 → 28 продуктов в инциденте 2026-05-11 (cloud
cleanup destruction). Эти функции активно вызывались из `bootstrapSync`,
full-sync defer'ов и могли удалить любую запись с нестандартной shape (overlay
TypeA, transient import-pasted объекты), **не проставляя tombstone**.

### Fix (план rustling-dazzling-bentley.md, Wave 1)

- **F1**: `cloud.cleanupProducts()` → no-op + лог. Все 3 caller-а уже обёрнуты в
  try/catch.
- **F2**: `cloud.cleanupCloudProducts()` + `cleanupProductRecord()` (мёртвый
  код, callers закомментированы после 2026-05-11) → no-op. Уменьшение surface
  для случайной реактивации.

Дальнейшие волны (Wave 2-4): централизованный shrink-guard в
`HEYS.products.setAll()` + `OverlayStore.writeRaw()` (✅ **deployed** в
`heys_core_v12.js:4671-4791` с kill-switch `__heys_disable_shrink_guard__`);
shared-fallback в renderOrphanAlert; defensive re-check в getDayData; авто-clone
из shared при тихом resolve; tombstone-aware shrink-tolerance в cloud-sync
(закрывает live bug — раньше >5% shrink REJECT в infinite loop, теперь pass если
все исчезновения tombstoned).

### Урок

Cleanup-функции с shape-inference filter — **antipattern**. Форма данных в LS
эволюционирует (overlay TypeA, tombstone-only arrays, deserialization
transients), любое «удалить если поля X нет» неизбежно убивает legitimate
записи. Единственный безопасный путь — **явный tombstone-список** (или versioned
migration). См. также CLAUDE.md правило «Never write cleanup/garbage-collection
by shape inference».

## Серия архитектурных hack'ов (2026-05-23)

Один день — пять связанных багов, все с одним метакорнем: **то что код заявляет
о своём поведении и то что реально делает интерсептор — расходятся**.

### 1. `refreshProfileSubscription` race с Phase A

[heys_subscriptions_v1.js:1430](heys_subscriptions_v1.js#L1430). На
`heys:auth-changed` через 200ms читал legacy `heys_profile` через `lsGet`
(memory cache возвращал stale `{}`), спредил, через `lsSet` → `nsKey()` скоупил
в `heys_<cid>_profile` → затирал результат Phase A (32-полевый профиль из БД)
4-полевым subscription-only объектом.

`shouldShowMorningCheckin` видел «incomplete» профиль и открывал wizard с
регистрационными шагами повторно после каждого reload.

**Fix**: force-raw read scoped LS + guard на `hasPersonalMarkers` — не пишем
`heys_profile` пока cloud sync не приземлил personal-поля. Subscription portion
придёт сам из той же row.v.

### 2. `ack_curator_changelog` precision-mismatch JS↔PG

[heys-api-rpc/index.js:2130-2160](../../yandex-cloud-functions/heys-api-rpc/index.js#L2130).
`Date.toISOString()` режет timestamp до миллисекунд (`.566Z`), Postgres хранит
микросекунды (`.566961`). Сравнение `created_at <= untilTs` пропускало записи с
µs, `last_seen_at` обновлялся до ms-precision, следующий запрос возвращал ту же
запись → банер показывался повторно после каждого «Понял».

**Fix**: `+ INTERVAL '1 millisecond'` tolerance к обоим UPDATE.

### 3. `heys_xp_cache_<cid>` zombie mirror

[heys_gamification_v1.js:1508](heys_gamification_v1.js#L1508). Comment заявлял
«Local-only XP cache (not synced to cloud, survives cloud overwrites)», но ключ
начинался с `heys_*` → `isOurKey()` → mirror через interceptor. В БД у клиента
1.5-месяцев старая копия XP, на cold-start на новом устройстве она приземлялась
в LS через Phase A loop и UI 30+ сек показывала неправильное число.

**Fix**: добавлен `'heys_xp_cache_'` в `LOCAL_ONLY_STORAGE_PREFIXES`
([heys_storage_supabase_v1.js:1813](heys_storage_supabase_v1.js#L1813)). Comment
теперь правда.

### 4. `heys_products_overlay_v2_BACKUP_*` тот же gap

Аналогично п.3, но новый outlier: gap в
[`isLocalOnlyStorageKey`](heys_storage_supabase_v1.js#L1816) —
`includes('_products_BACKUP_')` ловил `heys_products_BACKUP_` и
`heys_hidden_products_BACKUP_`, но **не** `heys_products_overlay_v2_BACKUP_*`
(между `products` и `BACKUP` стоит `_overlay_v2_`).

**Fix**: добавлена явная regex-проверка `/_products_overlay_v2_BACKUP_/`.

### 5. Phase A не приземлял `heys_game` / `heys_subscription_status`

[heys_storage_supabase_v1.js:6555-6580](heys_storage_supabase_v1.js#L6555).
Critical keys list изначально содержал 5 ключей:
profile/norms/products/hr_zones/today.

- `heys_game` (XP/level/badges) не входил → gamification-bar на cold-start
  показывала default totalXP=0 или ~25 (event-based partial fallback) пока full
  sync через 5-20 сек не приземлит.
- `heys_subscription_status` тоже не входил → `paywall.canWriteSync()`
  fail-open: пользователь с истёкшим триалом мог сделать write до приземления.

**Fix**: оба добавлены в Phase A. Плюс `heys_widget_layout_v1` для устранения
flash дефолтной сетки виджетов.

### Общие уроки

1. **Comment-claim ≠ runtime behavior**. Любой
   `localStorage.setItem('heys_*', ...)` зеркалится в облако через interceptor —
   это **default**, локальность нужно ОБЪЯВЛЯТЬ через
   `LOCAL_ONLY_STORAGE_PREFIXES`/`SUFFIXES`/`EXACT_KEYS`. Если comment говорит
   «local-only», но имя key начинается с `heys_` и ничего не занесено в
   blocklist — comment врёт.

2. **Race `lsGet → mutate → lsSet`** — паттерн где module читает LS, добавляет
   одно поле и пишет обратно. Если LS не приземлён cloud sync'ом — write создаёт
   частичный объект. Защита: либо force-raw read из scoped LS, либо guard на
   необходимые поля, либо server-side `mergeScalarKv` (field-level merge
   сохраняет existing).

3. **JS↔PG timestamp precision**. `Date.toISOString()` режет до миллисекунд,
   Postgres хранит микросекунды. Любое сравнение `WHERE col <= $ts` где `$ts`
   пришёл от клиента — добавлять `+ INTERVAL '1 millisecond'` tolerance.

4. **Phase A critical keys** = быстрый UI cold-start. Если UI читает ключ
   синхронно при первом рендере (gamification-bar, paywall gate, widget layout)
   — он должен быть в Phase A. Сейчас в списке 9 base-keys (~80-100 KB payload),
   запас ещё есть.

5. **Inline-cid в имени key** = архитектурный outlier. Все scoped ключи должны
   иметь форму `heys_<cid>_<base>` (prefix scope). Если cid в суффиксе
   (`heys_xp_cache_<cid>`, `heys_insights_feedback_<cid>`) — это double-scope и
   потенциальный bug при Phase A loop'е. Лечить через rename или
   `LOCAL_ONLY_STORAGE_PREFIXES`.

**Pattern to watch**: ревью любого нового `localStorage.setItem('heys_*', ...)`
писателя должно отвечать на 3 вопроса:

- Это action user-initiated или background sync?
- Объявлен ли ключ как local-only явно через `LOCAL_ONLY_STORAGE_*`?
- Защищён ли writer от race с cloud sync (force-raw read + guard или server-side
  merge)?

## Day-write race fix (2026-04-26)

Symptom: adding a product to a meal silently disappeared after refresh.

**Double race condition**:

1. **`flush()` closure-drift** in `useDayAutosave`
   ([heys_day_core_bundle_v1.js:2286](heys_day_core_bundle_v1.js#L2286)). React
   `useCallback` captured `day` via closure with `[day, ...]` deps. After
   `setDay(prev → newDay)` `addProductToMeal` scheduled `flush()` via
   `requestAnimationFrame(setTimeout(.., 50ms))`, but React commit hadn't
   propagated to closure → flush saw stale `day` → exited via guard
   `freshestDaySnap === daySnap` without writing.

   **Fix**: flush now reads `HEYS.Day.getDay()` (ref-based via `dayRef.current`)
   and prefers it when newer, with `force = true` to bypass downstream guards.

2. **Gamification overwrite**
   ([heys_gamification_v1.js:2270, :2549](heys_gamification_v1.js)). On
   `heysProductAdded` → `addXP → updateDailyMission/getDailyMissions` read
   `dayv2` from LS (stale, without the freshly added product), patched
   `dailyMissions` field, then wrote the entire object back — clobbering the
   user's add.

   **Fix**: re-read LS immediately before each `setStoredValue(dayKey, ...)` and
   merge only `dailyMissions` field on top of the freshest snapshot.

Both fixes needed together — fixing only one leaves the other path open.

**Pattern to watch**: callbacks scheduled outside React's commit phase
(`setTimeout`/`requestAnimationFrame`) capture closures that may be stale by the
time they fire. Always prefer ref-based reads (`dayRef.current`,
`HEYS.Day.getDay()`) over closure-captured state for late-firing writes.

## State-sync clobber pattern (2026-05-08)

A recurring class of bug across multiple LS-backed user-state keys.

**The pattern**:

1. Module A explicitly writes a shared LS key (e.g. `saveProfileSafe` in
   supplements writing `heys_profile`).
2. Module A dispatches a NARROW event (e.g. `heys:supplements-updated`) but not
   the broader `heys:profile-updated`.
3. React component B (e.g. `UserTabBase` in
   [heys_user_v12.js](heys_user_v12.js)) holds the same key in React state and
   listens ONLY for the broader event.
4. Component B's stale state isn't refreshed.
5. User edits any field in component B → its debounced auto-save (300ms for
   norms, 1000ms for profile/zones) writes the ENTIRE stale state back, with a
   fresh `updatedAt` → uploaded to cloud, clobbering writer's changes.

Symptom: a setting silently reverts after the user touches an unrelated field in
the user tab — sometimes minutes later, sometimes after sync roundtrip from
another device.

**Confirmed via cloud audit** for `plannedSupplements`:
`profile.plannedSupplements: []` while
`dayv2.supplementsPlanned: ["omega3","b12"]` persisted in day data — the plan
was actively synced to days but the profile field was overwritten.

**Fix template** (applied to `heys_profile`, `heys_norms`, `heys_hr_zones`):

1. **Writer side** — every explicit writer dispatches the canonical event
   (`heys:<key>-updated`) immediately after LS write. Detail object:
   `{ field?, fields?, source }`.
2. **HOT-sync interceptor** — `dispatchForegroundHotSyncProfileEvents` in
   [heys_storage_supabase_v1.js](heys_storage_supabase_v1.js) automatically
   dispatches the event whenever HOT-sync writes the key — covers cross-device
   cloud sync without each writer having to know.
3. **Listener side** — every component holding the key in React state subscribes
   to `heys:<key>-updated` and refreshes via `updatedAt` timestamp compare
   (`prevTs > newTs ? prev : incoming`) so concurrent user edits don't get
   clobbered by older external writes.

**Adding a new shared LS-backed setting** — verify:

1. Search for `setTimeout` + `lsSet`/`writeStoredValue` near the new key —
   that's the auto-save site.
2. Confirm there's a paired `addEventListener('heys:<key>-updated')` that
   refreshes state.
3. Confirm every external writer dispatches `heys:<key>-updated`.
4. If HOT-sync syncs the key, extend `dispatchForegroundHotSyncProfileEvents`.

**Already-vulnerable spots** (audit 2026-05-08):

- `heys_grams_history` — multiple meal-module writers, no event dispatch. Safe
  today (no React-state holder) but track if a future component caches it.
- Legacy `heysAdviceSettingsChanged` event naming — should rename to
  `heys:advice-settings-updated` if a listener is ever added.

open question, но фикс работает независимо.

1. **`readProfileForceRawScoped`**
   ([heys_morning_checkin_v1.js:44](heys_morning_checkin_v1.js#L44)) +

   `[MorningCheckin] 🛡️ partial subscription-only profile — sync in progress, deferring wizard`.

`console.error('[MorningCheckin] readProfileForceRawScoped DIAG', ...)`. По

```js
localStorage.removeItem(`heys_${HEYS.currentClientId}_profile`);
location.reload();
```

## Orphan data leak in `client_kv_store` (2026-05-11)

Symptom: 48 client_ids accumulated ~3.2 MB of data in cloud despite being
deleted from `clients` table months ago.

**Root cause #1**: `client_kv_store` was the only table referencing
`clients(id)` without a FK constraint. When curator deleted a client via UI, the
`clients` row was removed but kv_store data remained orphan. 10 other tables
(consents, payments, subscriptions, ...) had `ON DELETE CASCADE` — kv_store was
the asymmetric outlier.

**Root cause #2**: trigger `fn_bump_change_marker` on
`client_kv_store AFTER INSERT/DELETE/UPDATE FOR EACH ROW` blindly UPSERTed into
`client_change_markers` for every changed row. The marker's own FK to `clients`
(with CASCADE) made any cleanup of orphan kv_store rows impossible without admin
workarounds: trigger fires → INSERT into markers → FK violation because the
orphan client_id has no `clients` row.

**Fix** (migration `database/2026-05-11_kv_store_cascade.sql`, applied
2026-05-11):

1. Added EXISTS guard to `fn_bump_change_marker` — silently skip orphan
   client_id (defense in depth).
2. Added FK `client_kv_store_client_id_fkey` with `ON DELETE CASCADE`.

After migration:

- DELETE FROM clients automatically removes corresponding kv_store rows
- INSERT with non-existent client_id is rejected by FK validation
- Future orphans are structurally impossible

**Cleanup procedure used** (one-time, before adding the FK — preserved as DR
reference):

1. Backup orphan data to `client_kv_store_archive_20260511`
2. Insert temporary placeholder rows into `clients` for each orphan client_id
3. DELETE FROM client_kv_store WHERE client_id NOT IN (active list) — trigger
   now succeeds because clients row exists
4. DELETE FROM clients WHERE name LIKE '_garbage_cleanup_%' — CASCADE removes
   markers

**Pattern to watch**: when adding a new table that references `clients(id)`,
always include `ON DELETE CASCADE`. Audit other tables periodically — any
missing FK is a future orphan leak.

## Cloud cleanup destroying overlay data (2026-05-11)

Symptom: curator opened Poplanton client and table showed 139 products instead
of 366. Hard reload restored to 366. Logs revealed `[CLOUD CLEANUP]` silently
deleting valid data on every switch and once per boot.

**Root cause**: `cleanupProductRecord` in
[heys_storage_supabase_v1.js:5228](heys_storage_supabase_v1.js#L5228) decides
"valid vs invalid" by checking `.name` field:

```js
const cleaned = products.filter(
  (p) => p && typeof p.name === 'string' && p.name.trim().length > 0,
);
```

This logic predates the overlay v2 rollout. The breakage:

1. **Overlay TypeA rows** have shape
   `{id, shared_origin_id, overrides, in_my_list}` — `.name` lives in the shared
   catalog, denormalized at read time. Cleanup classifies all TypeA rows as
   garbage. Observed: 366 → 28 (338 rows wiped in single pass).
2. **`heys_hidden_products`** is an array of product IDs (strings). Strings have
   no `.name`. Cleanup deletes the whole key as "garbage".
3. **`heys_favorite_products`** — same shape, same fate.
4. **Backup keys** (`*_BACKUP_*`) get matched by the cleanup's regex and pruned
   too.

Affected for Poplanton (`ccfe6ea3`):

- `heys_hidden_products`: 289 IDs → deleted entirely
- `heys_favorite_products`: 4 IDs → deleted entirely
- `heys_products_overlay_v2`: temporarily 366 → 28 (LS restored on next sync)
- `heys_products_overlay_v2_BACKUP`: 433 → 139 (cleanup pruned the backup)

The overlay destruction was not permanent because LS still held the 366 rows and
pushed them back to cloud via auto-sync. If user had cleared LS first, data
would be lost.

**Fix** (commit `78d9136e`): disabled all three `cleanupProductRecord` /
`cleanupCloudProducts` call sites (bootstrap clientSync ~6516, full-sync
post-completion ~8714). Left explicit comments naming the breakage modes.
Restored `heys_hidden_products` for Poplanton from `_BACKUP_20260510` by
re-running the object→ID conversion that worked the day before.

**Pattern**: never write cleanup / GC functions that decide validity by **shape
inference** (presence of fields). Any future data shape evolution
(normalization, ID-only tombstones, schema version bump) makes the old shape
look like garbage to the cleanup. Use explicit tombstones, version numbers, or
migrations instead.

**Still owed** (see [todo.md](../../todo.md)): rewrite cleanup to handle overlay
v2 shape + pure-ID arrays + backup-key skip list. Until then, the function stays
disabled.
